# lab —— Agent 可靠性评测实验台

> 一套**不依赖任何评测框架**的 Agent 评测与加固工具。
> 被测对象（SUT）是同一个仓库里的 `api/`：一个仿 Manus 的通用 Agent 系统。

```
┌─────────────────────────────────────────────┐
│  测量仪器（lab/bench · lab/trace）           │  ← 看清"发生了什么"
│  ┌───────────────────────────────────────┐  │
│  │  控制手段（lab/guard · lab/faults）     │  │  ← 决定"要不要干预"
│  │  ┌─────────────────────────────────┐  │  │
│  │  │  SUT：api/app 的 Agent           │  │  │  ← 被测对象
│  │  └─────────────────────────────────┘  │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

## 三条命令快速开始

```bash
cd mooc-manus                              # 仓库根目录

# 1️⃣ 任务集自检 —— 不花钱、不需要 API Key，跑评测前必做

# 2️⃣ 跑一个任务（headless，返回结构化结果）

# 3️⃣ 看轨迹树（task → step → tool/llm，含 token 与成本）
python -m lab trace
```

## 为什么要有这个 lab

`api/` 里的 Agent 已经能跑通了，但**"能跑通"不等于"知道它有多可靠"**。
这个 lab 回答四个问题：

| 问题 | 用什么回答 |
|---|---|
| 它做得对吗？ | 28 个确定性任务（12 synthetic / 8 semireal / 8 CI 失败归因）+ 纯函数判定器（不看 Agent 自述） |
| 它每次都能做对吗？ | `pass^k`（任务级 k 次全对）+ Wilson/bootstrap 区间 |
| 钱和时间花在哪了？ | span 级轨迹（task/step/tool/llm 四级）+ 成本归因 |
| 坏了怎么修？ | 10 类故障注入 + 加固中间件 + 对照实验开关 |

## 加固开关（对照实验）

```bash
# 无加固
python -m lab bench run --runs 5 --group semireal --guard none \
  --fault partial_write --fault-tool write_file
# 加固
python -m lab bench run --runs 5 --group semireal --guard all \
  --fault partial_write --fault-tool write_file
```

`--guard` 取值：`all` / `none` / 显式能力名组合（如 `retry,postcondition`）。
也可以用环境变量 `LAB_GUARD`。

> ⚠️ `loop_guard` 与 `budget` 在 observe 模式下**只观测不干预** ——
> 真正影响成败的是 `retry` 与 `postconditions`。
> 关掉前两个只会让报告少两列，不会改变成功率。

### 但上面这两条命令分开跑是**有缺陷的**

两组跑在不同时段时，服务端整体变快/变慢会同时影响两边，**伪装成"加固的效果"**。
本项目真的踩过这个坑（v1 → v3 的 -22%，机制上说不通，最可能就是时段漂移）。

正确做法是**交错 A/B**：两条臂在**同一个 suite 内**交替跑。

```bash
python -m lab bench run --runs 3 --group semireal \
  --fault partial_write --fault-tool write_file \
  --ab-guard none --ab-guard "retry,postcondition,enforce" \
  --label "加固对照（交错）"

# 拆开对比（它们来自同一个 suite，所以时间漂移对两边同权）
python -m lab bench compare <suite_id> --arm "guard=none" --arm "guard=retry+postconditions+enforce"
```

排程是**按轮次轮转**的，不是简单地 A 全部在前：

```
第 0 轮: A, B      第 1 轮: B, A      第 2 轮: A, B
```

轮转是为了让两条臂在"谁先跑"上对称 —— 否则 A 永远处在"刚启动、配额充足"的位置上。

`--runs N` 的含义变成**每个臂各 N 次**（所以总运行数 = 任务数 × N × 臂数）。

## 噪声地板（每个 delta 的分母）

**"同一份代码跑两次能差多少？"** 没测过这个问题，下面这类句子就没有意义：

> B 比 A 便宜 22%

因为同一份代码重跑一次本来就可能差 20%+。

```bash
python -m lab bench noise-floor --runs 3 --group semireal
```

它做的事：把**同一套配置**复制成两个只有名字不同的臂，交错跑。
两臂之间没有任何因果差异，所以观测到的差值除了采样噪声别无解释。

```
噪声地板：成功率 ±3.2pt   成本 ±12.4%   token ±18.1%
```

它会把结果写进 `lab/runs/noise_floor.json`，之后：

- `bench gate` 会**自动读它**，把实测分辨率附在每条门禁旁边；
- 阈值比地板还紧时会显式报"这个门禁会因噪声频繁变红"；
- 加 `--auto-thresholds` 则直接把阈值抬到地板之上（**阈值必须来自数据，不能拍脑袋**）。

> ⚠️ 为什么必须**交错**：分两段跑会把服务端时间漂移算进"地板"，
> 地板被高估 → **真实的退化会被当噪声放过去**。方向恰好是危险的那一边。

## LLM 录制回放（让调试不再花钱）

审计里「可回放」是唯一完全为零的一项：以前复现一次失败必须重新调模型。
现在按 **请求内容**（不是调用序号）做缓存：

```bash
# 1. 录一次真跑（顺带测出"服务端非确定性"）
python -m lab bench run --runs 1 --task syn_sum_range --replay record

# 2. 看缓存里有什么，以及同一请求给过几种不同回答
python -m lab replay stats

# 3. 离线复现（不联网、不需要 API Key）
python -m lab bench run --runs 1 --task syn_sum_range --replay replay
```

| 模式 | 联网？ | 未命中时 | 解决什么 |
|---|---|---|---|
| `off` | 是 | — | 默认，行为与改造前一致 |
| `record` | **总是** | — | 录一次；顺带测出服务端非确定性（不额外花钱） |
| `reuse` | 未命中才联 | 联网并写入 | 改了 prompt 只想重跑受影响的那几次调用 |
| `replay` | **从不** | 直接失败 | 离线复现、无 Key 进 CI |

**三个设计决定，都值得讲**：

1. **键按请求内容算**。按调用序号算的话，上游任何变化都会让整个序列静默错位，
   你会拿到"属于另一个请求的响应"而轨迹看起来完全正常。按内容算，错位变成**显式未命中**。
2. **`record` 总是联网**。如果命中就读缓存，同一个请求永远不会被问第二次，
   "服务端会不会给不同回答"就**永远测不到** —— 那正是温度 0 也消不掉的噪声。
3. **`replay` 未命中必须失败**。偷偷联网会让"离线复现"变成"看起来离线、条件已经变了"。

### 实测发现：SUT 把随机 UUID 放进了提示词

第一次录完立刻严格回放，**未命中 6 次**。诊断直接说出了原因：

```
未命中：前 3 条消息一致，**第 4 条**不同。
  ✅ 抹掉 UUID / 时间戳之后两边完全一致 —— 这是 SUT 在提示词里放了随机 ID，
     **不是你的改动造成的**。
  处置：加 --replay-ignore-volatile（不需要重新录制）。
```

计划步骤的 id 是 `uuid4()`，每次运行都不同 → 含它的请求**在字节层面必然不同**。
加 `--replay-ignore-volatile` 后：

```
评测完成: 1/1 成功，耗时 0.4s        ← 真跑时是 24.5s
命中 18 / 未命中 0（其中 2 次走副键回遯）
等价成本 $0.0571，实际消费 $0.0000
```

> 副键（抹平易变字段后的键）是**录制时就一并存下**的。
> 这一点很重要：你只会在"发现未命中"之后才知道需要这个开关，
> 而那一刻不该再让你**重新录一遍**（重新花钱）。

### 未命中真的失败时，不能假装成功

实测过一种情况：严格回放未命中 6 次，SUT 在 LLM 失败后**降级继续**，
仍然交付了合格产物，判定器于是给出 `OK`。
如果只看 `ok`，一次"只剩半条轨迹"的运行与正常成功**长得一模一样**。

所以：

- 未命中 → 写入过程 flag `replay_misses:N`（进报告的"过程问题"）；
- 报告里单列一节说明"仍然成功 ≠ 复现成功"；
- `bench gate` 多一条**回放完整性**门禁：候选有未命中就直接失败（退出码 1）。

## 怎么加一个任务

在 `lab/bench/tasks/{synthetic,semireal}/` 下加一个 YAML：

```yaml
key: my_task
group: semireal
title: 一句话描述
goal: >-
  给 Agent 的自然语言目标（**必须写清输出路径**，否则判定器无从下手）
tags: [csv, exec]
fixtures:                    # 运行前铺到工作区的输入
  - path: /home/ubuntu/input/data.csv
    content: |
      a,b
      1,2
verify:                      # 判定规则（9 种；只支持**确定性**判定）
  - kind: csv_rows
    path: /home/ubuntu/out.csv
    rows: [["a", "b"], ["1", "2"]]
process:                     # 过程规则（不影响成败，只出 flag）
  max_tool_calls: 15
solution:                    # 参考解 —— **必须真的算一遍，不要直接写期望值**
  - kind: write_file
    path: /home/ubuntu/_solve.py
    content: |
      import pathlib
      pathlib.Path("out.csv").write_text("a,b" + chr(10) + "1,2" + chr(10))
  - kind: exec
    command: "python _solve.py"
wrong:                       # 错误解（用来确认判定器会拒绝错答案）
  - kind: write_file
    path: /home/ubuntu/out.csv
    content: "a,b\n1,3"
```

加完跑 `python -m lab bench validate`，它会对每个任务做三步检查：

| 步骤 | 期望 | 抓什么缺陷 |
|---|---|---|
| 只铺 fixtures | **失败** | 判定器太松 |
| 铺 fixtures + 参考解 | **通过** | 判定器太严 / 参考解写错 / 任务不可解 |
| 铺 fixtures + 错误解 | **失败** | 判定器接受错答案 |

并且会自动检测**同义反复**：如果参考解是"把期望值写出来"，就会告警 ——
因为那样的自检**无法发现期望值本身写错**（这个坑真的踩过，见下）。

## 设计原则

| 原则 | 为什么 |
|---|---|
| **不碰 SUT** | 加固通过代理 `GuardedTool` 注入，SUT 零改动；这样自研 loop 也能接同一套 |
| **判定器是纯函数** | 结论只取决于（规则，产物）→ 可重放、可恢复、可审计 |
| **不看 Agent 自述** | 实测过 SUT"0 个步骤却报成功"；自述只用于**交叉校验** |
| **文本优先** | 当前模型不能读图 → 轨迹与 Pareto 都是文本表（可 grep、可进 CI） |
| **observe 优先** | 预算阈值先只记录不干预 —— 阈值必须来自数据，不能拍脑袋 |
| **阈值来自实测** | 门禁阈值附上噪声地板；`--auto-thresholds` 把它抬到地板之上 |
| **交错而非分两段** | 时间漂移会伪装成方案差异；交错是分离它的唯一办法 |
| **指标不能依赖可关掉的能力** | 工具调用次数曾从 `loop_guard` 取 → `--guard none` 时对照组全为 0 |
| **失败即数据** | 任何一步失败都产出结构化结果，harness 不为单个任务崩掉 |
| **每个数字带区间** | 重尾数据下点估计会骗人；同时给 t 区间与 bootstrap 区间 |
| **诚实声明写进报告** | 混淆、样本量、已知缺陷都写在报告里，而不是藏在注释里 |

## 我错在哪（这一节比数字更重要）

这个项目里有几次自纠，它们比"成功率 100%"更能说明工程判断力：

### 1. 我用了一个自己没验证过的观测手段

评测跑完 38/40 次时我查不到进程，判定"进程被杀了、数据丢了"，
于是做了增量落库 + 写了个 `bench recover` 重建数据 + 在文档里写下"实测教训"。
**实际上评测跑完了**（40/40），只是 `ps aux` 在 Git Bash 下**看不到原生 Windows 进程**，
它给我的 0 是假阴性。

→ 删掉了基于误判写的所有结论，并把**真实理由**（长评测被中断的途径很多）写回代码注释。
保留 `recover` —— 能力本身是对的，但不该由那次假事故来论证。

### 2. 任务集的期望值本身写错了

两个任务的期望值是错的（`TNEGA SUNUM` 应为 `TNEGA SUNAM`；词频 Top3 算错），
**10 次"失败"全部是任务集的错**，Agent 每次都对。

→ 修期望值 + 修参考解（改成真的算一遍）+ 加**同义反复检测**（自检告警 17/20 → 0/20）。
**根因**：参考解是"把期望值写进文件"，它怎么可能发现期望值是错的？

### 3. 主动放弃了一个看起来很好的结论

v1 → v3 的 token/成本下降了 22%，配对检验 7/1 胜、区间不跨 0，看起来是硬结论。
但**我的改动在逻辑上只会增加 token**，而 v1 的崩溃只会减少 token —— 机制上说不通。
最可能是**时间相关的服务端漂移**（两组相隔 2 小时）。

→ 报告里明确写"**不能作为因果结论**"，并指出唯一解法是交错 A/B。
（也因此暴露了另一个缺口：**从没测过噪声地板**，即同代码跑两次能差多少。）

### 4. 沙箱可以被脚本逃逸（安全边界）

fast mode 的路径映射只作用于文件工具与命令行，**管不到脚本内容** ——
脚本里写 `/home/ubuntu/x` 会落到 `<盘>:/home/ubuntu`。
实测：盘根积了 15MB（两个 5MB 的 zip + 24 个分片文件）。

→ 参考解改相对路径 + `LocalSandbox` 加**增量逃逸检测**（初版只判断目录是否存在，
一次评测报了 98 次噪声告警 —— **噪声化的安全告警比没有告警更糟**）+ 清理命令。
并明确记录：**fast mode 只能跑可信任务，不能跑外部输入**。

### 5. "回放失败"其实不是我的代码的问题

刚做完录制回放，严格回放立刻未命中 6 次。
第一反应是"我是不是把键算错了"——**差点去查一个本来就对的地方**。
加了"未命中诊断"后才看清：

```
前 3 条消息一致，第 4 条不同；抹掉 UUID / 时间戳之后两边完全一致
```

根因是 SUT 把 `uuid4()` 生成的计划步骤 id 写进了提示词，每次运行都不同。

→ 做法有两点比修 key 更重要：
1. **诊断信息本身是产品**。未命中只有一个"缓存里没有"时，人会去怀疑自己刚改的代码；
   直接说出"差异只在 UUID"，就把"我改坏了"与"上游有隐藏随机性"区分开了。
2. **发现问题的时刻就是需要开关的时刻，而那一刻不该再花钱**。
   所以副键（抹平易变字段后的键）在**录制时**就存下来，
   `--replay-ignore-volatile` 可以事后开启，**不需要重新录制**。

### 6. 回放未命中 6 次，判定器却说 OK

同样这一轮：严格回放未命中 6 次，**任务仍然判定成功**。
因为 SUT 在 LLM 调用失败后**降级继续**，最后还是写对了产物。

只看 `ok` 的话，一次"只剩半条轨迹"的运行与正常成功长得一模一样 ——
而它会安静地进入您的 A/B 对比。

→ 未命中 → 过程 flag `replay_misses:N` + 报告单列一节 + `bench gate` 增加
**回放完整性**门禁（候选有未命中直接失败）。
**纪律：一个"看起来正常"的结果如果实际上不是完整复现，它就必须响亮地失败。**

### 7. 修好了一处失真，但它不是地板的主因 —— 而我差点把它写成自己的功劳

噪声地板测出 ±29% 后，$0 查出来它主要来自两个**装置缺陷**：
cmd.exe 输出带 `\r\n` + GBK 乱码（Agent 花 10 次调用追行尾）、缺 `sqlite3`（Agent 花 5 次探环境）。

我修了第一个，重测，得到：两臂观测差值 **+29.60% → -3.11%**。
看起来像"修复生效了"。

**但这个归因不成立**，而拦住我的是三件很朴素的事：

| 检查 | 结果 |
|---|---|
| 看**中位数**而不是均值 | $0.0986 → $0.0972，**基本持平** —— 修复没让典型运行变便宜 |
| 看**分辨率**而不是 delta | ±28.9% → ±23.6%，而分辨率才是"看不看得出来"的门槛 |
| 查**机制**而不是只看结果 | `apt-get` 次数 **8 → 8**，那个产生 45 次调用的主因**根本没碰** |

真相：每臂只有 3 次，**一个尾部事件从 A 臂跳到 B 臂就足以把均值差从 +30% 翻成 -3%**。

不过机制层面确实生效了（直接数轨迹，不是推断）：`od -c` 20→4、`cmp` 6→0，
踩坑运行比例 27%→14%。**修好了，但它不是钱的问题。**

→ 结论写成了："✅ 已修且机制已验收" 与 "❌ 不是成本地板的主因" 分开两行，
并把自己猜错的优先级（当时把"修 CRLF"排在第 1、把"缺 sqlite3"判为"先别做"）
原样保留在文档里当例证。

> **这次的教训与第 3 条是同一类错误的不同阶段**：
> 第 3 条是"把噪声当结论"，这次是"把改进归因给自己的改动" ——
> 而两次的拦截手段是同一套：**先测分辨率，再看中位数，最后查机制。**

### 8. 我把"命令文本"当成了"执行证据"，于是修错了东西

`noise-floor-measured.md` §5.1 写过一条结论："fast mode 没有 `sqlite3` 命令行"，
证据是轨迹里出现了 `apt-get`。**这条结论是错的** —— 那些命令长这样：

```bash
which sqlite3 || (sudo apt-get update -y && sudo apt-get install -y sqlite3)
```

`||` 分支**只有 `which` 失败时才会执行**，所以"命令文本里有 apt-get"
不能证明它跑过。用 `result_chars` 标定一下就清楚了：两条命令的历史差值（57）
与"工具存在"情形（60）几乎一致，而"工具不存在"时第二条会**更长**（425 > 249）。

**真正在烧钱的是另一件事**：文件里的 CRLF（地板 suite 里 9.5% 的 shell 调用在追行尾）。
我差点又给一个**不存在的缺陷**写代码（一个 `sqlite3` 垫片），
而它会安静地生效、看起来像"修好了"。

> 拦截手段与第 1 条是同一套：**先标定观测手段，再下结论**。
> 第 1 条是 `ps aux` 给了我假阴性，这次是**命令文本**给了我假阳性。

### 9. 我设计了一个依赖"调用方自觉释放"的稀缺资源

虚拟盘符的第一版是"随用随取 + `destroy()` 时释放"。一次 pytest 就把 **22 个候选盘符全用光**
—— 因为本仓库自己的测试里 **18 处构造 `LocalSandbox`、0 处 `destroy()`**。
而失败方式不是报错，是**静默退化**：后续运行拿不到盘符，逃逸又回来了，没人会发现。

修法有三层，缺一层都不够：池 + `atexit`（正常退出）、**弱引用**（区分"在用"与"对象已被丢弃"）、
属主存活登记（跨进程，绝不抢活着的别的进程的盘符）。

> **设计教训**：稀缺的**进程外**资源（盘符、端口、锁文件）不能依赖调用方自觉；
> 而且"资源在池里"不等于"资源在被使用" —— 这两件事我用一个 bug 才分清。

### 10. 我把"要修的那个变量"用在了"修复它自己"的发现过程里

修 PATH 继承时，第一版用 `shutil.which("git")` 找 Git 的目录 ——
而它读的正是**父 PATH**，也就是要修的那个变量。于是：

- 父 PATH 完好时：一切正常，**测试全绿**；
- 父 PATH 退化时（**恰好是我们要修的场景**）：找不到 Git →"保证目录"变成空集
  → 修复失效，而且**静默**。

拦住它的不是单测（单测进程自己拿着完好的 PATH），而是**端到端探测**：
把父进程 PATH 换成只有系统目录后，子进程仍然一个工具都找不到。

修法两条，缺一不可：
1. 发现过程换成**与 PATH 无关**的来源（注册表 `InstallPath`）；
2. 测试改成**先破坏 `os.environ["PATH"]` 再验证发现** ——
   否则它永远抓不到这个错。

> 这与第 1、8 条是同一类错误：**观测/前提手段本身没有先被验证**。
> 第 1 条是 `ps aux` 假阴性，第 8 条是命令文本假阳性，这次是"修复的自变量污染了自己的发现"。

### 11. 我用一条**过宽**的自动修复，误伤了 40 个文件

为了清掉几条 lint，我跑了 `ruff check lab/ --fix`。我以为它只处理我指定的那几类
（未用导入 / 重定义），但**实际生效的规则集比我预期宽得多**：
实测 **166 处自动改写、波及约 40 个文件**。

危险的不是风格，而是**遮蔽**：真正要审查的改动（虚拟盘符、成本归因、任务集）
被埋在几百行无关的 import 重排里；`# noqa: E402` 这类注释也被顺带删掉，
换个更严的检查器就会重新冒出来。

拦住它的本应是三条很朴素的检查，而我漏了第一条：
1. 改前先看 `--stat` 的影响面（**我没看，改完才看**）；
2. 自动修复必须**限定选择**（`--select F401,F841`），而不是让工具自己决定；
3. 改完立刻跑全量测试（这条我做了，所以功能没坏 —— 但流程上仍然是侥幸）。

> 与第 3、7 条同一类：**行动的影响面没有先被测量**。
