# Step 10：`ci` 组 capability 基线（第一份）

> 对应计划 T9。`ci` 组（CI 失败归因）从 2 个任务扩到 8 个之后的第一份基线，
> 也是**第一次**拿到"归因任务上这个 Agent 到底稳不稳"的数字。

---

## 一、实验配置

| 项 | 值 |
|---|---|
| suite | `26378c08` |
| 任务 | `ci` 组 **8 个**（每个都是"读 CI 日志 → 定位根因 → 修代码 → 写 diagnosis.json"） |
| 规模 | 8 任务 × **3 次** = **24 次运行** |
| 模型 | `deepseek-v4.1-flash`，温度 0.0 |
| 加固 | `guard[all]`（retry + postconditions + loop_guard + budget，enforce 关） |
| 并发度 | 1（耗时可比） |
| 环境指纹 | `dee9039ca1` |
| 预估 / **实际花费** | 预估 $9.54 / **实际 $1.7556**（新模型单价约为旧模型的 1/3，预估用的是同组历史均值） |
| 总耗时 | 2962 s（单次均值 123 s） |

## 二、结果

> 区间口径：比率类用 **Wilson** 区间（小样本下比正态近似稳），
> 任务级 `pass^k` 的区间是同一套 Wilson 公式作用在"任务数"这个更小的 n 上。

| 口径 | 值 | 95% 区间（**Wilson** / 任务级二项） | n |
|---|---|---|---|
| 运行级成功率 | **91.7%**（22/24） | [74.2%, 97.7%] | 24 |
| **任务级 `pass^3`**（3 次全对） | **87.5%**（7/8） | [52.9%, 97.8%] | 8 |
| `pass@3`（至少成功一次） | **100%** | — | 8 |

效率（每次运行均值）：**tokens 449,163**、**成本 $0.0732**、**耗时 123 s**、**工具调用 29.9**。

### 2.2 两次失败都不是"判定器苛刻"，而是真的没做成

| 运行 | `error_type` | 结束方式 | 判定器说什么 |
|---|---|---|---|
| `ci_shared_cache_state` run1 | `task_timeout` | **超过 300 s 硬上限被中断**（实际 312 s） | 三次构建必须互相独立：实际"两个新实例共享了状态" |
| `ci_shared_cache_state` run2 | `agent_error` | LLM 调用失败且**重试 3 次耗尽**（35 s 就结束） | 同上（没修掉类属性被当成实例状态） |

两次的性质不同，这一点值得记下来：
- run1 是**能力+预算**问题（这个任务要读完 CI 日志、定位类属性泄漏、改代码再写归因，300 s 对它偏紧）；
- run2 是**服务端/网络**问题（LLM 连续失败，与任务本身无关）——也就是说，
  91.7% 里至少有一个百分点是"外部故障"，不是 Agent 的判断力问题。

## 三、能说 / 不能说

| ✅ 能说 | ❌ 不能说 |
|---|---|
| "`ci` 归因类任务上，运行级成功率 **91.7% [74.2%, 97.7%]**，`pass^3` = **87.5%（7/8）**" | "它在 CI 归因上不可靠" —— 只有一个任务不稳定，且两次失败原因不同 |
| "唯一不稳定的任务是 `ci_shared_cache_state`（1/3），且其中一次是 LLM 调用失败耗尽重试" | "加固没用" —— 本次没有对照臂（`guard=all` 单臂） |
| "单次均值：$0.0732 / 449k tokens / 123 s / 29.9 次工具调用" | "它比 `semireal` 差" —— 两组任务类型不同，不可直接比 |
| "这是 **capability** 基线：它用来**发现能力边界**，不进回归门禁" | "87.5% 与 100% 有显著差距" —— 区间 [52.9%, 97.8%] 很宽，n=8 |

## 四、必须一起读的三条口径提醒

1. **样本量是任务数（8），不是运行数（24）**：`pass^3` 的区间宽度由**任务数**决定；
   想让区间收窄必须**加任务**，加重复次数没用（`pass^k` 的定义使然）。
2. **独立性假设**：本次并发度为 1，所以不存在"并发引入的相关失败"；
   若以后用 `--concurrency > 1`，`pass^k` 会偏乐观（报告里会自动打这条 caveat）。
3. **噪声地板是当前模型下的 ±46.8%（成本）**：所以本节的**成本**数字只用于"账目"，
   不能用来做方案间比较；可比较的是**成功率口径**（离散指标，本次 n=8 仍然偏小）。
4. **`ci` 组全部标 `capability`**（`test_ci_tasks_are_capability_not_regression` 钉住）：
   在测出方差之前它们不进回归门禁 —— 否则一个不稳定的新任务会让门禁因噪声变红。

## 五、这份基线立刻指出了两件可做的事

1. **`ci_shared_cache_state` 值得单独复测**（$0 的入口：`lab bench show 26378c08 ci_shared_cache_state --run 1`
   看它是"卡在探索"还是"改错了代码"），再决定它是"能力边界"还是"任务太难/超时太紧"。
2. **它的 300 s 上限可能偏紧**：run1 在 312 s 被切断 —— 也就是说这个任务的失败**部分来自预算设置**。
   如果复测确认它经常在 250~320 s 之间完成，应当**按数据调整该任务的 `max_seconds`**
   （而不是全局放宽，那会让真正的死循环跑更久）。
