# Step 9c：稳定损坏 2×2（A1）——Agent 到底靠什么自证

> 承接 `docs/step9b-silent-wrong-2x2.md` §6 指定的**唯一剩余可证伪方向**：
> "让损坏**跨读取保持稳定**（键 = 文件路径而非调用序号）"。
>
> 结论：**负结果**，但它第一次给出了机制层级的解释 ——
> 而且这个解释比 9b 的版本更根本（见 §5）。

---

## 一、为什么做这个实验

前三次面向 Agent 的实验都是负结果（两臂都 100%）：

| 实验 | 故障 | 文档里的机制解释 |
|---|---|---|
| 加固 2×2 | `partial_write`（写路径截断） | Agent 写完会**读回**自证 → 后置校验冗余 |
| T6 | `truncated_result`（读回被截短） | 内容明显不完整 → 一眼看穿 |
| T7 | `silent_wrong_result`（内容错、结构正常） | 重读时**自相矛盾** → 发现 |

三条都指向同一个解释：**"重读不一致"是 Agent 的防线**。

于是 9b 给出了唯一剩下的可证伪假设：

> 如果让损坏**跨读取保持稳定**（同一个文件在整个运行内始终给同一个错值），
> 不一致就消失了 —— 此时 Agent 还能发现吗？

**这个假设是自洽的，而且当时看起来是对的方向**（见 §5 为什么它其实还差一层）。

## 二、实现了什么（`--fault-stable`）

### 2.1 关键认识：`_corrupt_data` 本来就是确定性的

真正的缺陷**不在损坏值的生成**，而在**决策粒度**：

- `_corrupt_data` 对同一输入永远给同一输出（`re.sub` 前 3 个数字 +1）；
- 但 `decide()` 按**调用序号**抛硬币（`rate=0.5`）。

于是同一份文件被读两次时，可能一次中、一次不中 —— Agent 一比对就发现。
实测 T7 的注入次数与 `read_file` 次数一一对应（inj=1/2/3/5 → read=2/3/4/9）。

所以要做的是把决策粒度从**调用序号**换成**目标**（文件路径）。

### 2.2 改动

| 位置 | 改动 |
|---|---|
| `lab/faults/kinds.py` | `FaultRule.stable` 字段；`describe()` 带 `,stable`（**实验条件靠 spec 落库区分**，否则两组数据会混） |
| `lab/faults/injector.py` | `decide(..., target=)`；目标一旦命中就进 `_sticky`，此后**强制继续注入**（跳过 `rate` 与 `max_injections`）；日志区分 `by=random/sticky/sequence` |
| `lab/middleware.py` | `_fault_target(args)` 从工具参数取文件路径（`filepath`/`path`/…）并传给 `decide` |
| `lab/api.py` · `lab/cli.py` | `fault_rules_from_spec(..., stable=)` + `--fault-stable`（三个子命令都接上） |

**语义**：`stable=True` 时，同一目标的第一次读按 `rate` 抛硬币；
一旦命中，此后该目标的**每一次**读都返回**同一个**错值。

> 注意 `rate=1.0` 时 `stable` 是 **no-op**：每次读都已注入，而 `_corrupt_data` 确定性，
> 结果与 stable 完全一致。所以这个开关**只在 `rate<1` 时有意义**，实验也必须用 `rate=0.5`。

### 2.3 顺手修掉的一个**真 bug**（不是本次实验的目标，但会影响它）

`_corrupt_data` 原来用 `str.isdigit()` **判定**、用 `re.sub(r"\d", ...)` **转换** ——
两者语义不同，`str.isdigit()` 更宽：

```
value = 'x²y'      # U+00B2 上标二
any(c.isdigit() for c in value)  →  True      # 命中
re.sub(r"\d", ...)               →  'x²y'     # 一个都不匹配 → 零改动
```

于是 **"命中却没改动"**，而旧代码的 `touched` 却已经被置为 True ——
实验会"以为注入了、其实没注入"，结论静默地错
（`_truncate_data` 里有同样的兜底注释，警告的就是这一类）。

**修法**：判定与转换共用同一张 ASCII 数字表；无数字时走 docstring 早就承诺、
但从未实现的兜底（追加零宽空格）。测试钉住：
`test_corruption_hit_means_content_actually_changed`。

## 三、实验设计

```bash
python -m lab bench run --runs 3 --group semireal --purpose regression \
  --fault silent_wrong_result --fault-tool read_file --fault-rate 0.5 --fault-stable \
  --ab-guard none --ab-guard "retry,postcondition,enforce" \
  --label "A1: 稳定损坏 2x2"
```

- 与 T7 **同组、同臂、同故障、同 rate**，唯一差异是 `--fault-stable` → 可与 T7 直接对照；
- 交错 A/B（同一 suite 内轮转）→ 时间漂移对两臂同权；
- 7 个 `purpose=regression` 半真实任务 × 3 次 × 2 臂 = **42 次**。

## 四、结果

### 4.1 两次运行（第一次遇 provider 故障，见 §6）

| 运行 | suite | 落库 | 实际花费 | 备注 |
|---|---|---|---|---|
| A1-a | `ec8ac13b` | 31/42 | **$1.1221** | provider 403（`Upstream response was not valid JSON`）×多，3 次环境性失败；bash 1h 超时中断 |
| A1-b | `d2c3581f` | 32/42 | **$1.1107** | 无 403；1 次 `task_timeout`；bash 50min 超时中断 |
| **合计** | — | **63 次** | **$2.2328** | 预估 $8.68（按库中同组历史均值 $0.207/次）；实际 ≈ 26% 预估 |

两次都撞到 shell 的时间上限，所以每个 suite 都不完整（42 次）。
但两次合起来覆盖了 **7 个任务 × 2 臂，每格 ≥2 次**。

### 4.2 按"故障是否真的生效"分层（合并两次）

这一层是**必须**的：`rate=0.5` 且有些任务只读 1 次文件，所以有 19/63 次运行
**根本没注入**（`faults_injected = 0`）—— 它们不是"处理组"，混进去会稀释效应。

| 臂 | `inj=0`（未处理） | `inj>0`（故障真的注入） |
|---|---|---|
| `guard=none` | 8/8 | **26/27** |
| `guard=retry+postconditions+enforce` | 11/11 | **17/17** |
| **合计** | 19/19 | **43/44** |

- 44 次有注入的运行里，**唯一一次失败是 `task_timeout`**（不是判定失败）；
- 两臂在"故障真的生效"这一层上都是 ~100% → **加固仍然没有净收益**；
- 与 T7（**非** stable）的 21/21 + 21/21 对照 → **稳定与否都不影响结果**。

### 4.3 sticky 确实生效了（否则本节无意义）

用 `faults_injected` 与 `read_file` 次数对照。若目标是同一个文件被反复读、
且 sticky 生效，则期望 `inj ≈ 0.5k + 0.25(k−1) + 0.125(k−2) + …`（k = 读次数）：

| 观测（inj / read） | 次数 |
|---|---|
| 2/3 | 12 |
| 1/2 | 11 |
| 3/4 | 5 |
| 4/7 · 5/6 · 5/9 · 6/7 · 8/13 · 10/11 | 各 1–2 |

`inj = read − 1` 为主正是 sticky 的特征形态（第一次读没中，之后每次都中）；
k=3 的期望均值 2.125 与观测（2,2,3…）吻合。

> **能说**：`--fault-stable` 在真模型运行里确实让"同一目标的后续读取持续返回同一个错值"。
> **不能说**：这证明了每个目标都被重读（本次没有逐文件的读取键，见 §7）。

## 五、机制：Agent 不靠"重读"自证，靠**执行**

9b 的解释（"重读暴露不一致"）**只对了一半**。真正的机制在工具序列里：

**注入最多的那次运行**（`sem_bug_fix`，`inj=10`）：

```
read_file × 11   shell_execute × 20   write_file × 6   replace_in_file × 3   （共 51 次工具调用）
```

**44 次有注入运行的合计**：

| 工具 | 调用次数 |
|---|---|
| `shell_execute` | **386** |
| `read_file` | 159 |

且 **42/44** 次运行里 `shell_execute ≥ read_file`（只有 2 次例外）。

**结论**：这些任务里 Agent 会**运行代码、看真实行为**。
故障只污染了 `read_file` 这一个通道（`--fault-tool read_file`），
而**执行通道没有被污染** —— 所以 Agent 拿到真相的来源根本不在被损坏的那条路上。

这解释力比 9b 强：**不是"Agent 重读所以发现了"，而是"Agent 有另一条独立通道"**。
只要存在至少一条未被污染的独立通道，只污染读取通道的故障就没有用武之地 ——
无论损坏跨读取稳不稳定。

> 这也是为什么 T6 / T7 / A1 三次都拿到 100%：三次都在同一条通道上做文章。

### 5.1 唯一失败的运行值得单独提一句

`guard=none` 那次 `task_timeout`（`inj=4`，`read_file=7`，`shell_execute=15`）。
**可以说的**：它是超时，不是判定失败，且它确实在反复执行。
**不能说的**：不能据此说"稳定损坏会导致 Agent 打转" —— 单样本、且超时也可能是任务本身慢
（该组的 `task_timeout` 在历史数据里也出现过）。这条只能算**下一个假设**。

## 六、装置问题（这一节和结果同等重要）

| 问题 | 事实 | 影响 |
|---|---|---|
| **provider 瞬时故障** | A1-a 期间大量 `403 · Upstream request failed: [server_error] Upstream response was not valid JSON`（provider: Console Go）；约 1 小时后自行恢复（健康检查 1/1 成功） | A1-a 有 3 次环境性失败、且缺 11 次运行 → **该 suite 的数据不算干净**，所以重跑了 A1-b |
| **单次 bash 调用跑不完 42 次** | 42 次 × ~50–70s ≈ 35–50 min，两次都撞到工具的时间上限 | 两个 suite 都不完整；本次靠"两次合并 + 分层"补偿，**但这不是等价于一次完整运行** |
| **未注入比例高** | 19/63 = 30% 的运行 `faults_injected=0` | 必须分层分析；也说明 `rate=0.5` + 读次数少时"处理强度"不稳定 |

> 这三条都是**测量缺陷**，不是 Agent 的性质。尤其第一条：
> 一个"测量可靠性"的工具，自己依赖的外部服务不稳定 —— 这恰好是它存在的理由，
> 但也意味着**任何单次付费评测都必须先做健康检查**（本次是先跑完才发现）。

## 七、能说 / 不能说

| 能说 | 证据 |
|---|---|
| **稳定损坏没有让这个 Agent 失败**：44 次"故障真的生效"的运行里 43 次通过（唯一失败是超时） | §4.2 分层表 |
| **加固（retry + postconditions + enforce）在本实验里仍无净收益**：两臂在 inj>0 层都是 ~100% | §4.2 |
| **`--fault-stable` 机制在真模型运行里生效**：`inj` 与 `read` 的对应形态符合 sticky 特征 | §4.3 |
| **机制层级的解释**：Agent 有**独立的执行通道**（`shell_execute` 386 次 vs `read_file` 159 次，42/44 次运行 shell≥read），故障只污染了读取通道 | §5 |
| **`_corrupt_data` 曾有一个"命中却零改动"的真 bug**（`isdigit` vs `\d`），已修并有测试 | §2.3 |

| 不能说 | 为什么 |
|---|---|
| "稳定损坏对任何 Agent 都没用" | 只测了 1 个 SUT（课程版 PlannerReAct）+ 7 个半真实任务 |
| "Agent 的自证能力比我们以为的更强" | 真相更可能是"它根本没走那条通道"（§5），不是它更强 |
| "加固没用" | 只测了 3 类故障 × 1 个工具（`read_file`）；写路径与执行路径未测 |
| "稳定损坏导致 Agent 打转" | 唯一失败样本是超时，单样本，§5.1 |
| "成本和 T7 可比" | A1-a 有 provider 故障；两次 suite 都不完整；成本差异需按分层口径比 |

## 八、下一个可证伪的方向

§5 的机制给出了一个**比 9b 更精准**的方向：

> **前提**：此前的负结果都源于"只污染一条通道，而 Agent 有另一条独立通道"。
> **所以**：要测的是**当独立通道不存在时**会怎样，而不是继续在同一条通道上加强损坏。

具体两条（按可执行性排序）：

1. **把损坏放到"不可执行验证"的任务上**（最直接）：
   选/造一类**无法通过运行代码来验证**的任务（例如纯信息提取、需要引用外部编号的任务），
   此时 `shell_execute` 帮不上忙，读取通道才可能是唯一来源。
   验证方法：先数 `shell_execute` 次数（当前任务集里它总是 ≥ read），
   若某类任务里它接近 0，那类任务才是有信息的实验场。

2. **同时污染两条通道**（更强，但要想清楚）：
   把 `--fault-tool` 扩到 `*`（含 `shell_execute`），看 Agent 是否还有第三条路。
   风险：`shell_execute` 的结果被污染后，"执行真值"这个假设本身也不可靠了 ——
   要小心不要把实验变成"测试 Agent 能否识别出整个世界都是假的"。

3. （9b 的原方向，仍未做）**稳定损坏 + 交叉校验型 guard**：
   给 guard 加一个 Agent 提示词里没有的恢复手段（例如用沙箱**独立**读取真实文件，
   绕过被注入的工具返回值），看它是否能救回。这测的是 guard 的**检测面**，
   而不是 Agent 的自证面 —— 与 §5 的机制不冲突。
