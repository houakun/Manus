## 一、实验设计（以及一处与计划的偏离）

```bash
  --fault truncated_result --fault-tool read_file --fault-rate 0.5 \

# 正式（7 任务 × 3 次 × 2 臂 = 42 次）

  --fault truncated_result --fault-tool read_file --fault-rate 0.5 \
  --ab-guard none --ab-guard "retry,postcondition,enforce" \
  --label "读路径静默故障 2x2（C-D）" --yes
```

| 项 | 值 |

## 二、结果：**两臂都是 100%**

| 格 | 成功率 | 95% Wilson | 注入次数 | 后置告警 | 成本 | tokens/任务 | 工具调用/任务 |
|---|---|---|---|---|---|---|---|
| C′ 故障×`none` | **21/21 = 100%** | [84.5%, 100%] | 19 | 0 | $1.79 | 136,517 | 13.76 |
| D′ 故障×`enforce` | **21/21 = 100%** | [84.5%, 100%] | 25 | 5 | $1.91 | 148,085 | 14.62 |

**配对对比（按任务配对，消掉任务难度差异）**：

| 指标 | 配对差值 | bootstrap 95% 区间 | 相对变化 | 方向可信? | 对照地板（±） |
|---|---|---|---|---|---|
| 成功率 | **+0.0pt** | 区间重叠 | 0% | ❌ | ±0.0pt（离散指标，见下） |
| tokens/任务 | +11,568 | [-34,042, +65,208] | +8.5% | ❌ 跨 0 | ±17.2% → **看不出来** |
| 成本/任务 | ≈ +$0.01 | 跨 0 | +6.7% | ❌ 跨 0 | ±16.6% → **看不出来** |
| 耗时/任务 | -1,211 ms | [-7,693, +5,124] | -3.5% | ❌ 跨 0 | ±13.4% → **看不出来** |
| 工具调用/任务 | +0.86 | [-2.7, +4.8] | +6.2% | ❌ 跨 0 | ±16.4% → **看不出来** |

> 成功率那一行的 `±0.0pt` 是**离散指标的假象**（两臂都没有失败 → 配对区间塌成 0），
> **不能**读成"成功率完全可复现"。要看 Wilson 区间：两臂都是 [84.5%, 100%]（n=21）。

## 三、机制：为什么没救回来 —— Agent 自己会**重读**

把"注入次数"与"事件流里的 `read_file` 次数"对上（$0，从 `spans`/`tasks` 数出来）：

| 注入次数 | 该次运行的 `read_file` 次数 | 结果 |
|---|---|---|
| 0 | 0~1 | ✅ 通过 |
| 1 | 2 | ✅ 通过 |
| 2 | 3 | ✅ 通过 |
| 3 | 4 | ✅ 通过 |

**规律非常干净：每被截断一次，就多读一次。** 机制是：

1. `truncated_result` 把读回内容**截短**，但截断是**内容上可见的**（JSON 少了尾部 / 文本半截）；
2. Agent 的循环里本来就有"读 → 检查 → 再读"这个动作（它不依赖 guard）；
3. `rate=0.5` 意味着每次读取有 50% 概率被截断 → 重读 1~2 次即可拿到完整内容；
4. 于是 19~25 次注入**零次**导致任务失败。

对照写路径的负结果（`docs/ab-guard-experiment.md` §3.1：Agent 写完会读回验证）：

> **两处是同一个根因**：只要故障的损坏**能被重新查看发现**，
> 这个 Agent 的自验证循环就会覆盖它，guard 的"恢复"能力没有用武之地。

## 四、能说 / 不能说

| ✅ 能说 | ❌ 不能说 |
|---|---|
| "在读路径静默故障（内容截断、rate=0.5）下，加固对成功率**没有可观测收益**：两臂都 21/21" | "加固无效" —— 只测了**一类**故障、一个故障率、7 个任务 |
| "加固的成本/工具调用增量（+6.7% / +6.2%）**落在地板之内**（±16.6% / ±16.4%）且方向不可信（区间跨 0）" | "加固更贵" —— 区间跨 0，方向不可信 |
| "机制是 Agent **重读**：注入次数与 `read_file` 次数一一对应（inj=1→2 次、inj=2→3 次、inj=3→4 次）" | "所以加固永远无效" —— 只说明**这一类可见损坏**被自验证覆盖 |
| "检测本身是工作的：加固臂触发了 5 条后置校验告警（无加固臂 0 条）" | "enforce 把静默失败变成了可修复失败" —— 没有失败可修，收益无从体现 |
| "两个负结果**同根**：可被重新查看发现的损坏，都会被 Agent 的自验证循环覆盖" | "这个 Agent 免疫所有故障" —— `silent_wrong_result`（结构正常但内容错）还没测 |

## 五、这个负结果为什么仍然有价值

1. **它把"何时该加固"变成了可判定的问题**：不是"加了加固就更稳"，
   而是"**故障是否可被 Agent 重新查看发现**"—— 前者决定有没有收益空间。
2. **它给下一步指定了唯一方向**：只剩 `silent_wrong_result`（内容错但结构正常）这一类
   —— 它**无法**靠重读发现（重读拿到的还是同一个错内容）。
   这正是 T7 的选项 (a)，也是唯一的候选。
3. **它顺手验证了两件事**：故障注入的**读路径**接线是通的（19~25 次注入）；
   后置校验的**内容级**检测能触发（5 条告警）—— 即"检测层"没问题，缺的是"有失败可修"。

## 六、⚠️ 两个必须一起读的口径提醒

1. **本次跑用的是 `deepseek-reasoner`**；跑完后用户把 SUT 的模型换成了
   OpenCode Go 的 `deepseek-v4.1-flash`（见 §7）。**此后任何新跑都不能与本次、
   也不能与地板③（±16.6%）直接比** —— 那是另一个 SUT 行为。
   要花钱做 T7/T9/T13 之前，**必须先在新模型上重测地板**（T13 提前）。
2. **两臂的注入次数不相等**（19 vs 25）。故障注入按**调用序号**触发，
   而两臂的工具调用序列长度不同（加固臂多 0.86 次/任务），所以注入次数天然不同。
   这不影响"成功率都是 100%"这个结论，但它意味着**成本/工具的增量里混着"注入次数不同"**，
   所以那些 +6~8% 的差值**更不能当结论**。
