
两个设计决定：

1. **Pareto 用文本表而不是图** —— handoff 第 1 节写明当前模型不能读图，
   与 Step 2 的 trace 决策一致（文本优先，可 grep、可进 CI）。
2. **两种区间都给**（t 与 bootstrap）—— bootstrap 不假设分布形状，
   对重尾更稳；两者差得多就直接说明"这个均值不稳定"。

## 二、加固前后对比（semireal，n=40 vs n=40）

### 2.1 总体

| 指标 | v1（原始） | v3（加固后） | 变化 |
|---|---|---|---|
| 成功率 | 95.0% [83.5%, 98.6%] | **100.0%** [91.2%, 100%] | +5.0pt |
| tokens/任务 | 210,350 | 163,236 | -22.4% |
| 成本/任务 | $0.1302 | $0.1016 | -22.0% |
| 耗时/任务 | 58.2s | 43.1s | -26.0% |
| 工具调用 | 18.7 | 15.1 | -19.2% |
| **成本/成功任务** | **$0.1371** | **$0.1016** | **-25.9%** |
| 带 `error_type` 的运行 | 5 | **0** | — |

`成本/成功` 是我加的一个复合指标：它把"多少钱"和"做对没有"合成一个数，
比"成本/任务"更能反映真实代价 —— **便宜但总失败是最贵的**。

### 2.2 配对对比（消掉任务难度差异）

| 指标 | 配对差值 | bootstrap 95% 区间 | 相对变化 | 胜/负/平 | 方向可信? |
|---|---|---|---|---|---|
| tokens/任务 | -47,115 | [-82,903, -18,161] | -22.4% | **7/1/0** | ✅ 不跨 0 |
| 成本/任务 | -$0.0286 | 不跨 0 | -22.0% | **7/1/0** | ✅ |
| 耗时/任务 | -15,115 ms | [-31,000, -2,097] | -26.0% | 6/2/0 | ✅ |
| 工具调用 | -3.6 | [-6.0, -1.0] | -19.2% | 6/2/0 | ✅ |

### 2.3 🔴 但这个对比**不是因果结论**（必须写在最显眼处）

配对消除了**任务难度**差异，但**消不掉时间相关的服务端漂移**：
v1 的 40 次全在 18:37–19:16，v3 的 40 次全在 21:02–21:40。
服务端在那个小时整体变快/变稳，会同时影响所有任务 —— 配对**看不出来**。

而且有**反向证据**：我改的三处（D10 重试、工具回灌、收尾兜底）在逻辑上**只会增加** token，
v1 里的两次崩溃又只会**减少** token。所以 -22% 在机制上说不通。

**因此本节的正确读法是**：

| 结论 | 能否下 |
|---|---|
| 失败模式被修好了（5 处 `error_type` → 0） | ✅ **能**（离散事件，与时间无关） |
| SUT 自述变可信了（虚报 1→0、误报失败 4→0） | ✅ **能** |
| 成本/耗时下降了 20~26% | ⚠️ **不能作为因果结论**（时间混淆 + 机制上说不通） |
| Pareto 上 v3 支配 v1 | ⚠️ 同上（但至少说明"加固没有让事情变坏"） |

要下因果结论，唯一办法是**交错 A/B**（A,B,A,B… 共享同一时段）。

### 2.4 一个重要的方法论缺口：**我们不知道噪声地板**

没测过"同一份代码跑两次差多少"（test-retest）。这意味着：
**即使看到 22% 的差异，也无法判断它是否超过测量分辨率。**

这是 Step 5 最大的遗留缺口，也是后续任何 A/B 的前提（约 $4 可补上）。

## 三、失效归因

### 3.1 三次真实故障 → 同一个根因

| 编号 | 触发 | 修复前 | 归类 |
|---|---|---|---|
| D5 | `Plan` 为 `None` | AttributeError 崩溃 | **鲁棒性** |
| D9 | `plan.steps` 为空 | **虚报成功**（做没做都说成功） | **可信度** |
| D10 | `Step.model_validate` 失败 | ValidationError 崩溃 | **鲁棒性** |

根因统一：**提示词要求"必须返回严格 JSON"，但代码没把"违反约定"当可预期情况处理**。

### 3.2 顺带发现的三类"非失败型缺陷"

| 缺陷 | 表现 | 后果 |
|---|---|---|
| **收尾失败 = 任务失败** | 汇总 LLM 挂掉 → 活干完了却报失败（v1 有 4/40） | 拿"会不会收尾"代替了"活干完没" |
| **幻觉工具名 = 崩溃** | `_get_tool` 裸调用抛 ValueError 穿透 flow | 比"返回坏格式"更常见 |
| **失败的步骤被覆盖成完成** | `step.status = COMPLETED` 在循环外无条件执行 | `steps.failed` 统计**恒为 0**，失败率指标失真 |

### 3.3 归因分布（handoff 第 8 节的"定位/规划/验证/工具"雏形）

| 归因类别 | v1 观测 | v3 观测 |
|---|---|---|
| 工具层（`tool:*`、`postcondition` 告警） | tool:path_escape 1 次；后置校验告警 1 条 | 0 |
| 验证层（判定失败但自述成功） | 1 | 0 |
| 规划层（空计划） | 1（D9，D 基线里被当作成功） | 0 |
| 收尾/汇总层 | 4（误报失败） | 0 |
| 环境层（网络） | 2/40 次运行受影响（5 次 Connection error） | — |
| **过程问题（不影响成败）** | too_many_tool_calls 16、low_action_diversity 4、hardcoded_answer 3、path_escape 1 | 7 / 1 / 2 / 0 |

## 四、Pareto 前沿（按任务集分组）

⚠️ 初版把全部 suite 丢在一张表上，结果**一个 n=3 的冒烟 suite 因为运气"支配"了 n=60 的正式基线**。
已修：**必须按任务集分组**（不同任务集/规模根本不可比），且默认排除 n<10 的点。

### 任务集 A：semireal（8 个任务）

| suite | 规模 | 成功率 | 成本/任务 | **成本/成功** | 前沿 |
|---|---|---|---|---|---|
| `80caef04` v3 加固后 | n=40 | **100.0%** | $0.1016 | **$0.1016** | ★ |
| `70a79a26` v1 原始 | n=40 | 95.0% | $0.1302 | $0.1371 | 被 v3 支配 |

### 任务集 B：synthetic（12 个任务）

| suite | 规模 | 成功率 | 成本/任务 | **成本/成功** | 前沿 |
|---|---|---|---|---|---|
| `6895569c` 修正任务期望值后 | n=60 | **100.0%** | $0.0769 | **$0.0769** | ★ |
| `4cc51bc2` 修正前 | n=60 | 83.3% | $0.0769 | $0.0923 | 被支配 |

> 任务集 B 的两个点**成本完全相同**（$0.0769）—— 因为那 10 次"失败"是**任务集的错**
> （期望值写错），Agent 的行为与花费一模一样，只是判定结论从错改成对。
> 这顺便验证了成本核算的一致性。

**要画出真正的 Pareto 曲线（多个取舍点），需要跑多组有意做不同取舍的配置**
（限制迭代次数 / 上下文压缩开关 / 不同模型）。目前只有"加固前 vs 加固后"两个点。

## 五、对照 handoff 第 8 节的指标模板（填真实数字）

| 模板项 | 真实数据 |
|---|---|
| 任务集 | 自建 **20 个**确定性可验证任务（12 合成 + 8 半真实），20/20 通过三步自检，**0 个同义反复验证** |
| 成功率 | **100.0%** [91.2%, 100%]（semireal n=40）；synthetic **100%** [94.0%, 100%]（n=60） |
| 效率 | 15.1 步/任务；163k tokens/任务；$0.1016/任务；耗时中位数 40.5s |
| 故障注入 | 10 类全部实现；实测 `partial_write` 下 token **+198%**、成本 $0.125 |
| 预算 | observe 模式：per-task 分位数阈值使越界率 **100% → 10%**，enforce **0 误杀** |
| 归因 | 工具/验证/规划/收尾四类，详见第三节 |
| 上下文 | 未做压缩（已取消）；实测最长尾单次 953k tokens |
| 判定 | 纯确定性判定器（9 种检查），**未引入 LLM judge** |

### 简历 bullet（用真实数字）

> **Agent 可靠性评测实验台**（个人开源，17.8k 行）
> 为一个仿 Manus 的 Agent 从零搭建评测体系：20 个确定性任务集（三步自检 + 同义反复检测）、
> span 级轨迹、10 类故障注入、预算/熔断/重试/后置校验中间件。
> 定位并修复 3 个同类崩溃/虚报缺陷（结构化输出无兜底）与 3 类非失败型缺陷，
> 使 semireal 成功率 95%→100%、SUT 自述与独立判定从 8 处不一致降到 0；
> 用 per-task 分位数校准预算阈值，越界率 100%→10%，enforce 误杀 0；
> 并**发现自身测量中的时间混淆**，据此放弃无法归因的成本改善结论。

## 六、诚实的限制清单

| 限制 | 影响 | 补法 |
|---|---|---|
| **未测噪声地板** | 任何 <20% 的差异都无法判断真伪 | test-retest（≈$4） |
| **两组时间混淆** | 成本/耗时结论不可因果归因 | 交错 A/B（≈$4 + 运行时开关） |
| 任务集 8 个半真实样本 | 外推到"真实场景"需谨慎 | 扩任务集 |
| Pareto 只有 2 个取舍点 | 画不出曲线 | 跑多组取舍配置 |
| fast mode 沙箱可被脚本逃逸 | 产物可能落到工作区外；**只能跑可信内容** | 容器化 / junction |
| 无 LLM judge | 开放式任务无法评 | 先建确定性基线（handoff 决策 2） |

## 七、`lab` 的能力全景（供 Step 6 开源化用）

```
python -m lab run "目标"              # headless 跑一个任务 → 结构化 TaskResult
python -m lab trace [task_id]         # 轨迹树（task → step → tool/llm）+ 汇总
python -m lab stats                   # 跨运行聚合
python -m lab bench validate          # 任务集三步自检 + 同义反复检测（不花钱，跑评测前必做）
python -m lab bench run --runs 5      # 评测（成本预估 / 增量落库 / per-task 阈值）
python -m lab bench report <id>       # 从库重出报告（不重跑）
python -m lab bench compare A B       # 配对对比 + bootstrap 区间 + 重尾诊断
python -m lab bench pareto            # Pareto 表（按任务集分组）
python -m lab bench recover           # 从中断的评测里救数据
python -m lab sandbox clean-escapes   # 清理脚本逃逸到工作区外的残留
```

**148 个测试**、20/20 任务自检、`python -m lab bench validate` 可直接进 CI（不花钱）。
