# 噪声地板实测：同一份代码跑两次能差多少

> 承接 `docs/step7-replay-noise-interleave.md` §6。
> 这是那个"最大遗留缺口"（`step5-report.md` §2.4）**第一次被真正测出来**。

---

## 一、实验配置

```bash
python -m lab bench noise-floor --runs 3 --group semireal --purpose regression --yes
```

| 项 | 值 |
|---|---|
| 臂 | `noise-a` / `noise-b`（**配置完全相同**，只有名字不同） |
| 排程 | **交错**（第 0 轮 A,B；第 1 轮 B,A；第 2 轮 A,B） |
| 规模 | 跑的时候 8 个任务 × 每臂 3 次 = **48 次运行**；分析阶段按 **7 个 regression 任务** 算 |
| 模型 | `deepseek-reasoner`，温度 0.0 |
| 加固 | `all`（含 retry + postconditions，**不含 enforce**） |
| 实际花费 | **$5.36**（预估 $4.6，偏差来自多跑的那个 capability 任务；单次实测 $0.112/次） |

> 口径说明（顺便记一个自己踩的 bug）：第一遍跑的时候 `--purpose regression`
> **没生效**，跑出了 8 个任务。原因是 `run_suite` 会自己重新加载任务集，
> 而我漏了把 `purpose` 往下传 —— 一个典型的"静态看不出来、跑完才发现"的错。
> 修法是**把口径决定放到分析阶段**（`measure_noise_floor(include_uids=...)`），
> 于是修正不需要重跑：`bench noise-floor --from-suite e23eb282 --purpose regression`，**$0**。
> 上面 48 次与 $5.36 是那一次的真实花费（**多花了那一个任务的钱**）；
> 任务数与地板数字是分析阶段按 7 个算的。这就是"漏传过滤条件"的真实代价。

## 二、结果

> 本节是**第一次测量（修复装置前）**的结果。
> 修了一处装置失真后重测的结果在 §6 —— **成本地板从 ±28.9% 到 ±23.6%**，
> 而且“两臂观测差值从 +29.6% 降到 -3.1%”**不能归因于那次修复**（§6.4）。
> 要引用“当前地板是多少”，请用 §6.3 那张表，不要用本节。

| 指标 | 观测差值 | **测量分辨率（±）** | 单任务最大 | 被个别任务主导? |
|---|---|---|---|---|
| 成功率 | +0.00pt | **±0.00pt** | +0.00pt | 否 |
| 成本（相对） | **+29.60%** | **±28.94%** | +118.17% | ⚠️ 是 |
| token（相对） | **+29.83%** | **±30.56%** | +123.00% | ⚠️ 是 |
| 耗时（相对） | **+26.22%** | **±20.23%** | +83.10% | ⚠️ 是 |
| 工具调用（相对） | **+18.62%** | **±21.55%** | +82.61% | ⚠️ 是 |

**一句话**：两套**完全相同**的配置，成本/token/耗时的差异在 **20~30%** 量级，
而且每一个连续指标都被**个别任务**主导（单任务最大差值 83%~123%）。

### 2.1 三条必须跟着数字一起说的限制

1. **成功率的 ±0.00pt 不能读成"完全可复现"。**
   它是离散指标在"本样本内没有任何任务翻转"时的正常现象 —— 配对区间会塌成 0。
   两臂各 21 次都没翻过，在 90%+ 成功率的系统上**是运气，不是证明**。
   成功率的不确定性应该看 Wilson 区间，不是这个 0。
   换句话说：**这个地板能判连续量，不能判成功率。**
2. **被个别任务主导**（4/5 个指标都是 ⚠️）：成本地板几乎全来自 1~2 个任务的重尾。
   所以"任务级成本"这种细粒度结论，在 n=7 时根本无法支撑。
   要让地板变细只有两条路：**加任务**或**加次数**，换个说法重跑没用。
3. **地板是"同期、同配置"测的**：它衡量的是**本机 + 该服务端在这个时间窗内**的抖动。
   换时段/换服务端/换模型都不保证还成立。

## 三、拿它去重新审所有历史结论

这是测地板的**唯一目的**。把地板的绝对值当阀值，逐条重审：

| 对比 | 观测 delta | 地板(±) | 判定 |
|---|---|---|---|
| v1 → v3（成本） | **-22.0%** | 28.94% | 🔴 **在噪声之内 → 不能当结论** |
| v1 → v3（token） | **-22.4%** | 30.56% | 🔴 **在噪声之内 → 不能当结论** |
| **A → C**（故障注入，成本） | **+108.7%** | 28.94% | ✅ **远超出噪声 → 真实效应** |
| **A → C**（故障注入，token） | **+112.9%** | 30.56% | ✅ **远超出噪声 → 真实效应** |
| C → D（加固，成本） | +31.0% | 28.94% | ⚠️ 刚过地板，但配对区间跨 0 → 方向不可信 |
| C → D（加固，token） | +33.3% | 30.56% | ⚠️ 刚过地板，但配对区间跨 0 → 方向不可信 |

### 3.1 最重要的两条结论

**① v1 → v3 的 -22% 定量确认是噪声。**
`step5-report.md` §2.3 当时是靠**机制推理**放弃这个结论的
（"我的改动只会增加 token，缩减不可能来自它"），并指出"最可能是时段漂移"。
现在有了数字：**-22% 落在 ±28.9% 的地板之内**。
当时那个判断是对的，而且现在它从"推理"变成了"测量"。

**② 故障注入让成本翻倍（+109%）是稳的。**
`ab-guard-experiment.md` §3.1 用它论证"故障注入确实生效"。
现在可以确认：**+109% 是地板的 3.7 倍**，这个结论不受噪声威胁。
**这是目前项目里唯一一个"幅度远超测量分辨率"的因果结论。**

### 3.2 ⚠️ 地板不能替代显著性检验（一个必须讲清的区别）

C → D 的 +31% > 地板 28.94%，看起来"超出噪声"，
但 `ab-guard-experiment.md` 里它的配对 bootstrap 区间**跨 0**。

两者不矛盾，因为它们回答的是**不同的问题**：

| | 问的问题 | 在本例中 |
|---|---|---|
| **噪声地板** | 两个值**不同**，我分得出来吗？（测量分辨率） | +31% > ±29% → 分得出来 |
| **bootstrap 区间** | 这 +31% 的**方向**，我信得过吗？（推断） | 区间跨 0 → 信不过 |

而且严格说这一行还有第三个问题：地板是**同一配置**、**7 个任务**上测的，
而 C/D 是**不同配置**、**8 个任务**（含 capability 任务）上比的 ——
任务集和配置都不同，所以"31% > 29%"这个比较本身只是粗略的。

> **纪律**：地板是**门槛的下界**（小于它一定看不见），
> 不是**结论的证明**（大于它不等于结论成立）。
> 两个都要看，而且都要写出来。

## 四、它立刻改变了什么

### 4.1 门禁阈值原来比噪声还紧

`bench gate` 现在会自动读这个地板并当场报警：

```
> ⚠️ 阈值比噪声地板还紧：成本（相对）(阈值 20.0% < 地板 ±28.94%)
>    这种门禁会因为噪声频繁变红 —— 而频繁变红的门禁等于没有门禁。
```

原来的默认阈值（成本 20%）**低于测量分辨率**，也就是说：
**它本来就会因为噪声而频繁变红**。这正是 `evaluate_gates` 的注释里
担心的那件事（"频繁变红的门禁等于没有门禁"），现在有了实测依据。

处置两条路，都已可执行：

```bash
# ① 把阈值抬到地板之上（阈值必须来自数据）
python -m lab bench gate --baseline <id> --auto-thresholds

# ② 或者把地板压下去：加任务 / 加次数（这才是根本办法）
python -m lab bench noise-floor --runs 6 --group semireal --purpose regression
```

### 4.2 现在可以说的和不能说的

| 能说 | 不能说 |
|---|---|
| "故障注入让成本 +109%，是地板的 3.7 倍" | "加固让成本 +31%，所以加固更贵"（方向不可信） |

## 五、地板是被什么撑起来的（$0 查出来的）

地板宽到 ±29% 时，第二个问题应该是：**哪一个任务在搞事，为什么？**
（第一个问题是"地板是多少"）。逐任务拆开：

| 任务 | noise-a 成本 | noise-b 成本 | 差值 |
|---|---|---|---|
| **`sem_sqlite_report`** | **$0.0875** | **$0.1908** | **+118.2%** ← 主导 |
| `sem_bug_fix` | $0.0370 | $0.0521 | +40.9% |
| `sem_json_to_csv` | $0.0794 | $0.1008 | +27.0% |
| `sem_refactor_config` | $0.2033 | $0.1632 | -19.7% |
| `sem_log_analyze` | $0.1082 | $0.1268 | +17.2% |
| `sem_config_merge` | $0.0652 | $0.0753 | +15.4% |
| `sem_csv_clean` | $0.1706 | $0.1846 | +8.2% |

单个任务内部再看：

| 臂 | run | 工具调用 | token | 成本 | 耗时 |
|---|---|---|---|---|---|
| a | 0 / 1 / 2 | 15 / 16 / 15 | 126k~154k | $0.077~0.098 | 30~43s |
| b | 0 / 1 / **2** | 20 / **45** / 19 | 165k~**520k** | $0.100~**0.306** | 37~**84s** |

**同一任务、同一配置、成本差 4 倍。** 把那次 43 条命令的轨迹读一遍就看见了两个机制：

### 5.1 前 5 次调用全在探环境

```
0  which sqlite3 || (sudo apt-get install -y sqlite3 && which sqlite3); sqlite3 --version
1  sudo apt-get update -y >/dev/null 2>&1; sudo apt-get install -y sqlite3 ...
2  echo hello && uname -a && whoami && pwd
3  which sqlite3; command -v sqlite3; ... which python3 python py
4  sqlite3 --version 2>&1; echo "exit=$?"
```

**根因**：fast mode 的 shell 是 Windows `cmd.exe`，而且**没有 `sqlite3` 命令行**。

> 🔴 **更正（见 `docs/step8-device-fixes.md` §2）：这条根因是错的。**
> 它是从**命令文本**推断的（那些命令写成 `which sqlite3 || (sudo apt-get install …)`，
> 而 `||` 分支只有 `which` 失败时才会执行），而 `result_chars` 标定显示
> **当时 `which sqlite3` 是成功的、`sqlite3` 一直可用**。
> 那次 20 步运行的真正成因是**产物文件里的 CRLF**（§5.2 描述的模式，只是归错了对象）。
> 本行保留原文，作为"把命令文本当执行证据"的例证。

而任务 YAML 的 `solution` 注释里**已经写了**这件事：

```yaml
solution:
  # 注意：宿主环境没有 sqlite3 命令行，必须用 python 的 sqlite3 模块；
```

**但 `goal`（给 Agent 看的）里没写。** 于是 Agent 必须自己试出来 —— 试多久看运气。
这是"参考解知道答案而题目没说"的典型漏失。

### 5.2 第 29~38 次调用在追 CRLF

```
29  grep -n . report.txt; wc -l report.txt; od -c report.txt | head -n 5
31  cmp report.txt <(printf 'south=450\nnorth=400\n') && echo IDENTICAL || echo DIFFERENT
34  od -c report.txt
35  tr -d '\r' < report.txt > report_lf.txt
38  cmp report.txt expected.txt && echo IDENTICAL || echo DIFFERENT
```

**10 次调用全在确认行尾。** 为什么 Agent 会去查？因为它在上下文里看到了 `\r\n` ——
而那是真实的：实测确认 **cmd.exe 的一切输出都带 `\r\n`**：

```python
exec_command(... 'command -v sqlite3 || echo ABSENT')
→ output: "...'command' 不是内部或外部命令...\r\nABSENT\r\n"
```

### 5.3 顺带发现：错误信息是 GBK 乱码

```
output: "'command' �����ڲ����ⲿ���\n���������ļ���\r\n"
```

cmd.exe 的中文错误信息按错误编码解出来是乱码，**直接进 LLM 上下文**。
这不但浪费 token，还会让模型对"当前环境到底发生了什么"判断失准 ——
它可能因此多跑几轮去确认。

### 5.4 结论：地板量的是**整个装置**，不只是模型

这一节的数字推翻了一个很容易下的结论：

> ~~"同一份代码成本差 29%，说明模型服务端很不稳定。"~~

实际构成是：**模型服务端抖动 + 任务环境不可控 + 沙箱输出格式污染**。
后者两项是**可以修的工程问题**，而它们很可能占了大头。

> 这也正好验证了 §2.3 的那条提醒（"如果 delta 大得离谱，先怀疑**实验装置**"）——
> 当时那是一条原则，现在它有了具体清单。

**另一个呼应**：本 suite 里 `too_many_tool_calls` 这个**过程 flag 一共响了 13 次**。
项目早就在报警了，只是那时没有地板去说明
**"这 13 次报警撑起了 29% 的测量分辨率"**。现在这两件事接上了。

## 六、修复一轮之后：哪里真的变了，哪里没变

### 6.1 改了什么

只改了一处（**一次只改一个变量**）：`LocalSandbox` 解码子进程输出时
①把行尾 `\r\n` 归一为 `\n`，②逐行试 UTF-8 → 失败则回退 OEM 代码页（cmd.exe 的 GBK）。
理由：目标环境是 Ubuntu，真沙箱不会输出 CRLF 与 GBK 乱码 ——
归一是在**降低测量误差**，不是掩盖问题。

### 6.2 先看**机制**层面：修复确实生效了

不看成本，先数那条轨迹模式出现了几次（全用轨迹数据，$0）：

| 轨迹模式 | 修复前（48 次运行） | 修复后（42 次运行） | 每 42 次归一 |
|---|---|---|---|
| `od -c`（看字节） | 20 | **4** | 17.5 → 4 |
| `cmp`（比对文件） | 6 | **0** | 5.3 → 0 |
| `uname -a`（探系统） | 8 | **2** | 7.0 → 2 |
| `which` / `command -v`（探环境） | 34 | 18 | 30 → 18 |
| `apt-get`（装 sqlite3） | 8 | **8** | 7.0 → 8 |
| 含上述任一模式的运行数 | 13/48（27%） | **6/42（14%）** | —— |

**"追行尾"这一类浪费几乎消失了**（`od -c` 20→4、`cmp` 6→0），
踩坑的运行比例从 27% 降到 14%。这是直接证据，不是推断。

### 6.3 再看数字：**没变**

| | 修复前 | 修复后 |
|---|---|---|
| 每臂每任务成本**中位数** | $0.0986 | **$0.0972**（基本持平） |
| 每臂每任务成本**均值** | $0.1175 | $0.1091 |
| 成本**测量分辨率** | ±28.94% | **±23.64%**（改善有限） |
| 单任务最大差值 | +118.17% | **+65.12%**（同量级） |
| 成功率 | 48/48 | 42/42 |

### 6.4 🔴 最关键的一条：**我没法把那个改善归因给自己**

两臂观测差值从 **+29.60% → -3.11%**，看起来像"修复生效了"。
**但这个结论不成立**，理由三条：

1. **中位数几乎没变**（$0.0986 → $0.0972）。如果修复真的省了钱，典型情况应该变便宜。
2. **分辨率只从 ±28.9% 到 ±23.6%**，而分辨率才是"看不看得出来"的门槛。
3. **每臂只有 3 次**：一个尾部事件从 A 臂跳到 B 臂，就足以把均值差从 +30% 翻成 -3%。

看一眼符号分布就更清楚了：

| | 正差值任务 | 负差值任务 | 最大项 |
|---|---|---|---|
| 修复前 | **6/7** | 1/7 | `sem_sqlite_report` **+118.2%** |
| 修复后 | 3/7 | 4/7 | `sem_refactor_config` **+65.1%** |

修复前 6/7 同号 —— 那是**偏差**的特征（同配置两臂应该没有方向）。
修复后符号混合，看起来像噪声。**但只换了一个众数方向，不证明是我的改动造成的。**

### 6.5 真正的原因就在自己刚做的表里

回到 6.2 的表：**`apt-get` 8 次 → 8 次，一点没变。**

也就是说，**产生极端运行的那个机制（缺 sqlite3）我根本没碰**。
而它正是 45 次调用、520k token 那条运行的成因。

所以正确的说法是：

| 问题 | 状态 |
|---|---|
| CRLF + GBK 乱码 | ✅ **已修，机制层面已验收**（`od -c` 20→4、`cmp` 6→0） |
| 但它**不是成本地板的主因** | ❌ 中位数没降，分辨率只小幅改善 |
| 缺 `sqlite3` | 🔴 **已证伪**（`sqlite3` 一直可用）—— 见 `docs/step8-device-fixes.md` §2。真正烧钱的是**文件里的 CRLF**，已在 Step 8 修复 |
| 产物逃逸（绝对路径） | ❌ 未动，而且在这一轮**真实导致了一次任务失败**（见 §8） |

> **这一小节比任何数字都重要**：我差一点就把"+29.6% → -3.1%"写成自己的功劳。
> 拦住它的是三件很朴素的事：**看中位数而不是只看均值**、
> **查机制而不是只看结果**、**记住 3 次重复撑不起一个归因**。
> 这也正好是本项目一直在讲的那条纪律 —— 本文件 §3.2 刚用过一次，转头自己就差点犯。

| 🥈 | **产物逃逸（脚本里的绝对路径）** | 本轮真实导致 1 次失败 + 3 次逃逸告警 | 事后搬文件的方案在 **`--concurrency > 1` 时会互相抢同一个盘根目录** —— 需要先定并发语义 |
| 🥉 | 重测地板（在两个修完之后） | 只有前两项都落地，才能知道地板到底能降到多少 | —— |

`sqlite3` 的三个方案：

| 方案 | 保真度 | 代价 / 风险 |
|---|---|---|
| (a) 往 PATH 里放一个 `sqlite3` 垫片（转调 Python 的 sqlite3 模块） | 中 —— 输出格式与真 CLI 有差异，而格式差异本身会造噪声 | 纯代码、可移植 |
| (b) 把"无 sqlite3 CLI"写进任务的 `goal` | 低 —— 等于改题目去将就装置 | ⚠️ **该任务历史数据全部失效** |
| (c) 沙箱里预置真的 `sqlite3` 二进制 | **高** | 要把二进制进仓库（或首次运行时下载） |

**建议 (c)，不行再 (a)**：目标是让 fast mode **像** Ubuntu，而不是让题目变得容易。

## 八、另一个独立发现：产物逃逸导致了一次真实失败

修复后的定向重测里出现了一次 `FAIL`：`sales.db 期望存在=True，实际=False`。报因如下。

Agent 先 `write_file` 了一个脚本，内容里有**绝对路径**：

```python
DB_PATH = "/home/ubuntu/sales.db"      # ← 写进了文件内容
REPORT_PATH = "/home/ubuntu/report.txt"
```

然后 `shell_execute: python3 /home/ubuntu/create_report.py`。
`_rewrite_paths` 只重写了**命令字符串**里的 `/home/ubuntu`（脚本路径被重写对了），
但**管不到文件内容** → Python 把 `DB_PATH` 解成 `D:/home/ubuntu/sales.db`，写到工作区外。

| 后果 | 说明 |
|---|---|
| 任务被判失败 | 数据库文件不在工作区，判定器看不到 |
| 不可归因 | `error_type` 是空，因为 SUT 自己认为成功了 —— **看起来像"Agent 写错代码"** |

这正是模块里已经记录过的已知限制（`_escaped_root` 的注释），
但本轮第一次拿到它**直接导致失败**的证据 —— 以前只见过"产物落到工作区外"的告警。
