## 三、关键设计决策

### 3.1 任务集三步自检（这一步救回了一个有缺陷的任务）

每个任务都要过：空工作区必须**失败**、参考解必须**通过**、错误解必须**失败**。

**它立刻抓到了一个真问题**：`sem_sqlite_report` 的错误解（漏写 `ORDER BY`）**居然通过了判定**——
因为那份数据下 SQLite 的自然行序恰好等于降序结果，判定器根本区分不出来。
修法是把数据设计成 `south > north`，让"漏 ORDER BY"必然产生不同行序。

> 如果没有这一步，这个任务会在报告里给出"100% 成功"的假象，
> 而且它会掩盖所有排序类错误 —— **一个永远通过的判定器比没有判定器更糟**。

### 3.2 判定只看产物，并且**与 SUT 自述交叉校验**

`ok` 只来自对工作区文件的检查，`result.ok`（SUT 自述）单独统计并对比。
实测证明这个分离是必要的（见四.2）。

### 3.3 结果分与过程分是两个独立维度

`ok`（结果）+ `process_flags`（效率/越权/硬编码/原地打转）。
**过程问题不影响成功率** —— 否则"成功率提升"就无法归因了：
可能是模型变强，也可能只是放宽了过程要求。

### 3.4 比率用 Wilson 区间，连续量用 t95

n 小或 p 接近 0/1 时，正态近似会给出越界区间（5/5 成功 → `±0`，等于宣称"不可能失败"）。
Wilson 在 5/5 时给出 `[56.6%, 100%]` —— 这才诚实地表达"样本太少"。

### 3.5 区间不够宽时显式警告

n≤3 时 t 区间会宽到出现负值（如 tokens `[-1.1M, 1.4M]`）。
处理方式：非负指标把下界截到 0，**同时**在区间后打 ⚠️ 并注明"比点估计还宽 → 没有信息量"。
截断是为了可读性，⚠️ 是为了不掩盖事实。

## 四、实测发现（Step 4 的核心产出）

### 4.1 两次冒烟运行的对比

| suite | 任务 | 结果 | 成功率 | 95% 区间 |
|---|---|---|---|---|
| `beee03f1` | 2 个 × 1 次 | 1/2 | 50.0% | [9.5%, 90.5%] |
| `9e1da7da` | 3 个 × 1 次 | 3/3 | 100.0% | [43.8%, 100.0%] |

同温度 `0.0`、同一 SUT、同一任务集子集。

### 4.2 🔴 SUT 会**虚报成功**：0 步骤 0 工具却 `ok=True`

`beee03f1` 里 `syn_log_error_count` 被判失败，但 SUT **自报成功**。
查轨迹找到了原因：

```
[OK ] task=3dc1d79a  目标: 统计日志中 ERROR 行数...
计划   : 统计日志文件中 ERROR 行数并写
结果   : steps=0/0  tools=0  llm=1  tokens=2138  cost=$0.0018  elapsed=3000ms
└── [task] ✓ @0ms +3.1s  steps=0/0
    └── [llm] ✓ @2993ms  in=1785 out=353
```

**PlannerAgent 产出了一个 `steps=[]` 的空计划**，flow 直接走到 COMPLETED，
一个工具都没调、什么都没产出 —— 而 `TaskResult.ok` 是 `True`、`error` 是 `None`。

这是我 Step 1 修的 D5 的**同族但不同分支**：D5 处理的是 `plan is None`，
而这里是 `plan` 存在但 `steps` 为空。**当前没有修 SUT**，理由：
- 它不阻塞测量（判定器已经独立发现了）；
- 它是一个真实且典型的失败模式，留着它作为基线的一部分更有价值；
- 是否修属于 SUT 的设计决策，应该由你决定（修法：`steps` 为空时 `yield ErrorEvent`）。

**报告里已经把这个差异变成一项指标**（"SUT 自述 vs 独立判定"）：
如果只看 `result.ok`，`beee03f1` 的成功率会被读成 100%，而真相是 50%。

### 4.3 🔴 同一任务跨 suite 结果翻转（同温度 0.0）

| 任务 | `beee03f1` | `9e1da7da` |
|---|---|---|
| `syn_log_error_count` | ❌ 失败（0 步空计划） | ✅ 通过 |

再加上 Step 1 记录的"同任务两次 token 差 34%"，可以确诊：
**这个 SUT 的不确定性来自 Agent 循环本身（路径依赖 + 空计划这类边界），
而不是采样温度。** 这直接决定了加固工作的靶子：
不是"调低温度"，而是"消除空计划、约束循环、压缩上下文"。

### 4.4 n 太小的时候，区间宽到没有信息量

`9e1da7da`（n=3）：

```
tokens/任务  121,808  [0, 308,820] ⚠️
成本/任务    $0.0754  [$0, $0.1895] ⚠️
工具调用     15.33    [0.00, 36.75] ⚠️
```

每行都带 ⚠️（区间比点估计还宽）。这就是 handoff 第 8 节坚持要
`n=5, 95% CI` 甚至 n≥20 的量化理由 ——
**n=3 时你连"这个任务平均花多少钱"都说不出来**。

### 4.5 成本与时间的现实数字（决定 baseline 规模）

| 指标 | 实测 |
|---|---|
| tokens/任务（均值 / max） | 96,323 / 203,326 |
| 成本/任务 | ≈ $0.06（均值），单任务最高 $0.125 |
| 耗时/任务 | 均值 28.5s，P95 57s |
| 工具调用/任务 | 均值 12.1 |

### 4.6 平台约束：fast mode 的 shell 是宿主 shell

探测结果（Windows + cmd.exe）：

| 命令 | 可用 |
|---|---|
| `python` | ✅ 3.13.2 |
| `python3` | ❌（rc=9009） |
| `sqlite3` CLI | ❌ |
| `sed` | ✅（Git 提供） |
| `$(...)` / 单引号参数 | ❌（cmd.exe 不支持） |

所以任务解法写成**平台中立的 python 一行式**（只用单引号、不加换行）。
这是 fast mode 的固有限制（真沙箱是 Linux），已记入已知限制。

### 4.7 后续修正：`syn_rename_files` 判定强度不足（由一次质疑引出）

有人问"这个任务失败是不是故意设计的" —— 核查后确认它**从未失败过**（详见下），
但这次质疑让我重新审视了它的判定规则，发现了**两个真实的验证缺口**：

| # | 缺口 | 后果 | 修正 |
|---|---|---|---|
| 1 | 只验“文件名变了”，不验“内容还在” | `rm a.txt && touch a.md` 也能通过 —— **内容丢了却判成功** | 新增 2 条 `file_content` 检查 |
| 2 | `dir_count == 4` 不约束是哪 4 个 | 删掉 `notes.log` 再建 `extra.md`，数量仍是 4，全部检查通过 | 新增 `no_extra_files` 白名单检查 |

验证过程（修正前 6 条全过、修正后 2 条报错）：

```
✗ file_content | a.md 内容: 期望 'alpha'，实际 ''
✗ file_content | b.md 内容: 期望 'beta'，实际 ''
```

并补了 3 个回归用例（破坏性重命名、文件被掉包、正确做法必须通过）。
最后一个是必需的：没有它，前两个"拒绝对错答案"的用例可以靠"永远返回失败"蒙混过关。

**刻意不做的事**：不检测"工作区里留下了临时文件"。
真实运行中 Agent 把 `before.md5` 写到了 `/home/ubuntu/tmp/` ——
但 SUT 的提示词本来就要求它把中间结果存成文件，把这种正常行为当问题会制造大量假阳性。
这正是"验证强度"的取舍点：**要抓住真问题，但不能把正常行为当问题**。

## 六、需要你决定：baseline 的规模（要花真钱）

| 方案 | 运行数 | 预估成本 | 预计耗时（并发 1 / 并发 4） | 能得到的结论 |
|---|---|---|---|---|
| **A. n=1 全量** | 20 | **≈ $1.5** | 10 min / 3 min | 只有成功率点估计，**无法区分噪声** |
| **B. n=5 全量** ⭐ | 100 | **≈ $7.5** | 50 min / 15 min | 能给出 95% CI，是 handoff 第 8 节模板要求的规模 |
| **C. n=20 全量** | 400 | **≈ $30** | 3.3 h / 50 min | 单任务级置信区间，可以定量说"哪个任务不稳定" |
| **D. 先只跑 semireal** | 8×5=40 | **≈ $3** | 20 min / 6 min | 先看"半真实任务"是否明显更难（最有信息量的子集） |

**我的建议：先 D 再决定**。理由：
- semireal 的 8 个任务是"能不能代表真实场景"的关键证据，
  如果它们的成功率显著低于 synthetic，那才是真正值得研究的东西；
- 只花 $3、6 分钟就能拿到第一批带区间的数字；
- 拿到之后再决定要不要为 synthetic 花剩下的钱。

另外提醒：**耗时数字在 `--concurrency > 1` 时不可横向比较**（并行会互相争抢配额与本机资源），
所以并发跑只用于"拿成功率/成本"，不要用它比较响应速度。

回复 **A / B / C / D（或自定义）** 我就开跑并出正式报告。
