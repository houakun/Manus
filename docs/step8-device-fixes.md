## 二、🔴 先纠正一个已经写进文档的结论

`noise-floor-measured.md` §5.1 写的是：

> **根因**：fast mode 的 shell 是 Windows `cmd.exe`，而且**没有 `sqlite3` 命令行**。

**这个结论是错的。** 它的证据是"命令文本里出现了 `apt-get`"，但那些命令长这样：

```bash
which sqlite3 || (sudo apt-get update -y && sudo apt-get install -y sqlite3)
```

`||` 分支**只有 `which` 失败时才会执行**。命令文本里永远含 `apt-get`，
所以"数命令文本里的 apt-get"根本不能证明它跑过 —— 这是**把文本当执行证据**。

### 2.1 标定实验（$0，可复现）

在两种环境下跑同样的两条命令，量 `result_chars`（跨度记录里就有这个字段）：

| 命令 | A：工具存在 | B：工具不存在 | **历史记录** |
|---|---|---|---|
| `which sqlite3 && sqlite3 --version` | **317** | 249 | **347** |
| `which sqlite3 \|\| (sudo apt-get …)` | **257** | 425 | **290** |

判读：

- 两条命令的历史差值 **347−290 = 57**，与 A 情形的 **317−257 = 60** 几乎一致；
- B 情形下第二条会**更长**（425 > 249，因为 `which` 报错 + `sudo` 被禁用各有一段文本）；
- 历史值的整体偏移（约 +31）来自 `result_chars` 是在**中间件注解之后**量的。

结论：**当时 `which sqlite3` 是成功的**，`sqlite3` 一直可用。
（它来自 Git for Windows 的 `D:\devople\Git\usr\bin\sqlite3.exe`。）

### 2.2 那么那次 20 次调用的运行在干什么？

读 `run1-noise-a` 的产物：**`report.txt` 是 CRLF**。轨迹里是
`tr -d '\r'` → `cmp` → `od -c` → `nl` → `sed -n` → `grep -n` → `awk` ——
**10 次调用全在追行尾**，与 `noise-floor-measured.md` §5.2 描述的模式一致，
只是那次把它归因错了对象。

## 三、修复 ①：工作区内文本文件的 CRLF 归一

### 3.1 机制（两个 Windows 行为，Ubuntu 上都不存在）

| 来源 | 为什么产出 CRLF |
|---|---|
| 原生程序重定向（`sqlite3 … > report.txt`） | Windows 原生可执行文件的文本模式 stdout 把 `\n` 翻成 `\r\n` |
| **Python 文本模式写入**（`write_text` / `open('w')`） | Windows 上文本模式会做 `\n` → `\r\n` 翻译 |

**换 shell 治不了**：实测用 Git bash 执行 `sqlite3 … > out.txt` 与
`python -c "print('x')" > out.txt`，产物**同样是 CRLF** —— 因为被重定向的是
**原生 Windows 程序**，翻译发生在程序内部，不在 shell。

### 3.2 为什么"归一"是保真而不是篡改

目标环境是 Ubuntu，在那里上面两条路径都产出 **LF**。归一是在让本地产物
与目标环境一致 —— 与已经做过的 `decode_command_output`（命令输出行尾归一）同一个理由。
**保留 CRLF 才是失真**：它让模型去修一个它在真环境里根本遇不到的问题。

### 3.3 实测浪费（$0，从 `traces.db` 数出来）

地板② suite（`b1796efd`，即"修过命令输出行尾之后"）：

```
shell 调用 294 次，其中 28 次是追行尾 = 9.5%
  按任务：sem_csv_clean 16、sem_sqlite_report 4、sem_json_to_csv 3、
          sem_log_analyze 3、sem_refactor_config 2
```

`sem_csv_clean` 的 fixture **本身没有 CRLF**（YAML 块标量会把行尾归一成 LF，
29 个 fixture 里 0 个含 CRLF）—— 所以那 16 次追的是**它自己刚写出的产物**。

### 3.4 取舍与开关

- 只看**工作区内部**（工作区外的东西本来就该被判定为逃逸）；
- 含 **NUL 字节**的按二进制跳过（数据库 / zip / 图片不能动）；
- 只处理 `\r\n`，不动单独的 `\r`（那可能是进度条等有含义的内容）；
- 单文件 >2MB、单次 >200 个文件则跳过；
- 环境变量 `LAB_SANDBOX_NORMALIZE_CRLF=0` 可关闭（**对照实验的前提**，
  与 `--guard none` 同一个道理）；
- ⚠️ 已知语义边界：**故意**写 CRLF 的文件也会被归一。当前 22 个任务没有一个依赖
  CRLF（0 个 fixture 含 `\r`，也没有任何检查项断言行尾），所以现在没有影响。

### 3.5 代价（实测）

| 工作区文件数 | 归一开 | 归一关 | 开销 |
|---|---|---|---|
| 0 | 38.6 ms/命令 | 34.3 ms/命令 | **+4.3 ms** |
| 20 | 51.6 ms/命令 | 28.7 ms/命令 | **+22.9 ms** |

相对于"一次命令 ≈ 1~2s 的模型时间 + 一次可能白花的调用"，这个开销可以忽略。

## 四、修复 ②：虚拟盘符（把脚本里的绝对路径导回工作区）

### 4.1 问题

`noise-floor-measured.md` §8 记录过：Agent 写的脚本里
`DB_PATH = "/home/ubuntu/sales.db"`，而路径映射只作用于**文件工具**与**命令行字符串**，
**管不到脚本内容** → Python 把无盘符绝对路径解析成 `<当前盘>:/home/ubuntu/sales.db`
→ 产物落在工作区外 → 判定器读不到 → **正确的工作被判失败**，
而且 `error_type` 为空（SUT 自己以为成功了），看起来像"Agent 写错代码"。

### 4.2 为什么不是"改写脚本内容"

那会把 `D:\...` 这种 Windows 路径泄进模型上下文（它写什么、下次读回就看到什么），
直接破坏"我在 Linux 上"这个假设 —— 用一个失真换另一个失真。

### 4.3 机制：`subst` 虚拟盘

Windows 的**无盘符绝对路径按"当前盘"解析**。所以：

1. 每次运行 `subst X: <工作区根>`；
2. 子进程的 **cwd 落在该盘上**（`X:\home\ubuntu`），于是当前盘 = `X:`；
3. `/home/ubuntu/x` 自动解析成 `X:\home\ubuntu\x` = **工作区里的同一位置**。

**脚本一个字都不用改**，模型看到的还是 `/home/ubuntu/x`。

### 4.4 为什么它优于"在盘根建 junction"

junction 是**全局状态**（同一盘符只有一份），`--concurrency > 1` 时两个任务会互相抢。
虚拟盘是**每次运行一份**，天然并发安全。

### 4.5 与命令行重写的配合（这里踩了一个真坑）

有了虚拟盘之后，`_rewrite_paths` 必须把 `/home/ubuntu` 换成
**虚拟盘上的绝对路径**（`X:\home\ubuntu`），**不能**继续换成工作区的真实路径
（`D:\...\home\ubuntu`）。原因：

> cmd 的 `cd D:\x` **不会切换盘符**（要 `cd /d`）。子进程当前盘是 `X:` 时，
> `cd D:\...\docs && mv a.txt a.md` 里的 `mv` 仍跑在原目录。

实测症状：`bench validate` 里 `syn_rename_files` 的参考解挂掉，
报 `mv: cannot stat 'a.txt': No such file or directory` —— **看起来像任务坏了**。

## 五、修复 ③：确定性 PATH + 环境指纹

### 5.1 问题：Agent 看到的世界取决于评测是怎么被启动的

实测同一段探测命令、同一台机器：

| 启动方式 | 解析到的工具 |
|---|---|
| 从 **Git Bash** | `python python3 sqlite3 which grep od tr cmp uname sed awk` **全在** |
| 从 **PowerShell** | **全部不在**（连 `python` 都不在） |

原因：Git for Windows 只在 Git Bash 里把 `usr\bin` / `mingw64\bin` 加进 PATH；
在 cmd / PowerShell 里只加 `Git\cmd`。而 `sqlite3` / `grep` / `od` / `tr` / `cmp` /
`uname` / `which` 全在 `usr\bin` 里。

**这是测量缺陷，不是“环境差异”**：同一个任务、同一份代码，
换个 shell 启动就换了一套可用工具 —— 模型会花迭代去探环境
（轨迹里 `which` / `command -v` 共出现 **110 次**），而任务难度本身变了。
自变量被污染了：你以为在比“两份代码”，实际还夹着“两个启动上下文”。

### 5.2 做法

1. **固定前缀**：Git 的两个 bin + 系统目录（顺序固定）；
2. **父 PATH 兜底**：接在后面 —— 不“拿走”任务已经在用的东西
   （`bc` 只在用户 PATH 里，而 `syn_sum_range` 的冒烟测试用过 `bc`）；
3. **解释器救急**：宿主解释器目录放在**最后**（父 PATH 里一个 python 都没有时至少能跑，
   而放前面会让 `python` 与 `python3` 指向不同版本）；
4. **记录残余**：只在父 PATH 里的工具仍随启动上下文变化，所以产出**环境指纹**。

### 5.3 🔴 实现里最关键的一个坑：发现过程本身依赖了要修的那个变量

第一版用 `shutil.which("git")` 找 Git —— 而它读的正是**父 PATH**。
于是父 PATH 一退化（就是我们要修的那个场景），“保证目录”变成**空集**，
修复**在最需要它的地方失效**，而**所有测试都绿**（测试进程自己拿着完好的 PATH）。

拦住它的是端到端探测（而不是单测）：把父进程 `PATH` 换成只有系统目录后，
探测命令仍然一个工具都找不到。

修法：第一来源改成**与 PATH 无关**的注册表
（`HKLM\SOFTWARE\GitForWindows` 的 `InstallPath`），再看标准安装位置，最后才看父 PATH。
对应的测试也改了：**先破坏 `os.environ["PATH"]` 再验证发现** ——
否则它永远抓不到这个错。

### 5.4 环境指纹：把“这次跑的时候看到了什么”变成数据

- `python -m lab sandbox env` —— 人类可读（哪些工具不可用、缺了会怎样）；
- `--json` / `Sandbox.env_fingerprint()` —— 机器可读；
- **落库到 `bench_suites.env_digest` + `env_fingerprint`**（旧库自动 ALTER 迁移），
  `env_digest` 用来 GROUP BY（“这几组是不是同一个环境”），完整 JSON 用来解释；
- 报告头部固定一行环境指纹 —— 每个数字从此带环境说明。

### 5.5 顺手发现的一个保真地雷

指纹第一次跑出来就报了一个问题：`sort` / `find` 解析到了
`C:\Windows\System32` 下的 **Windows 版** —— 那里的 `find` 是**文本搜索**，
不是目录遍历（`find /home/ubuntu -name "*.txt"` 语义完全不同），
`sort` 的选项也不同（`-k` / `-n` / `-r` 行为不一样）。

根因是 Git 有**两种**可执行文件布局（`<root>\cmd\git.exe` 退 2 级、
`<root>\mingw64\bin\git.exe` 退 3 级），而我第一版只试了一种。
**这就是“把环境变成可查数据”的直接收益：看不见的偏差变成了看得见的一行。**

## 六、我在实现里踩的坑（这部分比结论更有用）

### 5.1 盘符是**进程外资源**，而"调用方会释放"这个假设不成立

第一版实现是"随用随取 + `destroy()` 时释放"。一次 pytest 就把 **22 个候选盘符全用光了** ——
因为本仓库自己的测试里 **18 处构造 `LocalSandbox`、0 处 `destroy()`**。
后果不是报错，而是**静默退化**：后续运行拿不到盘符，逃逸又回来了，没人会发现。

这暴露的是设计错误而不是实现错误：**稀缺的进程外资源，不能依赖调用方自觉释放**。

### 5.2 修法：池 + 弱引用 + 属主存活检查

| 机制 | 解决什么 |
|---|---|
| 进程级池 + `atexit` | 正常退出一定释放 |
| **池里存弱引用** | 精确区分"在用"与"对象已被丢弃" —— 只记盘符的话，被丢弃的沙箱永远回收不了 |
| 属主登记（pid 写进系统临时目录） | 跨进程判断：**绝不抢活着的别的进程的盘符**（抢了会把它的产物写进我们的工作区，且极难归因） |
| 回收条件 | 目标目录不存在 / 无属主登记 / 属主是本进程但弱引用已死 / 属主是别的进程且已死 |

登记文件刻意放在**系统临时目录**而不是工作区：工作区里每个文件模型都可能看到，
一个莫名的 `.lab-drive` 文件本身就是新的失真源。

### 5.3 连带修掉的一处测试卫生问题

`test_local_sandbox.py` 的 `sandbox` fixture 原来**不释放沙箱** ——
资源泄漏的根源就在测试自己身上。已加上释放，并新增 5 个用例把两个修复钉住
（含一条**反向**保护：二进制文件绝不能被归一）。
