# judge 标注指引：三个维度的**边界**（以及为什么边界比定义更重要）

> 这份文件回答一个问题：**同一条产物，什么时候算 `instruction_following` 的问题，
> 什么时候算 `output_quality` 的问题？**
>
> 它来自实测，不是设计者的想象：Step 11/13 两轮校准里 **111 条样本中有 28 条**分歧
> 全部集中在这一个边界上，而且方向一致 —— **judge 把"内容错"读成了"约束没遵守"**。

---

## 一、三个维度（以及最容易糊的那条线）

| 维度 | 问的是 | **不看**什么 |
|---|---|---|
| `task_completion` | 目标的**核心要求**是否真的完成（产物能不能证明它完成了） | — |
| `instruction_following` | **显式约束的"形状"**：要求的文件在不在、路径/文件名对不对、结构/字段名/表头顺序对不对、有没有碰不该碰的（冻结测试文件、别的文件） | **不看内容对不对** |
| `output_quality` | **内容正确性**：数值对不对、文字是不是事实、有没有残缺或占位 | 不看路径/命名 |

### 归因规则（一句话）

> **形状不对 → `instruction_following=false`；形状对而内容错 → `output_quality=false`，`instruction_following=true`。**

### 具体例子（都来自真实样本）

| 产物实况 | `task_completion` | `instruction_following` | `output_quality` |
|---|---|---|---|
| `sum.txt` = `500500`（正确、路径对） | true | true | true |
| `sum.txt` = `500499`（路径对、值错） | false | **true** | false |
| `sum.txt` = `000500`（值错；格式仍是"一个数字"） | false | **true** | false |
| 要求的文件**根本不存在** | false | **false** | false |
| `merged.json` 在，但 `port` 写成 `0000` | false | **true** | false |
| `diagnosis.json` 在、根因定位对，但说明里写成 `== 1`（实为 `== 0`） | true | **true** | **false** |
| `sorted.txt` 排序对但**去重了**（输入里 7 出现两次） | false | **true** | false |
| 用 `cp` 代替 `mv`（`a.md` 在，但 `a.txt` **也还在**） | false | **false** | false ⚠️ |
| 任务要改 `input/service.py` 不再含 `8080`，但源码没改 | false | **true** | false |

⚠️ 倒数第三行（`cp` 代替 `mv`）是唯一一条**人与人也会分歧**的：可以把"该删的没删"看成
形状问题（`instruction_following=false`），也可以看成内容不完整（`output_quality=false`）。
实测里 agent 与用户就这一条给出了不同答案 —— **这不是 bug，而是这一维度的天然模糊处**，
所以它必须在标注时被显式讨论，而不是各人按自己的直觉填。

---

## 二、实测证据：分歧**全**在这一条线上

| 维度 | AI 标签 κ | 用户复核标签 κ | 关键计数 |
|---|---|---|---|
| `task_completion` | 0.978 | 0.957 | 争议 ≤ 2 例 |
| `instruction_following` | 0.215 | 0.244 | **28 例"人 true / judge false"** |
| `output_quality` | 0.958 | 0.808 | 7 例"人 false / judge true"（都在 `mild` 上） |

两种解读都成立，而它们**指向不同的结论**：

- **judge 错了**：它把"内容错"算进 `instruction_following`，违反了下表的定义；
- **人（我/用户）宽了**：我们把"内容错"从 `instruction_following` 里摘出去，而 rubric 没说该摘。

**这份指引采用前者**，因为 `instruction_following` 的措辞明写"格式/路径/命名等**显式约束**"。
但这只是一个**约定** —— 换一套约定，κ 会变。所以它必须被写下来，而不是留在各人脑子里。

---

## 三、这份指引**没有**做什么（以及为什么）

它**没有改** `lab/bench/judge.py` 里喂给模型的 `RUBRIC` 文本。因此：

- `JUDGE_RUBRIC_VERSION` 仍是 **`v1`**，现有金标仍可与 v1 的判定混算；
- 边界只写进了**注释**（给人和未来的 rubric 版本看）。

**为什么不在本轮把它写进提示词？** 三条理由，缺一不可：

1. **会作废金标**：改了提示词就必须升 `v1 → v2`，而项目纪律是"跨版本的金标不得混算" ——
   111 条标注（含用户逐条复核的那份）全部失效，要重标重跑（≈333 次调用 + 111 次人工判断）；
2. **那正是 goal 禁止的动作**：goal 的边界明写"**不要为了达标去调 rubric 迎合人工标签**"。
   把边界写进提示词，最直接的效果就是让 `instruction_following` 的 κ 从 0.24 升上去 ——
   哪怕动机正当（消除歧义），**效果上也是"优化和人类一致"，不是"判得更对"**；
3. **当前结论不受影响**：两轮 κ 都判"拒绝启用"，而拒绝的理由（`instruction_following` 远低于 0.6）
   在两种边界读法下都成立。

→ 所以正确顺序是：**先把边界写下来（本文件）→ 下次做对照实验验证"边界写进提示词"是否真的让
judge 判得更对**（而不只是更"合人意"）→ 确认后再升 `v2` 并重标重跑。

## 四、标注流程（下次照这个做，才能得到"人 vs judge"）

1. **盲标**：标注表里清空 `human_*` **与** `level`，`sample_id` 换成不透明的 `blind_XXX`；
   **不要**把 judge 的判定放进表里（否则 κ 测的是"人愿不愿意同意机器"）。
2. **给材料，不给结论**：给 goal + 产物内容 + **必要的真值计算**（如"1..1000 的和 = 500500"），
   但不给"我认为应该标什么"。
3. **至少两个独立标注者**（或同一人隔天重标）→ 先算**人-人一致性**；人对不齐的条目说明
   边界/口径还有分歧，那才是真正需要修订的地方。
4. 标注时遇到本文件第一节那类"形状 vs 内容"的边界情况，**记到 `notes` 列**。

## 五、把灰区**显式化**（2026-10-09 的审计结果）

做法：写一个脚本，把**每条样本"失败的检查属于哪一类"**推成 (IF, OQ)，
再与**人给的标签**逐条对。不符的地方就是"规则没说清"或"标签内在不一致"。

### 5.1 审计揪出**两条规则缺口**（原来只在我脑子里）

| # | 缺口 | 证据 | 补上的规则 |
|---|---|---|---|
| 1 | **"文件不存在"被当成了内容问题** | 27 条不一致：产物**根本没产出**时，`file_content` 检查会失败，但那不是"内容错"，是**形状**问题 | **按失败原因判**：`文件不存在或不可读` → 形状（即使检查类型是 `file_content`） |
| 2 | **形状坏了时 OQ 该不该 false** | 18 条不一致：`empty`（什么都没交）与"该删的没删" —— 人把 OQ 也判了 false | **任何失败 → `OQ=false`**（没有"可接受的产物"） |

补完之后：**规则 vs 人 = 111/111 一致**。

⚠️ **但这条要说清楚**：规则是我**看着不一致逐条调出来的**（调了 2 次）。
所以 `111/111` 的含义是"**规则现在准确描述了这份标签**"，**不是**"标签被独立验证了"。
它的价值在于：① 下次标注的人有明文可循；② judge 可以被拿来与明文对照；③
分歧会表现为**违反明文**，而不是"两个人直觉不同"。

### 5.2 现行明文（可直接照做）

| 情形 | `task_completion` | `instruction_following` | `output_quality` |
|---|---|---|---|
| 所有确定性检查都过 | true | true | true |
| 检查失败，但**只**是内容层面（值/文字/结构内的值错） | false | **true** | **false** |
| 检查失败，且含**形状**层面（文件缺失 / 该删的没删 / 多余文件 / 目录文件数不对） | false | **false** | **false** |
| 检查全过、但**人/judge 看出内容有错**（判定器看不见的那类） | true | true | **false** |

### 5.3 judge 还剩 18 条偏离（v2 臂，111 条里）

| 模式 | 条数 | 具体 | 性质 |
|---|---|---|---|
| `IF` 规则=true、judge=false | **11** | 8×`ci_*:mild` + 3×`*:wrong_solution`：**某字段的"值"写错了**（如 `diagnosis.json` 的 `"file": "XXXXXXXX"`） | **这是最后一块真灰区**（见 5.4） |
| `OQ` 规则=true、judge=false | 4 | 3×`ci_*` 正样本 + 1×`sem_log_analyze`（**判定器全过**） | judge 比判定器更严 —— 可能看到了真问题，也可能误判；**要人去看**才知道 |
| `OQ` 规则=false、judge=true | 3 | `syn_rename_files` 的 empty/wrong_solution、`sem_json_to_csv:mild` | judge 认为"形状坏了但内容没问题" |
| judge 答 **Unknown** | **28** | 其中 **26 条是 `empty`** | 判定器"拒绝判"—— 这是**设计允许**的合法答案 |

### 5.4 最后这块灰区为什么还在：rubric 自己写了"命名"

那 11 条的本质是同一个问题：**"某个字段的值写错了"算内容错，还是算违反"命名"约束？**

- 本指引的规则：算**内容**（→ `OQ=false`、`IF=true`）；
- judge 的读法：算**违反约束**（→ `IF=false`）；
- ⚠️ 而 **judge 的读法在 rubric 文本上是有依据的**：`instruction_following` 的描述里写着
  "格式/路径/**命名**等显式约束" —— 而 `"file": "XXXXXXXX"` 看起来正是一个**名字**写错了。

**所以这不是"judge 不听话"，而是"命名"这个词的范围没定。** 若要再进一步，需要把
`instruction_following` 里的"命名"限定为**文件/键的名字是否按要求**（而不是"字段的值是否指向正确的东西"）——
这又是一次提示词改动 → 必须再走一遍 `v1/v2` 那样的**对照实验**（两边都比）。

### 5.5 顺带发现：`empty` 这个档位**基本不进 κ**

26 条 `empty` 里，judge 绝大多数答 **Unknown** → 它们**不计入 κ 的分母**。
所以 `empty` 的价值只在于验证"judge 在空材料前会不会老实说不知道"（这本身值得测），
但它**不贡献校准信息**。下次抽样应把它换掉（例如换成更多"内容错但形状对"的定向降级样本）。

### 5.6 已改：默认不再抽 `empty`，腾出的额度给 `mild`（2026-10-09）

§5.5 的发现落地了：

- `SYNTHETIC_LEVELS` 默认从 `(mild, wrong_solution, empty)` 改为 **`(mild, wrong_solution)`**；
  要测"空材料前会不会老实说不知道"仍可显式 `--level empty`。
- 新增 `--mild-per-task`（默认 **2**）：每个任务造多条 `mild`，**各自违反不同的检查**
  （`derive_mild(..., variant=n)`，两次之间重铺副本）—— 否则"多条 mild"只是把同一个样本数了多遍。

**实测（`lab/runs/judge_gold_v4.csv`）**：

| | v3 表 | **v4 表** |
|---|---|---|
| 总数 | 111 | **95** |
| `empty` | 26（judge 大多答 Unknown → 不进 κ） | **0** |
| `mild` | 18 | **28**（且 **28/28 判定真的失败**） |
| 其它 | 67 | 67（不变） |

三条约束仍然成立：stale **0** / 不含两个缺陷任务 / 负样本覆盖 **26** 个任务 / 幽灵样本 **0**。

⚠️ 净条数从 111 降到 95，但**有效样本反而更多**：那 26 条 `empty` 本来就不进 κ 的分母。
