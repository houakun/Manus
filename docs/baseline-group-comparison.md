# 分组对比：synthetic vs semireal（n=60 / n=40）

> 数据来源
> - **synthetic**：suite `4cc51bc2`（12 任务 × 5 次 = 60 次运行，$4.61，耗时 36.4 分钟）
>   判定结论经**修正任务期望值后重新判定**（见第三节）
> - **semireal**：suite `70a79a26`（8 任务 × 5 次 = 40 次运行，$5.21，耗时 38.8 分钟）
> 模型 `deepseek-reasoner`、温度 `0.0`、并发 `1`、预算模式 `observe`

---

## 一、对比结果

| 指标 | synthetic (n=60) | semireal (n=40) | 倍数 | 区间重叠？ |
|---|---|---|---|---|
| **成功率** | **100.0%** [94.0%, 100%] | **95.0%** [83.5%, 98.6%] | — | ✅ 重叠 → **不显著** |
| tokens/任务 | 123,989 ± 14,003<br>[109,986, 137,991] | 210,350 ± 58,127<br>[152,224, 268,477] | **1.70×** | ❌ 不重叠 → 显著 |

## 二、三条结论

### 2.1 "玩具任务刷分、真实任务崩掉" —— **不成立**

成功率 100% vs 95%，**Wilson 区间大幅重叠**（[94%,100%] 与 [83.5%,98.6%]）。
在这个样本量下**不能说半真实任务更难**。

这一点必须如实说：如果只报"100% vs 95%"而不给区间，
读者很容易得出"SUT 在真实任务上退化"的结论 —— 而数据显示的是**两者都很高，差异落在噪声里**。

> 想真的判断"难度是否有差异"，需要更大的 n（或换成按任务配对的比较：
> 同一任务在两组里各跑一次，差值才排除任务难度的影响）。

### 2.2 成本差异是**显著**的：半真实任务贵 1.7×、多 1.33× 工具调用

token 与工具调用的区间不重叠 → 这个差异可以下结论。
耗时是边缘（41.8 vs 41.2，刚好不重叠），不宜强断言。

### 2.3 🔴 最重要的差异不是均值，而是**方差**

| | 相对区间宽度 | max/均值 |
|---|---|---|
| synthetic | ±11% | 2.2× |
| semireal | **±28%** | **4.5×** |

半真实任务的成本分布有**很重的长尾**（最贵一次 953k = 均值的 4.5 倍）。

**这直接解释了 D 基线里 60% 的 token 越界率**：
按"均值 + 一点余量"设的预算阈值，在半真实任务上会被长尾频繁击穿。
**阈值必须按分位数（P95/P99）而不是按均值设** —— 这是本次对比给出的最可操作的结论。

## 三、过程中的三次自纠（都比数字本身重要）

### 3.1 🔴 任务集有 2 个任务的期望值**本身就是错的**

| 任务 | 我写的期望 | 正确答案 | 后果 |
|---|---|---|---|
| `syn_string_reverse` | `TNEGA SUNUM` | **`TNEGA SUNAM`** | 0/5，Agent 算对却被判错 |
| `syn_word_freq` | `the:3, brown:2, dog:2` | **`the:4, dog:3, brown:2`** | 0/5，同上 |

**10 次"失败"全部是任务集的错，Agent 每次都写对了。**
修正后重新判定：**synthetic 从 83.3% → 100%**。

**为什么自检没发现**：三步自检（空工作区失败 / 参考解通过 / 错误解失败）里，
**参考解就是"把期望值写进文件"** —— 它怎么可能发现期望值是错的？
自检验证的只是"判定器能不能读回自己刚写的东西"。

这正是"任务集本身也要被验证"那句话的边界：
**我的自检能验证判定器与错误的偏离，但验证不了期望值的正确性。**

### 3.2 新增防护：同义反复检测（tautology detector）

`lab bench validate` 现在会自动检测"参考解直接写出了期望值"并告警。

首次运行结果：**20 个任务里 17 个是同义反复（85%）** ——
也就是说 85% 的任务集**没有能力发现自己的期望值写错**，而其中 2 个真的写错了。

已把 9 个最可能出算术/排序错误的任务的参考解改成**真的算一遍**
（写一个 `_solve.py` 再用 `python _solve.py` 跑），
这样期望值写错时参考解对不上、自检会直接失败。

**目前仍有 8 个任务带同义反复告警**（数据转换类，期望值已人工核对过），
它们是**已知的验证强度弱点**，会一直显示在自检输出里，不再被隐藏。

### 3.3 🔴 发现 fast mode 的沙箱可以被**脚本逃逸**（安全 + 正确性）

排查参考解为什么跑不通时发现：`exec` 返回 rc=0 但产物没生成。

原因：**沙箱的路径映射只作用于两处 —— 文件工具、命令行字符串；
脚本内容它管不到。** 脚本里写 `"/home/ubuntu/x"` 会被 Python 解析成
`<当前盘>:/home/ubuntu/x`，直接写到工作区外面。

实测确认这不是假设：

```
D:\home\ubuntu\   ← 存在
├── config.json      （sem_refactor_config 的产物）
├── days.txt / fizzbuzz.txt
└── parts/part_000 … part_006   （来自一次真实的 sem_refactor_config 运行）
```

**双重危害**：
1. **正确性**：产物落在工作区外 → 判定器读不到 → 正确的工作被判失败；
2. **安全**：fast mode 的"沙箱"**可以被任意脚本逃出** ——
   它只能用于**可信的任务与内容**，绝不能跑外部输入。

已做的处理：
- 参考解改用**相对路径**（exec 的 cwd 已经是映射后的 `/home/ubuntu`）；
- `LocalSandbox` 新增**逃逸检测**：每次命令执行后检查工作区外那个位置是否存在，
  存在就告警并写进 `ToolResult.data["escaped_paths"]`，让"产物找不到"能一眼归因，
  而不是让人去怀疑判定器或模型能力；
- 明确记录为**已知限制**：真要把绝对路径导向工作区需要盘根目录级别的 junction，
  那是全局状态、并行任务会互相干扰，代价大于收益。

> `D:\home\ubuntu` 的残留文件我没有擅自删除（在工作区之外）。
> 如果需要清理，一条命令即可；保留它的代价是：未来某次脚本逃逸会"看起来成功"，
> 但新的逃逸检测会在 trace 里告警。

## 四、已知限制（请连同数字一起读）

| 限制 | 影响 |
|---|---|
| **两组 SUT 版本不同** | semireal 跑在 D10 修复**前**，synthetic 在修复**后**。修复只影响"格式错误崩溃"这条路径（semireal 里 2/40），对均值影响很小，但严格来说不是同版本对比 |
| **8 个任务仍是同义反复验证** | 它们的期望值只经人工核对，未经独立计算 |
| 判定器不评价过程质量 | 过程分只有 flag（见报告第六节） |
| 无 LLM judge | 开放式任务无法评（handoff 决策 2：先建确定性基线） |
| 并发 1 | 耗时可比，但代价是 36~39 分钟/组 |
| 成本 | 本次两组基线共花费 **$9.82**（$4.61 + $5.21），累计（含调试）约 $12 |

## 五、下一步建议（按投入产出比）

1. **阈值改按分位数设**（P95/P99），而不是按均值 —— 2.3 节的数据直接支持这一点；
2. **把剩下 8 个任务的参考解也改成"真的算一遍"** —— 机械工作，但能把验证强度补满；
3. **semireal 用修复后的 SUT 重跑一次**（$5.21）—— 才能得到同版本的分组对比；
4. 修 SUT 里"原地打转"的问题（Step 4 发现：953k token / 51 次工具调用那两次），
   用上下文压缩 + 纠偏提示，**而不是熔断**；
5. Step 5：加固前后对比 + Pareto 曲线（需要先有同版本的 baseline）。
