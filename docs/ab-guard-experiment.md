# 加固对照实验（2×2）：一个负结果，以及它为什么比假的正结果有价值

> 对应 `docs/step6-gap-audit.md` §3.2：补上「加固前后成功率曲线」。
> 前置改造（guard 开关）已在 `docs/step6-gap-closure.md` 完成。
> 本次实验实测花费 **$19.55**（原估 $8.3，见 §6）。

---

## 一、实验设计（以及为什么原设计会白花钱）

| 格 | 故障 | 加固 | 说明 |
|---|---|---|---|
| **A** | 无 | `none` | 基线 |
| **B** | 无 | `all` | sanity：加固不伤正常路径（**$0，复用已有 v3 基线 n=40**） |
| **C** | `partial_write@0.5` | `none` | 加固前 |
| **D** | `partial_write@0.5` | `retry+postcondition+enforce` | 加固后 ← 要的那条曲线 |

**动手前发现原设计有两个致命缺陷，已修正**：

| 原设计 | 后果 | 修正 |
|---|---|---|
| 故障率 `rate=1.0`（每次 `write_file` 都截断） | 故障**不可战胜** → 两格都是 0%，曲线是平的 | 改成 `0.5` |
| 后置校验**只记录告警、不改 ToolResult** | 模型看不到问题 → 加固**物理上不可能**改变成败 | 新增 `enforce`：校验失败 → `success=False` + 告警文本回灌 |

第二条是**真的自愈链断了**（检测了却没有回灌）。补上它本身就是"自愈"能力的闭环，
而不只是为了实验方便。

## 二、结果

| 格 | 成功率 | 95% Wilson | pass^3 | token 中位 | 成本 | **成本/成功** |
|---|---|---|---|---|---|---|
| **A** 无故障×无加固 | **24/24 = 100%** | [86%, 100%] | 8/8 | 147,845 | $3.36 | $0.1400 |
| **B** 无故障×加固（复用） | 40/40 = 100% | [91%, 100%] | 8/8 | — | — | — |
| **C** 静默故障×**无**加固 | **23/24 = 95.8%** | [80%, 99%] | 7/8 | 359,360 | $7.01 | $0.3048 |
| **D** 静默故障×**加固** | **21/24 = 87.5%** | [69%, 96%] | 7/8 | 391,330 | $9.18 | **$0.4373** |

**A vs B（sanity）**：两侧都是 100% → ✅ **加固不影响正常路径**（这格是免费的，但必须做）。

**C vs D（要的曲线）**：**加固那格反而更差**（-8.3pt），而且：

| 指标 | C → D 配对差值 | bootstrap 95% 区间 | 可信? |
|---|---|---|---|
| tokens/任务 | +162,095（+33.3%） | [-122,436, +467,235] | ❌ 跨 0 |
| 成本/任务 | +31.0% | 跨 0 | ❌ |
| 工具调用/任务 | +2.3（+8.1%） | [-5.6, +9.8] | ❌ 跨 0 |
| 成功率 | -8.3pt | 区间重叠 | ❌ |

**所有差异都不显著**，但方向一致（6/8 个任务在 D 上更贵）。

## 三、机制：为什么加固没用，以及为什么在这个任务集上必然没用

### 3.1 🔴 Agent 自己会验证并恢复 —— 后置校验在写路径上天然冗余

C 格有 **17 次运行真的被注入了故障**，但**没有一次导致任务失败**：
Agent 写完文件后会**读回验证**，发现内容不对就重写。

代价是真实的（但它记在"故障"头上，不是"加固"头上）：

| | A（无故障） | C（有故障） | 变化 |
|---|---|---|---|
| token 均值 | 228,909 | **487,361** | **+113%** |
| 成本 | $3.36 | **$7.01** | **+109%** |
| 工具调用均值 | 18.6 | **28.8** | +55% |

> **故障注入确实有效**（成本翻倍证明 Agent 在做额外的工作），
> 但**它没能突破 Agent 自身的恢复能力**。所以 guard 的"恢复"价值没有可发挥的空间。

### 3.2 所有 4 次失败都在**同一个任务**上，且都不是故障导致的

| 格 | 任务 | 故障次数 | 后置告警 | 实际产物 | 问题 |
|---|---|---|---|---|---|
| C | `sem_markdown_toc` run2 | **0** | 0 | `- ## 安装` | 留下了 `##` 标记 |
| D | `sem_markdown_toc` run0 | 1 | 1 | `- 安装`（漏 H1） | 漏了一级标题 |
| D | `sem_markdown_toc` run1 | 2 | 2 | `- 安装`（漏 H1） | 同上 |
| D | `sem_markdown_toc` run2 | 2 | 2 | `-   安装` | 缩进错 |

其余 **7 个任务在三格里全是 3/3**。

**所以 8.3pt 的"加固变差"完全由这一个任务的 3 次运行决定** ——
而它恰恰是本项目里**已知最不稳定的任务**（规格脆：要保留 H1、去掉 `#`、缩进精确到 2/4 空格）。

### 3.3 🔴 `enforce` 的副作用：把"静默错"换成"可见错 + 更多尝试"

D 格三次失败**都触发了后置告警**（说明 enforce 确实把截断暴露给了模型），
模型于是**重写** —— 而每次重写都是一次**新的出错机会**，在这个脆弱的任务上就变成了新的错误。

> 这是一条重要的机制结论：**`enforce` 的价值取决于"恢复路径是否可靠"**。
> 恢复路径可靠 → 它把静默失败变成可修复失败（收益）；
> 恢复路径脆弱（如本任务的规格）→ 它只是增加了尝试次数，反而放大出错面。
> 只报"告警次数上升"是不够的 —— **必须同时看最终产物的合格率**。

### 3.4 检测层是好的，只是收益没兑现

D 格触发 **95 条后置校验告警**（C 格 0 条，因为校验被关掉了）。
**检测机制工作正常**；不成立的是"检测 → 恢复"这一步的净收益。

## 四、这个负结果为什么比假的正结果有价值

如果我在原设计（rate=1.0）下硬跑，会得到两列 0%，然后很可能去调参、换故障，
最终**凑出一条看起来漂亮的曲线** —— 而那会是彻头彻尾的假象。

现在拿到的是一条**可解释的负结果**：

| 结论 | 依据 |
|---|---|
| 加固中间件的**机制**是好的（开关生效、校验触发 95 次、sanity 格 100%） | §2、§3.4 |
| 加固在**这个任务集 + 这个故障**下**没有净收益** | §2（-8.3pt，不显著） |
| 原因是**Agent 自身的验证能力已经覆盖了这个故障** | §3.1 |
| 且任务集里有一个**不稳定任务**淹没了小效应 | §3.2 |
| **故障注入本身**的价值是确凿的（成本 +109%） | §3.1 |

**这正是这个项目一直在讲的方法论**：先验证前提（原设计会白花钱 → 改了），
再测；测出来是负的就报负的，并解释清楚为什么。

## 五、什么条件下才能测出"加固曲线"（修正后的建议）

三条硬条件，缺一条曲线就不存在：

| 条件 | 当前的缺口 | 怎么补 |
|---|---|---|
| 故障必须**Agent 自身无法发现** | 写路径上 Agent 会读回验证 → 必然冗余 | 换成**读路径**的静默故障（`truncated_result` / `silent_wrong_result`），并在 guard 里加**内容级**校验（现在的读校验只查字段存在，太弱） |
| guard 必须提供 **Agent 没有的恢复手段** | 写截断 Agent 自己能恢复 | 例如：对读结果做**交叉校验**（同一信息两个来源比对），Agent 提示词里没有这个动作 |
| 任务必须是**稳定的**（否则淹没小效应） | `sem_markdown_toc` ~70% 稳定 | 加 `purpose: capability\|regression` 标记（审计 §4.9）；把不稳定任务从 A/B 里移出或先修规格 |

并且：**`enforce` 只应在"恢复路径可靠"的任务上开** —— 见 §3.3。

## 六、成本教训（很重要）

| | 预估 | 实际 | 偏差 |
|---|---|---|---|
| 实验总花费 | $8.3 | **$19.55** | **2.4×** |

原因：故障格的单次成本是基线的 **2~3 倍**（Agent 因产物被截断而反复重试）：

| 格 | 单次成本 |
|---|---|
| A（无故障） | $0.140 |
| C（故障，无加固） | $0.292 |
| D（故障，加固） | $0.383 |

**已修**：CLI 的成本预估现在会区分"带故障 / 无故障"的历史均值：

```
带故障：预估 $10.33（依据：库中同组历史均值（semireal，带故障注入），单次 ≈ $0.431）
无故障：预估 $2.73 （依据：库中同组历史均值（semireal，无故障），单次 ≈ $0.114）
```

差 3.8 倍 —— 用无故障均值去估故障实验会低估一半以上。

## 七、顺手修掉的两个"指标污染"bug

### 7.1 🔴 工具调用次数依赖了可被关掉的能力

`RunOutcome.tool_calls` 原来从 `loop_guard` 取，而 `loop_guard` 会被 `--guard none` 关掉
→ **对照组全部显示 `tools=0`**，看起来像"Agent 没调工具"。
更糟的是：`bench compare` 因此报出完全虚假的"+31 次工具调用"。

→ 改成从**事件流**（`tasks.tool_sequence`）算；`load_suite` 也改成联表取该字段
（历史数据一并修正）。修正后 C→D 的工具调用差异是 +8.1%（而非 +31 次）。

> **原则：指标不能依赖可以被开关关掉的能力。** 否则"对照组"本身就被开关污染了。

### 7.2 子命令缺参数声明（同类 bug 第二次）

`bench run` 引用了 `args.fault_latency`，但 `--fault-latency` 只声明在顶层 `run` 上
→ 只有真跑到那条分支才炸（和之前漏 `ensure_runs_dir` 一个类型）。
已补参数，并加了一条**把子命令所有参数都传一遍**的解析测试兜住。

另外 `fault_rules` 现在会被**打印出来** —— 这次我脚本忘了传 `--label`，
日志里连"哪一格是什么配置"都看不出来，只能靠事后查库补救。

## 八、下一步

1. **先修任务集**：`sem_markdown_toc` 的规格（它已经污染过两次实验）+ 加
   `purpose: capability|regression` 标记；
2. **把 guard 的检测面做到读路径**（内容级校验），这样"Agent 无法自证"的故障才存在；
3. 用**读路径静默故障**重做一次 2×2（这是唯一可能出曲线的组合）；
4. 或接受这个负结果，把精力放到审计 §3.1/§3.3 已完成的部分（`pass^k` + CI + gate），
   以及 §4 里性价比更高的项（噪声地板、加任务数）。
