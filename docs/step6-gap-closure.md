### 2.2 ⚠️ 报告里必须一起写的三条限制

审计把这描述为"把不显著变成真数字"。**这个说法需要修正**——实测：

| 口径 | v1 | v3 | 区间重叠？ |
|---|---|---|---|
| pass^k | 75% [41%, 93%] | 100% [68%, 100%] | ❌ **仍然重叠** |

`pass^k` 给的是**更诚实的口径**（把分析单位从 40 次运行换成 8 个任务，
于是"2 个任务不稳定"不再被平摊掉），**不是免费的统计功效**。
它的样本量是**任务数（8）**，想让区间收窄必须**加任务**，不是加重复次数。

所以报告里固定输出三条 caveat（由 `TaskLevelRates.caveats` 生成）：

1. 样本量是任务数 n=8，不是运行数；
2. `pass^k` 假设同一任务的 k 次试验独立 —— **并发运行会引入相关失败**，此时偏乐观；
3. `pass^k` 与运行级成功率的差异**不代表显著性**。

## 三、② guard 开关：对照实验的唯一硬前提

### 3.1 审计的诊断被证实

`ToolGuard` 的 `verify_postconditions` / `max_attempts` 是构造参数，
CLI / config / bench **都不可配** → 加固永远是开的 → **物理上做不出"无加固"对照组**。

### 3.2 实现

```bash
python -m lab bench run --runs 5 --group semireal --guard none --fault partial_write
python -m lab bench run --runs 5 --group semireal --guard all  --fault partial_write
```

| 能力 | 关掉它会怎样 |
|---|---|
| `retry` | 一次超时/抖动就直接失败 |
| `postconditions` | **静默失败会冒充成功**（写入只写了一半也判成功） |
| `loop_guard` / `budget` | **只影响观测**（observe 模式下本就不干预成败） |

> 这一点必须写清楚，否则会有人误以为"关掉 loop_guard 但成功率没变 = 它没用"。

**证据（测试而非推断）**：

| 用例 | guard=all | guard=none |
|---|---|---|
| 注入 `transient_error`（幂等工具） | `attempts=2`，**成功** | `attempts=1`，**失败** |
| 注入 `partial_write` | 写入只写了一半，**后置校验抓到告警** | 写入同样只写了一半，**没有任何人发现** |

同时 `RunOutcome.guard_config` 一路落库（新列 + ALTER 迁移），
`ToolGuard.report()["config"]` 进报告 —— **没有它两组数据无法区分是谁的**。

## 四、③ CI + 回归门禁 + README

### 4.1 `bench gate`：把对比结果变成退出码

```bash
python -m lab bench gate --baseline 70a79a26 --candidate 80caef04
```

| 门禁 | 阈值 | 实测 | 结论 |
|---|---|---|---|
| 运行级成功率下降 | ≤ 5.0pt | -5.0pt | ✅ 95.0% → 100.0% |
| pass^5 下降 | ≤ 10.0pt | -25.0pt | ✅ 6/8 → 8/8 |
| 成本上升 | ≤ 20%（需方向可信） | -22.0% | ✅ $0.1302 → $0.1016 |

反向（把 v3 当基准）三项全红、退出码 1 ✓。

**关键设计：默认 `require_significant=True`** ——
只有"差值方向可信（bootstrap 区间不跨 0）**且**超过阈值"才判失败。
理由：本项目实测**同一代码不同时段也能差 20%+**；
"只要数值变差就红"会让门禁因噪声频繁变红，而**频繁变红的门禁等于没有门禁**。

## 五、顺手发现并修掉的 3 个问题

### 5.1 🔴 `pass^k` 的静默类型错误（最值得记的一个）

初版 `task_level_rates(per_task: Sequence[Sequence[bool]])`，而调用方传了 `dict`。
Python **不报错**：迭代 dict 得到**键（字符串）**，于是
`map(bool, "semireal/sem_bug_fix")` 把 20 个字符变成 20 个 True →
输出 `k=20`、`uniform_k=False` —— **数字悄悄错了，没有任何异常**。

对比：这一步如果直接采信，报告里会出现 `pass^20 = 100%` 这种荒谬但不易察觉的数字。

→ 签名改成 `Mapping`，并在入口**显式 `isinstance` 检查**（附上这个事故的注释）。

> 根因不是打字错误，而是"类型不对但能跑"这类错误的隐蔽性：
> 崩溃会有人管，错数字没人管。所以关键函数要在入口校验类型。

### 5.2 `.venv-ci` 没被 `.gitignore` 覆盖

`.venv/` 匹配不到 `.venv-ci/` → 模拟 CI 用的临时虚拟环境会被 `git add .` 打包进去。
已改成 `.venv*/`（通配，防同类问题）。

### 5.3 `bench gate` 的默认行为

见 §4.1 —— 默认要求"方向可信"，否则 CI 会因噪声频繁变红。

只有后置校验能抓，正好对应 guard 最独特的能力（§3.2 的测试已经证明

> 提醒：**没有故障就没有加固的价值可测** —— SUT 在无故障任务集上已经是 95~100%，
> 所以"guard off vs on"在无故障条件下两列都会是 ~100%，曲线是平的。
