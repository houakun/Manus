## 二、🔴 阈值校准结论：**当前阈值对半真实任务系统性偏紧**

| 维度 | 你的软阈值 | 实测均值 | 软线越界率 | 硬线(×2.5) | 越硬线次数 |
|---|---|---|---|---|---|
| tokens | 150,000 | **210,350** | **60%** | 375,000 | **4** |
| 成本 | $0.10 | **$0.1302** | **55%** | $0.25 | 2 |
| 工具调用 | 15 | **19** | **68%** | 37.5 | 2 |
| 耗时 | 60 s | 58 s | 28% | 150 s | 3 |

**结论：现在切 `enforce` 会砍掉 55%~68% 的运行（软线越界率）；即使只看 2.5× 的硬线，也有 4~5 次会被砍掉，其中部分是成功的。**

阈值是按"简单任务"定的（你的 n=5 基线 token 均值 63k、成本 $0.039），
而半真实任务的均值是它的 **3.4 倍**。这说明：

1. **阈值不能全局统一** —— 至少需要按分组（synthetic / semireal）分别设；
2. 更彻底的做法是**按任务的历史分位数设**（例如"超过该任务历史 P95"才算越界），
   因为任务之间的成本差异本身就比任务内的方差大得多（见第四节）；
3. **好在硬上限（×2.5）设计是对的**：38 次里只有 4 次触到硬线 ——
   也就是说 enforce 不会大面积误杀，但它会误杀那 4 次（其中 2 次是**成功的**）。

### 3.1 SUT 缺陷：结构化输出没有兜底（同一个根因的第 3 次出现）

```
ValidationError: 1 validation error for Step
Input should be a valid dictionary or instance of Step
input_value=[{'name': 'monitor', 'price': 320}, ...]
```

LLM 在"最终结构化输出"的位置返回了一个**列表**（它把转换后的数据本身当答案交了），
SUT 直接执行 `Step.model_validate(parsed_obj)` → 崩溃。

这与 Step 1 修的 D5、Step 4 的"空计划虚报成功"是**同一个模式**：

| 编号 | 位置 | 触发条件 | 后果 |
|---|---|---|---|
| D5 | `planner_react.py:208` | Plan 为 `None` | AttributeError 崩溃 |
| D9 | 同上 | `plan.steps` 为空 | **虚报成功** |
| D10 | `react.py` | `Step.model_validate` 失败 | 崩溃（本次） |

**系统性结论**：提示词要求"必须返回严格 JSON"，但代码没有把"违反约定"当成**可预期情况**处理。
逐个打补丁是治标的；正确做法是在 `_json_parser` + `model_validate` 外面加**统一兜底**：
解析失败 → 把"格式错误 + 期望格式"回灌给 LLM 重试一次 → 仍失败才 yield `ErrorEvent`。
这也是投入产出比最高的一处加固。

### 3.2 我的任务缺陷：`sem_markdown_toc` 目标歧义（已修）

原描述"所有以 # 开头的标题（包括二三级标题）"**可以被合法地读成**"要提取的是二三级标题"，
而且缩进规则也只规定了二三级 → 有一次运行据此跳过了 H1，被判失败。

**这是假阳性（把任务缺陷当成能力缺陷）**，正是"任务集也要被验证"要防的东西。
已改为显式列举"一级二级三级都要 + 一级缩进 0 个空格"，并在任务里记录了这次修正。

## 四、🔴 核心发现：最贵的运行 = "绕了很多弯但最终做对了"

| 任务 | 运行 | tokens | 工具调用 | **动作多样性** | 4 项阈值 |
|---|---|---|---|---|---|
| `sem_refactor_config` | run1 | **953,151** | **48** | **0.25** | 全部越界 |
| `sem_sqlite_report` | run2 | **862,223** | **51** | **0.235** | 全部越界 |
| —— 平均 —— | | 210,350 | 19.0 | ~1.0 | |
| `sem_csv_clean` | run0 | 385,854 | 28 | 0.39 | 全部越界 |
| `sem_log_analyze` | run3 | 381,261 | 29 | 0.34 | 全部越界 |

**动作多样性 = 不同动作指纹数 / 总调用数。** 0.25 意味着 48 次调用里只有约 12 个不同动作
—— 每个动作平均重复了 4 次。这就是 Step 3 里"`max_consecutive_repeat` 抓不到、
`action_diversity` 抓得到"的那种**近似重复**（同工具、稍改参数的原地打转）。

三条由此得出的结论：

1. **浪费的根源不是工具失误，而是 Agent 自己的循环。**
   40 次运行只有 **1 条**后置校验告警 —— 工具没有说谎。
2. **最贵的运行全部是成功的。**
   953k token / 862k token 这两次，产物都是合格的。
3. **所以"熔断中止"是错误的干预手段。**
   如果按"工具调用 > N 就停"，这两次会从成功变成失败 ——
   失败率凭空上升 5%。正确的干预是：
   - **上下文压缩**（把重复动作的历史输出从记忆里压掉）→ 降低单次调用成本；
   - **纠偏提示**（"你已经重复了同一个操作 4 次，请换一种策略"）→ 让它自己跳出循环；
   - 熔断只作为**最后一道**保险（阈值设得远高于正常波动，例如 >100 次调用）。

## 五、SUT 自述 vs 独立判定：**两个方向都有偏差**

| 口径 | 成功数 | 成功率 |
|---|---|---|
| SUT 自述 `result.ok` | 35/40 | 87.5% |
| **独立判定（权威）** | **38/40** | **95.0%** |

- **1 次虚报成功**（自报成功但产物不合格）：危险方向，会抬高成功率；
- **4 次误报失败**（自报失败但产物合格，占 10%）：会**低估**成功率。

4 次误报失败的三个原因：汇总阶段 LLM 调用失败（网络）、干完后又去问用户、整任务超时。
**共同点：活已经干完了，只是"收尾"没做好。**

> 这直接回答了"该看什么来判定任务完成"：**看交付物，而不是看 Agent 有没有好好收尾。**
> 如果只看 `result.ok`，你会得到 87.5%；只看交付物是 95.0%。差 7.5 个百分点，
> 而且这 8 个点里全是"能干活但不会收尾"的样本 —— 它们恰恰是最值得保留的优化对象。

## 六、方法与可信度：**我在这份报告的第一版里判断错了**

这一节必须如实记录，因为它直接关系到"数字能不能信"。

### 6.1 一次误判（已纠正）

评测在 18:37 启动、跑了 **38.8 分钟**。我在中途轮询了几次，最后一次（约第 35 分钟）
看到日志停在 `sem_sqlite_report run3/5`、并且 `ps aux | grep` 查不到进程，
于是判定"进程被外部杀掉了、suite 没落库"，并据此：

1. 实现了增量落库（`on_start` / `on_outcome` / `on_finish`）；
2. 写了 `lab bench recover`，从工作区 + 轨迹**重建**了 38 次运行（suite `3ee99cef`）；
3. 在文档和代码注释里写下"实测教训：跑到第 38 次被杀、之前全丢"。

**实际上评测跑完了**：原始 suite `70a79a26` 有完整的 **40 次运行、38 次成功**，
耗时 2329.7s，40 个工作区齐全。`self_reported_ok` 也全部写入了。

**错在哪**：`ps aux` 在 Git Bash 下**看不到原生 Windows 进程**，
我用它做了一个"进程已死"的判定 —— 而它给出的 0 是假阴性。
（最后一次轮询时 `run3/5` 正在跑，`run4/5` 的日志还没打印，看起来就像"卡住了"。）

**已做的纠正**：
- 删除基于误判写下的代码注释与文档结论，改为**真实理由**：长评测被中断的途径很多
  （Ctrl-C、机器休眠、终端关闭、远程会话断开），增量落库让这些情况最多丢一次运行 ——
  这个设计本身是对的，但它**不是因为那次事故才需要**；
- 本文档的数字全部改用权威 suite `70a79a26`（40 次）；
- 删除了重建出来的 `3ee99cef`（它是权威数据的真子集，留着只会让记录混乱）。

**保留下来的东西**：
- 增量落库（正确的设计，且现在有测试）；
- `lab bench recover`（**仍然有价值**：真的被 Ctrl-C 打断时它就是救数据的唯一手段；
  它现在是"备而未用"的能力，不是事故的纪念品）；
- 修好的成本预估（那个问题是真的：预估 $1.80 / 实际 $5.21，低估 2.9 倍）。

### 6.2 这次误判的真正教训

比"要加增量落库"更有价值的教训是：**我用了一个自己没验证过的观测手段**。
`ps aux` 返回 0 时，我本可以再确认一步（例如看日志文件是否还在增长、
或用 `tasklist` 交叉验证），但我直接下了结论，并围绕错误结论写了一堆代码和文档。

这与本项目一直在讲的主题是同一件事：**观测通道本身必须被验证** ——
Step 1 的 D6（PYTHONHOME 污染子进程）、D8（孤儿进程污染耗时指标）、
这次的进程存活误判，本质都是"你以为你在看真相，其实你在看假象"。

### 6.3 判定强度的一次加固（这一条是真的）

`syn_rename_files` 原本只验"文件名变了"，不验"内容还在" ——
`rm a.txt && touch a.md` 也能通过。已加 2 条内容校验 + 1 条白名单校验，
并补了 3 个回归用例（含"正确做法必须通过"的反向用例）。

### 6.4 环境性失败

日志中有 5 次 `Connection error`（模型服务端网络抖动），**2/40 次运行受影响**，
其中 1 次导致 LLM 重试耗尽（但产物合格）。
目前只能靠 `error` 文本识别环境性失败，尚未做成结构化字段 —— 见第八节。

## 八、下一步建议（按投入产出比排序）

1. **修 SUT 的结构化输出兜底**（1 处统一处理，覆盖 3 个已发现的崩溃/虚报实例）
   → 预计直接消除 2/38 的异常（其中 1 次是产出失败）。
2. **阈值按分组重设 + 按任务历史分位数动态判定**
   → 现在是 61% 的越界率，切 enforce 等于随机砍任务。
3. **把"原地打转"的干预做成上下文压缩 + 纠偏提示，而不是熔断**
   → 目标是压掉 953k/862k 这类运行的成本，而不是把它们判失败。
4. **网络类失败结构化区分**（`env_error` 字段），并从成功率分母里剔除后再单独报告
   → 避免把网络抖动算成 Agent 能力问题。
5. 继续跑 synthetic（8 任务 × 5 次 ≈ **$1.3**，因为 synthetic 便宜得多），
   拿到分组对比后才能回答"这套系统在玩具任务上刷分、在真实任务上崩掉吗"。
