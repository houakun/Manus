# Step 17：分辨率预算 —— 地板 ±46.8% 由什么撑起来，哪个杠杆才有效（**已执行：→ ±16.1%**）

> ⚠️ **本篇是 $0 的"再分析 + 预注册方案"，不是一次新实验。**
> 全部数字来自对**已有** suite `62bde6db`（7 任务 × 2 臂 × 3 次 = **42 次运行**）的重新分析；
> §六 的预测用的是参数模型，**假设写在 §二.3**，请连着假设一起读。

---

## 一、为什么要算这笔账

当前噪声地板是 **成本 ±46.83%**（`lab/runs/noise_floor.json`）。它的直接后果是：
**任何小于这个量级的 delta 都只能写"看不出来"** —— 而项目里已经有三批实验因此得到负结果
（`docs/step9-readpath-2x2.md` / `step9b` / `step9c`）。

所以在"换模型 / 加任务 / 加次数 / 改统计量"之间选哪条路**花钱最少、最可能真的降低地板**，
必须先知道：**这 ±46.8% 是模型随机性撑起来的，还是别的东西**。

本篇回答这个问题，并给出一张"加任务 vs 加次数"的预算表。

## 二、数据与方法

### 2.1 数据

`suit_id = 62bde6db…`（`label = 地板4（新模型 deepseek-v4.1-flash）`），
`lab/runs/traces.db` 的 `bench_runs` 表，42 行（7 个 semireal 任务 × 2 臂 × 3 次）。

### 2.2 口径（与 `lab/bench/noise.py` 对齐，先做复现校验）

- 逐任务相对差：`delta_t = (mean_b − mean_a) / mean_a × 100`；
- 分辨率 = 对 `{delta_t}` 做**配对 bootstrap** 区间的**半宽**。

**复现校验**：mean 口径下 `delta = +11.11%`、`resolution = ±47.08%`，
与存档的 `+11.11% / ±46.83%` 一致（0.25pt 是 bootstrap 抽样误差）。

### 2.3 预测用的参数模型（**这一段是假设，不是数据**）

```text
log(单次运行成本) = μ_t ± s_t/2 + ε        ε ~ N(0, σ_w²)
```

| 符号 | 含义 | 来源 |
|---|---|---|
| `μ_t` | 任务 t 的典型成本（log） | 7 个任务的实测值，bootstrap 重采样 |
| `s_t` | 任务 t 的**臂级系统差**（log） | `Var(s) = Var(d_t) − 2σ_w²/k`，从数据反推 |
| `σ_w²` | **单次运行**的抖动（log） | 每个（任务 × 臂）3 次运行的组内方差，pooled |
| `k` | 每臂每任务运行次数 | 变量 |

**两条强假设（会让预测偏乐观）**：
① 新任务与现有 7 个**同分布**；② `σ_w` 不随 k 变化（真实情况下窗口变长可能引入漂移）。

## 三、发现 1：**地板这个数字自己就很宽**

对 7 个 `delta_t` 再做一层 bootstrap，看**半宽本身**的分布：

| 量 | 值 |
|---|---|
| 半宽中位数 | **44.4%** |
| 半宽 **90% 区间** | **[12.8%, 58.9%]** |

也就是说："地板 ±46.8%"是**7 个点**估出来的，它自己可能落在 12% 也可能落在 58%。

**推论**：`bench gate` 把 ±46.83% 当成一个**点阈值**用，是过度自信。
合理的读法是"**地板至少在 40% 量级**"，而不是"地板 = 46.83%"。

---

## 四、发现 2：**78% 的地板不是"模型随机"**

| 量 | 值（log 尺度） | 白话 |
|---|---|---|
| `σ_w`（单次运行抖动） | **0.340** | 同一任务、同一配置跑两次，成本可差 **±48%** |
| `Var(d_t)`（per-task delta 的方差） | **0.3531** | — |
| 其中**运行噪声**贡献 (`2σ_w²/k`) | 0.0770 → **22%** | 加次数能影响的部分 |
| 其中**任务/臂级系统差**贡献 | 0.2761 → **78%** | 加次数**动不了**的部分 |

> ⚠️ 必须说清：这 78% 我**没有**验明它到底是"任务固有差异"还是"臂级时段效应"
> （noise_floor.json 的 notes 早就警告过后者）。但**无论是哪一种，结论都一样**：
> 它**不随每臂运行次数 k 下降**，所以**加次数救不了它**。

---

## 五、发现 3：稳健统计量**没有**让地板变窄（反直觉）

一个自然的想法是"用中位数 / 截尾均值，抗重尾"。实测（同一份 42 次数据）：

| 口径 | `delta` | **分辨率（±）** |
|---|---|---|
| **mean（现用）** | +11.11% | **±47.08%** |
| median（每任务取 3 次中位数） | +14.64% | **±54.22%** |
| trimmed-33（每臂去掉最大最小各 1） | +14.64% | **±52.66%** |

**都更宽。** 原因不神秘：n=3 时"中位数"约等于"取中间那一个值"，
**丢掉了信息**，方差反而更大。稳健统计量抗的是**离群点**，不是**样本少**。

**推论**：不要为了降地板去换统计量 —— 至少在这份数据上这是**反向**的。

---

## 六、预测表：加任务 vs 加次数

（参数模型，每个格子 = 200 次模拟的**半宽中位数**）

| 任务数 n ↓ \ 每臂次数 k → | **3** | **6** | **12** |
|---|---|---|---|
| **7（现在）** | 42.4% | 40.5% | 39.2% |
| **14** | 33.6% | 33.3% | 28.8% |
| **28** | 26.2% | 23.8% | 22.8% |
| **56** | 19.7% | 18.1% | 17.3% |

> 上表由 §十 的脚本直接产出（同一数据 + 同一 seed）。⚠️ 它是 **Monte Carlo 值**：
> 换 seed 单个格子会在 **±2pt** 内跳动（表里 n=14 那一行 k 不单调就是这种跳动），
> 所以**看量级，不要看小数点**。

模型在 `(n=7, k=3)` 处给出 42.4%，**实测 47.1%** → 模型**低估约 4.7pt**，
所以上表应读成"**下限量级**"，不要当精确预言。

**三条读法**：

> ⚠️ **这三条后来被推翻了**（见 **§十二**）：它们只是 **7 个 semireal 任务**的属性 ——
> 换成 **18 个 regression 任务**后，“系统差”从 78% 掉到 ≈0，**加次数反而变成有效手段**。
> 继续读本节时请记住：这里测的是**那个任务集**，不是测量台的通用规律。

1. **加次数很快饱和**：k 从 3 → 12（**运行量 ×4**）只把地板从 ~42% 压到 ~39%（**不到 4pt**）；
   而且 k ≥ 6 之后基本不动 —— 这正是 §四 那 78% 的直接后果。
2. **加任务是有量级的杠杆**：n 从 7 → 28（任务 ×4）压到 ~26%（**约 16pt**）。
3. **两者合用不叠加**：28 任务 × 6 次 ≈ 24%，比 28 任务 × 3 次的 26.2% 只多 ~2pt —— 与 1 一致。

## 七、一个现成的杠杆：**地板只测了 7 个任务**

这是本次分析里**最可操作**的一条：

| 事实 | 值 |
|---|---|
| `regression` 组的任务数 | **18** |
| 当前地板实际测的任务数 | **7**（T13 用 `--group semireal`） |
| `bench gate` 拿这份地板去守 | **任意** suite（可能 28 个任务） |

两个后果：

1. **口径不匹配**：分辨率是**任务数 n 的函数**（≈ `1/√n`）。
   拿 7 个任务测出的 ±46.8%，去当 28 个任务 suite 的"测量分辨率"，
   **偏保守**（真实的 28 任务分辨率按同一机制应窄约一半）—— 也就是说**分辨率被白白浪费**。
2. **补测很便宜**：把地板扩到全部 **18 个 regression 任务**
   （18 × 2 臂 × 3 次 = **108 次运行**，按单次 ≈ $0.021 估 **≈ $2.3**），
   按 §六 的表预计地板从 **~47% → ~31%**。
   比"加 21 个新任务"便宜一个数量级，比"加次数"有效得多。

> ⚠️ 但 `regression` 组里含 synthetic + semireal + 部分 ci，**任务异质性未必同分布**，
> 所以 18 任务的地板**比例上未必正好是 47%×√(7/18)=29%** —— §六 的表是模型值，
> 真要引用必须**实测**。

## 八、建议（按性价比排序）

| # | 动作 | 花费 | 预计地板 | 评价 |
|---|---|---|---|---|
| 1 | **把"地板是在 n 个任务上测的"写进 gate 输出**，并禁止拿 7 任务地板当 28 任务阈值 | **$0** | 不变 | 不改数字，只改**读法**；`noise_floor.json` 里已有 `task_count`，gate 目前不强调 |
| 2 | **地板重测扩到 18 个 regression 任务** | **≈ $2.3** | ~31% | **性价比最高**；先做这个 |
| 3 | 加次数 3 → 6 | ≈ $0.9 | ~41% | **不划算**（钱花得不多，但几乎没收益） |
| 4 | 新写 10 个 regression 任务（18 → 28） | 人力 | ~26% | 一劳永逸，但慢 |
| 5 | 换 median / 截尾口径 | $0 | **更宽** | **不要做**（§五） |

**一句话**：想把地板压下来，**加任务**（先把免费的 18 个用满）**远优于加次数**；
换统计量在这个数据规模上是负收益。

## 十、复现（**$0**）

以下脚本读 `lab/runs/traces.db`，重跑 §二~§六 的全部数字（无需 API Key）：

```bash
python - <<'PY'
import sqlite3, math, random, statistics as st
from collections import defaultdict
random.seed(20261009)
c = sqlite3.connect('lab/runs/traces.db'); c.row_factory = sqlite3.Row
rows = c.execute("""select task_key, arm, run_index, cost_usd from bench_runs
                    where suite_id like '62bde6db%'""").fetchall()
G = defaultdict(dict)
for r in rows:
    G[(r['task_key'], r['arm'])][r['run_index']] = r['cost_usd']
tasks = sorted({r['task_key'] for r in rows})

def hw(vals, B=2000):
    n = len(vals)
    if n < 2: return 0.0
    ms = []
    for _ in range(B):
        ms.append(sum(vals[random.randrange(n)] for _ in range(n)) / n)
    ms.sort(); return (ms[int(0.975*B)] - ms[int(0.025*B)]) / 2

def vals_of(t, arm):
    return [G[(t, arm)][i] for i in sorted(G[(t, arm)])]

def per_task_delta(fn):
    return [(fn(vals_of(t,'noise-b')) - fn(vals_of(t,'noise-a'))) / fn(vals_of(t,'noise-a')) * 100
            for t in tasks]

d = per_task_delta(st.mean)
print(f"mean: delta={st.mean(d):+.2f}%  res=±{hw(d):.2f}%")
print(f"median: res=±{hw(per_task_delta(st.median)):.2f}%")

# 半宽**自身**的分布（本文 §三）
bws = sorted(hw([d[random.randrange(len(d))] for _ in range(len(d))], B=1000) for _ in range(300))
print(f"半宽的 90% 区间: [{bws[15]:.1f}%, {bws[285]:.1f}%]  中位 {bws[150]:.1f}%")

logs = {t: {a: [math.log(x) for x in vals_of(t, a)] for a in ('noise-a','noise-b')} for t in tasks}
sw2 = st.mean([st.variance(logs[t][a]) for t in tasks for a in ('noise-a','noise-b')])
dl = [st.mean(logs[t]['noise-a']) - st.mean(logs[t]['noise-b']) for t in tasks]
var_d = st.variance(dl)
print(f"sigma_w={math.sqrt(sw2):.3f}  Var(d_t)={var_d:.4f}  "
      f"运行噪声={2*sw2/3:.4f} ({100*(2*sw2/3)/var_d:.0f}%)  "
      f"系统差={var_d-2*sw2/3:.4f} ({100*(var_d-2*sw2/3)/var_d:.0f}%)")

# --- §六 预测表：加任务 n vs 加次数 k（模型见 §二.3）---
sw = math.sqrt(sw2); sys_sd = math.sqrt(var_d - 2*sw2/3)
mus = [st.mean([*logs[t]['noise-a'], *logs[t]['noise-b']]) for t in tasks]
def simulate(n, k, M=200):
    out = []
    for _ in range(M):
        gen = []
        for _ in range(n):
            mu = random.choice(mus); s = random.gauss(0, sys_sd)
            a = [math.exp(mu + s/2 + random.gauss(0, sw)) for _ in range(k)]
            b = [math.exp(mu - s/2 + random.gauss(0, sw)) for _ in range(k)]
            gen.append((st.mean(a), st.mean(b)))
        ds = [(gb-ga)/ga*100 for ga, gb in gen]
        out.append(hw(ds, B=1000))
    out.sort(); return out[len(out)//2]
print("      " + "".join(f"{k:>9}" for k in (3, 6, 12)))
for n in (7, 14, 28, 56):
    print(f"n={n:<4}" + "".join(f"{simulate(n,k):>8.1f}%" for k in (3, 6, 12)))
PY
```

### 11.2 结果：成本地板 **±46.83% → ±16.10%**

| 指标 | 7 任务（旧，`62bde6db`） | **18 任务（新，`a88ca8f2`）** | 变化 |

### 11.3 与 §六 的预测对照：**预测偏保守了**

§六 的模型在 n=18 处给 ~**31%**，实测 **16.1%**（不到预测的一半）。

**为什么**：§六 的模型假设“新任务与现有 7 个**同分布**”，而实际加进来的 11 个 synthetic 任务
**比 semireal 稳定得多**（单次成本均值 $0.012 vs semireal $0.022，任务间异质性也更小）。
这正好印证 §七 那句警告 —— **任务异质性不是同分布的，所以比例换算不可靠，必须实测**。

### 11.4 三条必须一起读的限制

1. **耗时没跟着变好**（±29.3% → ±42.3%）：被个别 synthetic 任务主导（单任务最大 **+296.53%**）。
   所以“地板降低了”只对成本 / token / 工具调用成立，**耗时的细粒度结论仍然不可读**。
2. **成功率地板不再是 ±0.00pt**：这 108 次里有 **6 次真失败**（两臂 96.3% vs 92.6%）。
   归因：4 次是**产物没产出**（`sem_log_analyze` / `sem_refactor_config` / `syn_fizzbuzz` / `syn_rename_files`）、
   1 次 `task_timeout`（344s）、1 次 LLM 重试耗尽（274s）。
   → 两面含义：① 这是**更诚实**的地板（旧那个 ±0.00pt 是假象）；
   ② 它也说明 **regression 组并非 100% 稳定**（94.4%），默认 5pt 的成功率阈值**比地板还紧**。
3. **口径变了**：这份 ±16.1% 是在 **18 个任务**上测的，而多数历史 suite 只有 7 个 regression 任务 ——
   所以 `bench gate` 会（正确地）报“口径不一致”。**不要**把 ±16.1% 直接当 7 任务 suite 的阈值。

### 11.5 顺带修掉的一个真缺陷：预估成本**不按模型筛**

跑 §八 #2 时发现：`bench noise-floor --purpose regression` 预估 **$9.58**，而 §七 写的是 ≈$2.3。

查下去是 `SpanStore.avg_cost_for_group` **不筛模型**：

| 模型（semireal 组） | 单次成本 |
|---|---|
| `deepseek-reasoner` | $0.1086（268 次） |
| `deepseek-v4.1-flash` | **$0.0212**（76 次） |

混在一起算 → 对当前模型**高估 4.5 倍**。这与该方法 docstring 里记的“曾经**低估** 3 倍”是**同一类错误的两个方向**：
估错本身才是问题（高估会让 `--yes` 变成例行动作，而例行确认等于没有确认）。
已修：`avg_cost_for_group` 新增 `model_name` 过滤 + 调用点传当前模型 + 用例
`test_avg_cost_for_group_filters_by_model`。修完预估 **$2.29**，而实际花了 **$1.732**（这次反而略高估，方向安全）。

## 十二、更正（2026-10-10）：新地板**推翻了 §六 的一条结论**

> ⚠️ 本节必须与 §六 **一起**读：§六 的“加次数很快饱和”**只在 7 个 semireal 任务上成立**。
> 它是那个任务集的属性，**不是**测量台的通用规律。

### 12.1 两个任务集上的方差分解**完全相反**

| | 7 任务（semireal，`62bde6db`） | **18 任务（regression，`a88ca8f2`）** |
|---|---|---|
| `sigma_w`（单次运行抖动，log） | 0.340 | 0.449 |
| `Var(d_t)` | 0.3531 | **0.1209** |
| 其中**运行噪声** | 22% | **~100%** |
| 其中**系统差** | **78%**（sd=0.525） | **≈0**（sd=0.000） |

（18 任务那一栏只在**正成本**运行上算：有 1 次运行成本为 $0（LLM 重试耗尽），
`log(0)` 会污染方差 —— 分析时踩到的一个小坑。）

### 12.2 于是 ③④ 的排序**反过来了**

| 动作 | 花费 | 7 任务上的预测（§六） | **18 任务上的预测** |
|---|---|---|---|
| ③ 加次数 3 → 6 | ≈$1.75 | ~41%（几乎不动） | **~12.3%**（从 ±16.1% 起） |

### 12.3 为什么会反过来（以及为什么这不奇怪）

§七 自己写过：“任务异质性**不是同分布的**，比例换算不可靠”。
7 个 semireal 任务里有几个**重尾**任务（典型 `sem_log_analyze`：同一臂 3 次运行成本涨 2.6 倍），
它们制造了那 78% 的“系统差”；而 11 个 synthetic 任务稳定得多，加进来后把这一项**稀释掉了**。

所以正确的说法是：

- **“加次数有没有用”取决于任务集的重尾程度**，不存在通用答案；
- 想回答它，只能在**当前这个任务集**上做一次方差分解（**$0**，§十 的脚本换个 suite_id 即可）。

## 十三、§十二 的“反转”**也是错的**（2026-10-10，6 次数据打脸）

> §十二 根据 3 次数据宣布“加次数有效（±16.1% → ~12.3%）”。
> **实测推翻了它。** 本节把它记下来 —— 包括**为什么错**。

### 13.1 实测：216 次运行（18 任务 × 6 次 × 2 臂，suite `01417afc`）

| 指标 | 3 次（`a88ca8f2`） | **6 次（`01417afc`）** |
|---|---|---|
| 成本 | ±16.10% | **±15.15%**（预测是 ~12.3%） |
| token | ±16.85% | ±15.82% |
| 工具调用 | ±14.51% | ±14.65% |
| 耗时 | ±42.28% | **±47.51%**（继续变差） |
| 成功率 | ±9.26pt | **±5.56pt**（这是真正的收获） |
| 实际花费 | $1.732 | **$3.656**（预估 $4.52） |

**成本地板只降了 0.95pt。** §十二 的“加次数有效”**不成立**。

### 13.2 为什么错：**把“负的方差估计”当成了“系统差=0”**

§十二 用的分解是 `系统差 = Var(d_t) − 2σ_w²/k`。两个样本量给出的数完全不同：

| | 3 次 | **6 次（更可靠）** |
|---|---|---|
| `σ_w` | 0.449 | **0.571** |
| `Var(d_t)` | 0.1209 | 0.1667 |
| 纯噪声预测 `2σ_w²/k` | 0.1347 | 0.1088 |
| 实测 / 预测 | 0.90× | **1.53×** |

3 次数据里 `Var(d_t) − 2σ_w²/k = −0.0138`（**负数**）。我把负数截断成 0，
于是写出“系统差 ≈ 0”。

**这是错的**：方差估计出现负值，说明**估计本身不可靠**（每任务每臂只有 2~3 个观测估 `σ_w`、
18 个点估 `Var(d_t)`），**不是**说明系统差不存在。6 次数据把 `σ_w` 估高了 27%
（0.449 → 0.571），“系统差”立刻变成正数 **0.0579**。

> **教训一句话：把“减出来的负数”截断成 0，等于用估计误差造了一个结论。**
> 负值应该读成“这个分解在当前样本量下不可用”，而不是“该项为 0”。

### 13.3 加次数真正的收获：**暴露了一个装置问题**

> ⚠️ **这一节的归因后来也被推翻了**：那个 6.48pt 在统计上**不显著**，
> 而失败的真实机制是 **planner 空转**（16/17 次一个工具都没调）。见 **§十四**。

成本地板没降，但**成功率地板从 ±9.26pt 降到 ±5.56pt** —— 于是有一个差异**变得可读**了：

| | noise-a | noise-b | 差 |
|---|---|---|---|
| 3 次 | 96.3%（52/54） | 92.6%（50/54） | 3.7pt（**< ±9.26pt，不可读**） |
| **6 次** | 95.4%（103/108） | **88.9%（96/108）** | **6.48pt（> ±5.56pt，可读）** |

**两臂配置完全相同**（同一 guard、无故障），所以 6.48pt 的差**不应该存在**。
按 `noise_floor.json` 自己的 notes：“如果 delta 大得离谱，先怀疑**实验装置**”。

已排除的归因：

- **不是时间漂移**：前半 108 次 9 次失败、后半 8 次（均匀）；两臂的失败时间点分散在 18:42~21:25。
- **不是某个轮次的位置效应**：交错按**轮次**轮转臂顺序（`runner._build_schedule`），
  而 b 臂在 run0/run2/run3 都更差 —— 位置在轮次间是轮转的，抵消不了“每个轮次都更差”。
- **失败任务分散**：11 个不同任务，最多 `syn_csv_filter` 3 次。

**尚未排除的（下一步要查的）**：

- 交错粒度是**轮次级**（一个臂连续跑 18 个任务 ≈ 25 分钟），不是**任务级**（A,B,A,B…）。
  轮转只能让位置效应在**多轮之间**平均，消不掉**块内**的时段漂移。
- 汇总层面的 12 vs 5 次失败，二项检验 **p ≈ 0.07**（不显著）；
  而配对口径下 6.48pt > 5.56pt（可读）。两个口径不一致 ——
  说明配对确实提高了功效，但也提醒：这里的“可读”只是“配对区间不跨 0”，**不是“机制已查明”**。

### 13.4 结论：**别再叠样本了，先查那个 6.48pt**

| 动作 | 结果 |
|---|---|
| ③ 加次数 3 → 6（$3.656） | 成本地板 **±16.10% → ±15.15%**（几乎没动）；成功率地板 **±9.26 → ±5.56pt**（有用） |
| ④ 加任务 18 → 28 | **未做，且现在更没理由**：连加次数都没用，说明瓶颈不在样本量 |

**下一步不该再加样本，而该查那个 6.48pt 从哪来** —— 它是**装置**的系统偏差，
在查清之前，所有“两臂对比”（包括加固对照实验）都带着这个偏差。

## 十四、§十三 的“装置系统偏差”**也下早了** —— 真正的机制是 **planner 空转**（2026-10-10）

> §十三 说“装置有系统偏差”。**这一条也下早了。** 查机制后真相是另一个东西，
> 而且它比“装置问题”有价值得多。

### 14.1 失败的形态：**16/17 次根本没有调用任何工具**

| | 成功（199） | 失败（17） |
|---|---|---|
| `tool_calls == 0` | **0** | **16** |
| `answer` 是**计划文本**（“用户希望我…” / “我来分析你的需求…”） | **0** | **16** |
| 平均 `tool_calls` | 10.9 | 0.9 |
| 平均 `llm_calls` | 16.6 | 7.8 |
| 平均耗时 | 62.2s | 18.3s |

**0/199 vs 16/17** —— 这不是巧合，是一个**确定的失败模式**：
planner 输出的结构化 JSON 不合规（日志里是 `结构化输出解析失败（第 1/2 次）: 你返回的是 list，期望一个对象`），
执行器因此**完全没有启动**，Agent 把 planner 的**计划文本**当成了最终答案。

唯一的例外（`syn_prime_count` / noise-b / run3）是真执行了 15 次工具调用、产物却不对 ——
**与另外 16 次机制完全不同**。

### 14.2 而且它**自述成功**

| 判定 | SUT 自述 | 次数 |
|---|---|---|
| 失败 | **自述成功** | **16** |
| 失败 | 自述失败 | 1 |
| 成功 | 自述失败 | 2 |
| 成功 | 自述成功 | 197 |

**假阳性率 = 16/17 = 94%。** 而且这 16 次的 `error_type` 是 `None` ——
**SUT 不认为这是错误**。判定器（纯函数、不看自述）抓住了全部 16 次。

> 这正是 README 里那句“判定器**不看 Agent 自述**”的价值：
> 如果只看自述，这 7.4% 的失败会**全部消失**。

### 14.3 于是“6.48pt 臂差异”该怎么读

空转按臂：**noise-b 11 次 / noise-a 5 次**（Fisher p ≈ 0.13，不显著）。

- 空转是**模型输出格式的随机事件**，不是某个臂的属性；
- §十三 引用的“6.48pt > 分辨率 ±5.56pt”里，**分辨率不是显著性检验**
  —— 它是“单次配对 delta 的噪声半宽”，而两臂差异的显著性要用汇总样本量算
  （Fisher 精确检验：p = **0.064**，未达 0.05；逐任务配对 7:1，p ≈ 0.07）；
- **结论：没有足够证据说装置有系统偏差。**

### 14.4 三次下结论、三次被数据修正

| 轮次 | 结论 | 被谁推翻 |
|---|---|---|
| §六 | “加次数饱和，加任务才有量级” | §十二（据 3 次数据） |
| §十二 | “系统差≈0，加次数有效” | §十三（6 次数据实测） |
| §十三 | “装置有系统偏差” | **§十四（机制分析：planner 空转）** |

三次里**两次是“用不足的样本量下结论”**，一次是“用不匹配的显著性口径下结论”。
共同点：**都在机制没查清之前就给了因果解释**。

### 14.5 真正值得钉下来的一条（它比地板数字重要）

> **SUT 的 planner 在 216 次运行中有 16 次（7.4%）输出格式不合规 → 执行器不启动 →
> 把计划文本当答案 → 且自述成功。判定器抓住了全部 16 次。**

可复现（$0，不需要再跑模型）：**`python -m lab bench idle-failures`**（新增命令，

> 直接标出“⚠️ 空转：一个工具都没调用”—— 否则光看空列表的工具序列很容易被当成“没记录”。

**下一步（$0）**：

## 十六、机制**第三次更正**：不是 planner 格式，是 `react` 忽略了 `step.success`（2026-10-10）

> §十四 说“planner 输出格式不合规”。**§十四 的机制描述是错的。**
> 用测量台自己的入口读了一次失败运行的完整轨迹后，真正的原因浮出来了 ——
> 而且它比“格式不合规”更具体、更可修。

### 16.1 轨迹级的证据（`bench show 01417afc syn_csv_filter --run 0 --arm noise-b`）

```text
[task  ] manus-planner-react[fast]      ok
  [llm ] deepseek-v4.1-flash            ← create_plan（正常）
  [step] 编写并运行 Python 脚本：读取 ...  ok   {'success': 'False'}   ← 注意这里
    [llm ] deepseek-v4.1-flash          ← execute_step
```

**step 的 status 是 `ok`，但 `success=False`。**

也就是说：**模型在结构化结果里诚实地写了“这一步没做成”**（`Step.success=false`），
而 `react.execute_step` 拿到合法 JSON 后**无条件**把 `step.status` 置成 `COMPLETED`：

```python
if holder.ok:
    step.success = new_step.success          # ← 如实写了 False
    ...
    step.status = ExecutionStatus.COMPLETED  # ← 却置成“完成”
    ...
    step.status = ExecutionStatus.COMPLETED  # ← 而且下面还有一处重复赋值
```

于是：**“失败的步骤”被记成“完成的步骤”** → `steps_done` 计入 1 → flow 认为干完了 →
以“任务成功”结束（`self_reported_ok=True`）→ 而产物根本不存在。

**不是 planner 的格式问题，是 react 忽略了模型的自评。**

### 16.2 为什么这件事只有测量台能看见

| 视角 | 看到的东西 |
|---|---|
| SUT 自己 | `ok=True`、`self_reported_ok=True`、`steps_done=1` —— **一切正常** |
| `react` 的日志 | 没有任何 ERROR |
| **判定器（纯函数，不看自述）** | `✗ [csv_rows] 文件不存在或不可读: /home/ubuntu/filtered.csv` |
| **`bench show`** | `[step] ... ok {'success': 'False'}` + `⚠️ 空转：一个工具都没调用` |

### 16.3 修复（`[lab/D11]`，两处）

| 文件 | 改动 |
|---|---|
| `api/.../agents/react.py` | `step.status` 反映 `new_step.success`（`COMPLETED` / `FAILED`），事件状态同步；`success=false` 时写入 `step.error`；删掉那处**重复赋值** |
| `api/.../flows/planner_react.py` | ① 收尾时若**没有任何步骤成功** → 上报 `ErrorEvent`（否则 adapter 的 `ok` 仍是 True）；② **顺手修掉一个真实缺口**：`EXECUTING` / `UPDATING` 分支直接 `self.plan.xxx`，而第 4 步有一条“会话 WAITING → 直接置 EXECUTING（**不经过 PLANNING**）”的路径 → `plan` 为 None 时抛 `AttributeError`（类型上它一直是 `Plan \| None`）。改成**显式守卫 + 结构化错误事件**（与 D5/D9 同一风格；没用 `assert`，因为 `-O` 会把它移除） |

> 另：`planner_react.py` 里 5 处无占位符的 f-string（`f"..."`）由 lint 自动去掉了 `f` 前缀 —— 纯风格，不影响行为。

**验收用例**：`lab/tests/test_sut_robustness.py::test_step_reported_unsuccessful_is_not_marked_completed`
（D11，沿用 D5/D9/D10 的 ScriptedLLM 手法）：脚本让模型“一个工具都不调、直接返回 `success=false`”，
断言 `steps.failed >= 1`、`steps.succeeded == 0`、`ok is False`、`error_type == "agent_error"`。

**`pytest` 361 passed**（+1）、`bench validate` 28/28 —— 修复没有破坏任何既有行为。

### 16.4 ⚠️ 这条修复**没有**被真模型验证过

ScriptedLLM 用例证明的是“代码逻辑对了”，**不是**“真模型的空转率降下来了”。
要回答后者必须**重跑**（18 任务 × 3 次 ≈ $1.7），而且按 §十二/§十三 的教训：
**先别把预期写进结论**。

另外：`api/` 从此有了行为变更 —— 按项目自己的口径，**修复前后的 suite 不可直接比**
（`SuiteResult.sut_version` 就是为这件事准备的）。

## 十七、D11 修复的真模型验证（2026-10-10，**$0.893**）

> §16.4 写着“这条修复**没有**被真模型验证过”。本节把它补上 —— 而且**先写了预期再看数据**。

### 17.1 预注册的四个指标（跑之前写下的）

| 指标 | 修复前（`01417afc`，216 次） | **预期** |

| **假阳性**（自述成功 ∧ 判定失败） | **16（94%）** | **→ 0** |
| **空转次数本身** | 16（7.4%） | **预期不降**（模型行为没变） |

最后一条是刻意的：**这次修的是“报告”，不是“模型能力”** ——
如果它降了，反而要怀疑哪里不对。

### 17.2 实测（suite `194c8daf`，18 任务 × 3 次 = 54 次，实际 **$0.893**）

| 指标 | 修复前 | **修复后** | 预注册 | 结论 |
|---|---|---|---|---|
| 成功率 | 92.1%（199/216） | **96.3%（52/54）** | — | — |
| 失败的 `error_type` | `None` × 16 + `agent_error` × 1 | **`agent_error` × 2** | 全部 agent_error | ✅ |
| **假阳性** | **16（94%）** | **0** | → 0 | ✅ |
| 空转次数 | 16 / 216 = 7.4% | **2 / 54 = 3.7%** | 预期不降 | ✅（见 17.3） |
| 自述=成功 ∧ 判定=失败 | 16 | **0** | — | ✅ |

两次失败逐条：

- `sem_json_to_csv run1`：`steps_failed=12`、`llm_calls=26`、**一个工具都没调** → 走 **D11 路径**
  （模型反复尝试 12 步全没做成）；
- `sem_refactor_config run0`：`steps_failed=0`、`llm_calls=1` → 走的是 **D9 路径**（计划为空），不是 D11。

### 17.3 空转次数为什么“没降”

**模型的行为一点没变**：它仍然会在结构化结果里写 `success=false`（或产出空计划）。
修复改的是**这一步之后**：失败不再被记成“完成”、不再自述成功。

所以正确的读法是：

> **“静默的 7.4% 变成了显式的失败”** —— 不是“失败消失了”。

如果空转真的降到 0，那说明模型换了 / 提示词变了，而不是这条修复起作用。

### 17.4 一条必须一起说的限制

成功率 92.1% → 96.3% **不能**读成“修复提升了成功率”：

- 样本量不同（216 vs 54），区间重叠；
- 修复前后的 `api/` **行为不同**，按项目自己的口径本来就**不可直接比**；
- 要判“成功率有没有变”，得用**交错 A/B**（同一次评测里跑两个版本），而不是比两个 suite。

### 17.5 结论

| 能说 | 不能说 |
|---|---|
| “修复后，'自述成功但什么都没做'从 94% 降到 **0**” | “修复让 Agent 不再失败” |
| “失败的 `error_type` 从 `None` 变成 `agent_error`（可归因了）” | “修复提升了成功率” |
| “空转仍是 3.7% —— 那是**模型行为**，不是这条修复能治的” | “空转已解决” |
