## 二、录制回放（`lab/replay/`）

### 2.1 四种模式，各自解决一个不同的问题

| 模式 | 联网？ | 未命中时 | 解决什么 |
|---|---|---|---|
| `off` | 是 | — | 默认，行为与改造前逐字节一致 |
| `record` | **总是** | — | 录一次真跑；**顺带测出服务端非确定性**（不额外花钱） |
| `reuse` | 未命中才联 | 联网并写入 | 改了 prompt 只想重跑受影响的那几次调用 |
| `replay` | **从不** | 直接失败 | 离线复现；**不需要 API Key**，可进 CI |

### 2.2 三个关键设计决定（都是踩过才明白的）

**① 键按请求内容算，不按调用序号。**
按序号算的话，上游任何变化（改一个 prompt、工具顺序变了、沙箱路径不同）
都会让整个序列**静默错位** —— 你会拿到属于另一个请求的响应，而轨迹看起来完全正常。
按内容算，错位变成**显式未命中**，而且支持**部分命中**
（这正是 `reuse` 能省钱的原理）。

用完整 sha256 而不是 `trace/span.py` 那种 12 位短指纹：后者作主键时，
缓存到十万条的碰撞概率约 2e-5，而碰撞的后果是**悄悄返回另一个请求的响应**。

**② `record` 总是联网，不做读穿。**
如果命中就读缓存，同一个请求永远不会被问第二次，
「服务端会不会给不同回答」这个问题就**永远测不到** —— 而那正是温度 0 也消不掉的噪声。
所以录制这个动作本身就免费携带了一个测量。

**③ `replay` 未命中必须失败，不能偷偷联网。**
偷偷联网会让「离线复现」变成「看起来离线、其实条件已经变了」——
回放出来的差异你无法归因。未命中就是信息。

### 2.3 真模型验证（本次实际跑的）

```
# 录制
python -m lab bench run --runs 1 --task syn_sum_range --replay record
→ 评测完成: 1/1 成功，耗时 24.5s

python -m lab replay stats
→ 条目数 18，等价成本 $0.0571
→ 服务端非确定性：0/18 = 0.0%（已观测范围内服务端是确定的）

# 严格回放（无副作用、不需要 Key）
python -m lab bench run --runs 1 --task syn_sum_range --replay replay
→ 评测完成: 1/1 成功，耗时 6.5s，但**未命中 6 次**（见 §3）
```

### 2.4 实测发现：SUT 把随机 UUID 放进了提示词

第一次严格回放立刻未命中 6 次。**第一反应是"我是不是把键算错了"** ——
差点去查一个本来就对的地方。为此加了「未命中诊断」，它直接说出了原因：

```
未命中：前 3 条消息一致，**第 4 条**不同。
  ✅ 抹掉 UUID / 时间戳之后两边完全一致 —— 这是 SUT 在提示词里放了随机 ID，
     **不是你的改动造成的**。
  处置：加 --replay-ignore-volatile（不需要重新录制）。
```

根因：SUT 的计划步骤 id 是 `uuid4()`，每次运行都不同 →
含它的请求**在字节层面必然不同**。

**这里有两个比"修 key"更重要的判断：**

1. **诊断信息本身就是产品。** 未命中只给一个"缓存里没有"时，
   人会去怀疑自己刚改的那行代码。直接说出"差异只在 UUID"，
   才能把「我改坏了」与「上游有隐藏随机性」区分开。
2. **发现问题的时刻就是需要开关的时刻，而那一刻不该再花钱。**
   所以**副键**（抹平易变字段后的键）在**录制时**就一并存下 ——
   `--replay-ignore-volatile` 可以事后开启，**不需要重新录制**。

加上它之后：

```
评测完成: 1/1 成功，耗时 0.4s          ← 真跑时 24.5s
命中 18 / 未命中 0（其中 2 次走副键回遯）
等价成本 $0.0571，实际消费 $0.0000
```

轨迹里每次 LLM 调用都带 `cache_status = hit` / `hit-loose` ——
**这是"本次运行确实离线"的取证依据**，而不是只能相信命令行参数。

## 三、发现并修掉的一个"静默降级"问题

严格回放未命中 6 次，**任务仍然判定成功**。
因为 SUT 在 LLM 调用失败后**降级继续**，最后还是写对了产物。

只看 `ok` 的话，一次「只剩半条轨迹」的运行与正常成功**长得一模一样**，
而它会安静地进入你的 A/B 对比。

处置（三层，缺一层就会被绕过）：

| 层 | 做法 |
|---|---|
| 过程 flag | 未命中 → `replay_misses:N`，进报告的「过程问题」 |
| 报告 | 「已知限制」里单列一节：**仍然成功 ≠ 复现成功**，这些样本不能用于对比 |
| 门禁 | `bench gate` 新增**回放完整性**门禁：候选有未命中 → 直接失败（退出码 1） |

实测退出码：

```
| 回放完整性 | = 0 次未命中 | 1 次运行回放不完整 | — | ❌ 失败 |
❌ 门禁未通过（1/4 项）
exit=1
```

> **纪律**：一个"看起来正常"的结果如果实际上不是完整复现，它就必须响亮地失败。

## 四、交错 A/B（`--ab-guard`）

### 4.1 为什么必须在一个 suite 内交错

`docs/step5-report.md` 已经诊断过：两组跑在不同时段时，
服务端整体变快/变慢会同时影响两边，**伪装成方案差异**（v1 → v3 的 -22% 就是这样）。

```bash
python -m lab bench run --runs 3 --group semireal \
  --fault partial_write --fault-tool write_file \
  --ab-guard none --ab-guard "retry,postcondition,enforce" \
  --label "加固对照（交错）"

python -m lab bench compare <suite_id> --arm "guard=none" --arm "guard=retry+postconditions+enforce"
```

排程**按轮次轮转**，而不是简单地"先跑完 A 再跑 B"：

```
第 0 轮: A, B      第 1 轮: B, A      第 2 轮: A, B
```

轮转是为了让两臂在「谁先跑」上对称 —— 否则 A 永远处在"刚启动、配额充足"的位置上。

### 4.2 两个容易踩的坑（都已用测试钉住）

| 坑 | 后果 | 处置 |
|---|---|---|
| 工作区不按臂隔离 | 两臂写同一份产物 → 成功率虚高，**且不报错** | 目录名带臂 slug（`run0-guard-none`），并有测试断言 4 个运行 4 个不同工作区 |
| `recover` 用 `int(name.replace("run",""))` 解析目录 | `run0-guard-none` → ValueError → **静默跳过整条臂** | 改正则，并把臂名一并恢复 |

### 4.3 落库：`bench_suites` 也要存实验条件

只存在运行级不够：跑完十几个 suite 后想回答"哪几次是同配置的"，
需要**一条 SQL**筛出来，而不是把几万行 runs 读进内存再在 Python 里比。

新增列：`bench_suites.{guard_config, fault_spec, replay_mode, arms, interleaved}`、
`bench_runs.{fault_spec, arm, replay_mode}`、`tasks.{replay_mode, replay_stats}`。

> `faults_injected` 原来只有**计数** —— 它能支持 `avg_cost_for_group(faulted=True)`，
> 却完全答不了"这次注入的是哪一类"。做到 10 类故障 × 2 种加固的矩阵时，
> 分组只能靠人工写在 label 字符串里。`fault_spec` 补上了这一列。

## 五、噪声地板（`bench noise-floor`）

### 5.1 它回答的是"分母"问题

没有它，这句话**没有意义**：

> B 比 A 便宜 22%

因为同一份代码重跑一次本来就可能差 20%+（`step5-report` §2.4 自己承认的缺口）。

```bash
python -m lab bench noise-floor --runs 3 --group semireal
```

做法：把**同一套配置**复制成两个只有名字不同的臂，交错跑。
两臂之间没有任何因果差异，所以观测到的差值除了采样噪声别无解释。

**两个数字别搞混**：

| 数字 | 含义 |
|---|---|
| `delta` | 两臂之间**实际观察到**的差（点估计）。理想接近 0；它有多大就说明运气有多大 |
| `resolution` | 配对 bootstrap 区间**半宽** = "小于它看不出来"。**报告里应该用这个** |

还会额外给一个 `单任务最大差值` 并标出「是否被个别任务主导」——
如果地板完全由一个任务贡献，那说明**那个任务本身不稳**，而不是测量系统抖，
两者的处置完全不同（前者修任务，后者放弃该指标的细粒度结论）。

### 5.2 为什么必须交错，不能分两段跑

分两段跑会把服务端**时间漂移**算进"地板"，地板被高估 →
**真实的退化会被当噪声放过去**。方向恰好是危险的那一边。
所以只有一个入口，且强制 `interleave=True`；如果传入的 suite 没交错，
`measure_noise_floor` 会在报告里显式警告"地板被高估"。

### 5.3 与门禁的联动（闭环）

`bench gate` 会自动读 `lab/runs/noise_floor.json`：

- 每条门禁旁边**附上实测分辨率**（没测过就显示「未测」，而不是假装有）；
- 阈值比地板还紧时显式报「这个门禁会因噪声频繁变红」；
- `--auto-thresholds` 直接把阈值抬到地板之上 ——
  **阈值必须来自数据，不能拍脑袋**（与 `guard/budget.py` 按分位数推导阈值同一条原则）。

### 5.4 链路已用真模型跑过一遍（但**不是**可用的地板）

```bash
python -m lab bench noise-floor --runs 2 --limit 3 --group synthetic \
  --label "噪声地板-链路验证(3任务,不具统计意义)"
# 实际花费 $1.04（12 次运行，单次均价 $0.0865）
```

实测输出：

```
- 臂: noise-a / noise-b（✅ 已交错）
- 规模: 3 任务 × 每臂 2 次，每臂 n=6
- 配置: guard=all fault=无 model=deepseek-reasoner T=0.0

| 指标 | 观测差值 | **测量分辨率（±）** | 单任务最大 | 被个别任务主导? |
|---|---|---|---|---|
| 成功率 | +16.67pt | **±25.00pt** | +50.00pt | 否 |
| 成本（相对） | +10.85% | **±35.56%** | +46.70% | ⚠️ 是 |
| token（相对） | +8.85% | **±33.08%** | +41.24% | ⚠️ 是 |
| 耗时（相对） | +21.86% | **±48.83%** | +81.25% | ⚠️ 是 |
| 工具调用（相对） | +0.25% | **±18.97%** | +20.69% | ⚠️ 是 |
```

**它可以证明的事**：交错排程真的生效（日志里 `[noise-a]` / `[noise-b]` 按轮交替）、
两臂工作区互相隔离、地板文件能落盘、门禁能读到它。

**它不能证明的事**：这 5 行数字**不是**可用的噪声地板。
样本量只有 3 个任务，而且 5 个指标里有 4 个被个别任务主导（⚠️）——
换句话说，这轮测出来的是「那 3 个任务自己的方差」，不是「测量系统的分辨率」。

> 把一次 3 任务的链路验证当成地板去用，就是拿测试跑通当结论 ——
> 而这个项目已经在「拿工具当结果」上栽过一次（§6）。
> 所以它只当**装置验收**看，真地板见 §6。

## 六、还没做（需要花钱的一步）

**真正的噪声地板已经测了**（`docs/noise-floor-measured.md`）。
下面保留当初写的命令与预估，以及实测结果与预估的对比：

```bash
# 回归任务集（7 个）× 每臂 3 次 × 2 臂 = 42 次运行
python -m lab bench noise-floor --runs 3 --group semireal --purpose regression --yes
# 预估 ≈ $4.6（按库里 semireal 无故障均值 $0.11/次）
# 实测：48 次运行 / $5.36（多跑了一个 capability 任务，见 docs/noise-floor-measured.md §1）
```

**实测结果（修复装置前 / 后）**：

| 指标 | 分辨率（±）修复前 | 分辨率（±）修复后 |
|---|---|---|
| 成功率 | ±0.00pt（**假象**） | ±0.00pt（**仍是假象**） |
| 成本 | ±28.94% | **±23.64%** |
| token | ±30.56% | ±24.38% |
| 耗时 | ±20.23% | ±22.60% |
| 工具调用 | ±21.55% | ±17.47% |

它立刻改变了三件事：

1. **v1 → v3 的 -22% 定量坐实是噪声**（落在 ±23.6% 之内）——
   当初靠机制推理撤回它是对的，现在它从"推理"变成了"测量"。
2. **故障注入的 +109% 是地板的 4.6 倍** —— 这是目前唯一一个幅度远超测量分辨率的因果结论。
3. **默认门禁阈值（成本 20%）比地板还紧** → 它本来就会因噪声频繁变红。
   `bench gate` 现在会当场报这一点。

> ⚠️ **修了一处装置失真（CRLF + GBK 乱码）之后，成本地板只从 ±28.9% 降到 ±23.6%。**
> 机制层面确实生效了（追行尾的 `cmp` 6→0、`od -c` 20→4），但它**不是地板的主因** ——
> 主因是缺 `sqlite3`（`apt-get` 8→8，一点没变），而那个还没修。
> 更要紧的是：两臂观测差值从 +29.6% 变成 -3.1% **不能归因于这次修复**
> （中位数没动、每臂只有 3 次，一个尾部事件换臂就够了）。
> 完整自纠见 `docs/noise-floor-measured.md` §6。

> `--purpose regression` 是默认值，且**必须**保持它：
> `capability` 任务（`sem_markdown_toc`）的波动是「能力边界」，
> 把它算进测量分辨率会让地板大到没有意义。

跑完之后：

1. `lab/runs/noise_floor.json` 会被写出来；
2. 之后每一次 `bench gate` 都会带上实测分辨率；
3. 此前所有 A/B 结论（包括 v1 → v3 的 -22%）才有了一把可比对的尺子。

更重要的发现是**这个 ±29% 由什么构成**：逐任务拆开后，主导项是
`sem_sqlite_report` 的 +118%，而它由两个**装置问题**撑起来（不是模型抖动）：

1. fast mode 没有 `sqlite3` 命令行，而任务的 `goal` 里没写这件事
   → Agent 前 5 次调用都在探环境（任务 YAML 的 `solution` 注释里其实写了）；
2. cmd.exe 的一切输出带 `\r\n`、中文错误信息是 GBK 乱码
   → Agent 花了 10 次调用追行尾。

所以：**地板量的是整个装置，不只是模型。** 详见 `docs/noise-floor-measured.md` §5。

## 七、顺带修掉的问题

| # | 问题 | 为什么值得记 |
|---|---|---|
| 1 | 严格回放未命中 6 次仍判 OK | 见 §3，**静默降级**是最危险的一类"看起来正常" |
| 2 | `recover` 静默跳过带臂的目录 | 旧代码的 `except ValueError: continue` 会**安静地丢样本** |
| 3 | 指标列存成 JSON 后无法 SQL 分组 | 见 §4.3，`fault_spec` / `arm` 必须是独立列 |
| 4 | 回放运行的 `cost_usd` 会被读成真实消费 | 拆出 `equivalent_cost_usd` / `actual_spend_usd` 两个字段 |
| 5 | 回放的耗时会被读成"变快了" | 回放时 `_latency_ms` **归零**，原值另记为 `equivalent_latency_ms` |

第 5 条值得展开：耗时是最容易被误读成"我们优化了它"的指标。
一次 0.4s 的回放如果带上录制时的 24.5s 耗时会让人以为"快了很多"；
带上 0 又会被读成"性能极好"。所以**归零 + 单独记等价量 + 报告里显式声明**。

## 九、一个方法论观察

这两件事（回放 / 噪声地板）看似是两个独立功能，其实是**同一个东西的两面**：

| | 问的问题 | 用在哪 |
|---|---|---|
| **回放** | 「同样的输入，我能再得到同样的输出吗？」 | 调试、CI、离线分析 |
| **噪声地板** | 「**不同的**输入，我能分辨出来吗？」 | 解读 delta |

一个是**控制变量**，一个是**测量分辨率**。
没有前者，你无法复现；没有后者，你无法判断。
两者都缺的时候，最容易发生的事就是**把噪声当结论**——
而本项目已经因此撤回了一个 -22% 的结论。
