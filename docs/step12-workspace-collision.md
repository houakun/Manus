# Step 12：工作区覆盖 —— 一个**测量台地基缺陷**的完整证据链

> 承接 Step 11（judge 首次校准）。Step 11 的三个 κ 数字已被**撤回**；本篇记录：
> 它是怎么被发现的、为什么能潜伏、修了什么、以及**修复本身的证据**。
>
> 一句话：**判定是当场做的（所以是对的），但事后读到的产物可能属于另一次运行。**
> 这毁掉的不是某一个实验，而是"事后读产物"这个能力本身。

---

## 一、缺陷是什么

```python
# lab/bench/runner.py（修前）
workspace = bench_root / task.group / task.key / f"run{run_index}{arm_suffix}" / "workspace"
#                                                                  ↑ 没有 suite_id
```

工作区路径只由 `group / task_key / run<N><arm>` 决定。于是**所有用同一 arm + 同一 run
编号的 suite 写同一个目录** —— 后跑的 `_reset_workspace()` 会清空它再重写，
先跑的那份产物就**被静默覆盖**了。

关键点：**覆盖发生在判定之后**。所以：

| 环节 | 是否受影响 | 原因 |
|---|---|---|
| 当次判定（`ok`） | ❌ 不受影响 | 判定读的是**当时**的工作区 |
| 指标（token/成本/耗时） | ❌ 不受影响 | 从 `bench_runs` 落库读 |
| `bench show` 的"关键产物" | ✅ **受影响** | 事后读目录 |
| judge 校准（judge 看产物） | ✅ **受影响** | 事后读目录 |
| 人工标注（人看产物） | ✅ **受影响** | 事后读目录 |
| `bench recover` | ⚠️ 部分 | 靠目录反推运行，会张冠李戴 |

## 二、它是怎么被发现的（这一点比缺陷本身更值得记）

**不是单测发现的。** 单测全绿 —— 因为每条测试只跑一个 suite，而缺陷只在
"多个 suite 复用同一 `run<N><arm>` 目录名"时才暴露。

发现路径是**交叉核对两件独立记录**：

1. `bench purpose-audit` 提示 `syn_string_reverse` / `syn_word_freq` 有"干净失败"，我去看
   `bench show`，读到失败原因是**旧的期望值**（`TNEGA SUNUM` 应为 `TNEGA SUNAM`）——
   那是历史数据，说得通。
2. 但接着我发现 **`sem_log_analyze` 的一条运行"判定通过、工作区里却什么产物都没有"**。
   判定通过要求产物存在，所以产物**曾经**存在 → 它后来消失了/被换掉了。
3. 于是写脚本比对**工作区最新文件 mtime vs 该次运行的时间** → 得到 **39/100**。
4. 再用 `git`/库交叉验证具体案例（见下）。

**教训**：这是 README 自纠 #1/#8 的同类 —— *观测手段本身要先被验证*。
"判定通过"与"产物在不在"是两份记录，它们的**不一致**才是线索。

### 具体案例（三个"判定说文件不存在、文件现在却在"的样本）

| 样本 | 判定记录时间 | 文件 mtime | 文件现在的内容 |
|---|---|---|---|
| `a7c92a0b:sem_sqlite_report:0:noise-a` | 2026-09-16 19:16 | 2026-09-17 20:23 | `sales.db` 8192B，4 行数据正确 |
| `beee03f1:syn_log_error_count:0:-` | 2026-09-16 14:05 | 2026-09-16 20:10 | `error_count.txt` = `2`（正确） |
| `70a79a26:sem_json_to_csv:0:-` | 2026-09-16 19:16 | 2026-09-17 20:02 | `products.csv` 内容正确（该次 `error_type=sut_crash`） |

三个文件的时间都**晚于**判定时间 → 它们是**后来的运行**写进去的。

## 三、影响面

| 口径 | 数字 |
|---|---|
| Step 11 的 100 条校准样本中，产物被覆盖过的 | **39 条（39%）** |
| 更宽的候选池（400 条最近运行）中 stale 的 | **256 条（64%）** |
| 库里"判定失败"的 23 条样本里，人工认为"其实做完了"的 | **15 条**（10 条是任务期望值写错、**3 条是工作区被覆盖**、2 条是格式/内容归因分歧） |

第 3 行值得单独说：**"库里失败"与"产物是坏的"是两件事**。
所以"多抽失败样本来平衡金标"这个思路本身就不成立（Step 11 就是这么栽的：
89/100 条三维度全 true，所有反例来自同一个任务）。

## 四、修了什么（三件事）

### 4.1 工作区按 suite 隔离（`lab/bench/runner.py`）

```python
workspace = bench_root / suite_id / task.group / task.key / f"run{run_index}{arm_suffix}" / "workspace"
```

- 用**完整** suite_id（不是短 id）：目录名撞车的后果正是这个 bug，不值得省那几个字符。
- `run<N><arm>` 的命名**保持不变** —— `bench recover` 靠它反推运行序号。
- `bench recover` 同时认**新旧两种布局**（历史目录不迁移）：两者层数不同
  （3 层 vs 4 层），glob 互不重叠，而 `group`/`task` 在两种布局下都位于
  `workspace.parents[2]`/`[1]`，所以解析逻辑共用。

### 4.2 新鲜度守门（`lab/bench/workspace.py`）

- `check_freshness(workspace, run_time)` → `fresh` / `stale` / **`unknown`**
- 接进 `bench show` / `bench judge` / `judge-sheet`（stale 一律**显式告警**）
- 三态必须分清：把 `unknown` 当 `fresh`，就是把"没验证过"写成"验证过了"
- 基准用 `tasks.started_at`（它的实际语义是"结果落库时刻"，在 SUT 跑完之后）

### 4.3 产物摘要落库（`tasks.artifact_digest`）

- 判定前算一次工作区内容摘要（`sha256`，含 `input/`、排除 `__pycache__`），
  事后重算比对 —— **比 mtime 可靠**（mtime 会被复制/恢复/时钟调整骗过）
- ⚠️ **历史 661 行无法回填**（当时没算）→ 它们的校验结果只能是**"无法校验"**，
  而不是"一致"；`bench show` 会如实这么报
- schema 变更走 `_TASKS_GUARD_COLUMNS` 迁移（`ALTER TABLE`），向后兼容

## 五、修复过程中的**两次自纠**（都发生在我自己身上）

### 5.1 第一版检测器只报 1/100 —— 因为基准取自"被覆盖的那个东西"

第一版用 `store.load_task_by_workspace(workspace)` 取运行时间。
问题是：**工作区正是被覆盖的那一个** —— 覆盖之后按路径反查，拿到的是**后来那次**的行，
于是"基准时间"跟着漂到后面去，`stale` 永远检不出来。

改成按**运行身份**（`suite_id + task_key + run_index + arm`）查之后，恢复成 **39/100**。

> 单测当时全绿。**是"在真实数据上跑一遍"把它抓出来的** ——
> 这正是本项目那条纪律的又一次印证。已加回归测试钉住（`run_created_at` 的键控行为）。

### 5.2 项目自己的守卫抓到我漏改一处

`save_run` 里有一道一致性检查：`save_run` 的 dict、`_TASK_INSERT_COLUMNS` 常量、
以及那条静态 INSERT SQL **三处必须同步**。我加了列却漏了常量，它当场报错：

```
ValueError: save_run 的 dict 与 INSERT 列不一致（多了或漏了）：['artifact_digest']
```

修好后加列才生效。**防御性设计起作用了** —— 值得记一笔。

## 六、为什么它能潜伏这么久（机制）

1. **失败是静默的**：不报错、不影响判定、不影响成本指标 —— 只有"事后读产物"时才错。
2. **症状与真实问题不像**：表现为"某个任务怎么老是失败"（其实是读到了别人的产物），
   或"judge 判定和人工标注不一致"（其实是两边在看不同的东西）。
3. **它专挑"多 suite 复用同名目录"时发作**：项目里这种情形很常见
   （噪声地板跑了 4 轮、T6/T7 的 A/B 实验、A1 的重跑……），于是覆盖率很高。
4. **单测天然测不到**：每个用例只跑一个 suite。

## 七、能说 / 不能说

| 能说 | 不能说 |
|---|---|
| 工作区已按 suite 隔离，新运行不会再互相覆盖（有测试 + 变异检验：注入旧行为后测试确实 FAILED） | ❌ 不能说"历史数据的产物都可信了" —— 那 39% 已经丢了，无法恢复 |
| 读产物前会显式告警 stale，且**三种状态都有输出**（不会静默） | ❌ 不能说"新鲜度检查能保证产物一定对" —— 它只能发现"明显被换过"，同一次运行内的篡改看不出来 |
| 新运行的产物摘要落库，事后可校验（有端到端测试：写入 + 重算 + 比对一致） | ❌ 不能说"历史 661 行也能校验" —— 当时没算摘要，只能报"无法校验" |
| `bench recover` 同时支持新旧两种布局（历史目录仍可重建） | ❌ 不能说"recover 的结果与原始一致" —— 若目录已被覆盖，它重建的是**后来那份** |

---

## 八、遗留问题（写出来，而不是藏起来）

1. **历史产物无法恢复**：39% 的样本产物已被覆盖，任何基于它们的结论都要重新做。
2. **同次运行内的篡改**：摘要只能校验"目录是否变过"，防不了"运行期间就写错了"。
3. **`bench recover` 仍会张冠李戴**：它按目录反推运行；目录被覆盖时，它重建的是别人的。
   目前**只能靠新鲜度告警提醒**，没有硬拦截。
4. **candidate 池里 64% 是 stale**：说明这个缺陷的覆盖率比 39% 还高 ——
   凡是多轮复用同名目录的实验都中招（噪声地板、A/B、重跑）。
