## 三、关键设计决策

### 3.1 接缝选在 `GuardedTool` 代理，而不是改 SUT 的 `_invoke_tool`

handoff 原计划是"改 SUT 的 `_invoke_tool` 调用 `call_tool`"。实际做的时候发现更好的位置：
SUT 对工具只用 **四个成员**（`.name` / `.get_tools()` / `.has_tool()` / `.invoke()`），
所以一个代理就能接管全部工具调用：

```
真 FileTool  ←  GuardedTool(FileTool, guard)  ←  SUT 的 tools 列表
```

**收益不只是"少改一行"**：Step 4 的自研 loop 只要也用 `BaseTool`，
就自动获得同一套预算/熔断/重试/校验 —— **这才是 A/B 两边口径一致的前提**。
如果埋点写在 SUT 里，自研 loop 必须重复实现一遍，两边稍有差异，对比结论就不可信。

### 3.2 `retryable` 与"是否该重试"必须分开

SUT 原来的 D2 问题（重试导致重复副作用）根源是把两件事混成一件。现在拆开：

| 概念 | 谁决定 | 含义 |
|---|---|---|
| `ToolResult.retryable` | 工具自己 | "**这个失败类型**是不是暂态"（超时=是，路径越界=否） |
| `is_idempotent(name)` | 中间件的声明表 | "**重复执行**安不安全" |
| `decide_retry()` | 中间件 | 两者都为真才自动重试 |

**未知工具默认非幂等**（MCP 动态工具就属于这一类）：不知道就按危险处理，
少重试一次只是慢一点，多执行一次副作用可能已经写坏了数据。

### 3.3 中间件**永不抛异常**

所有失败都转成 `ToolResult(success=False, ...)` 返回。两个原因：
1. SUT 的 `_invoke_tool` 只在**异常**时才重试 —— 我们返回结果，它的重试循环自然退化，
   不会出现"中间件重试 3 次 × SUT 再重试 3 次 = 9 次"的双重试；
2. 可预期的失败应该走返回值、让 LLM 看到并自行决策，而不是用异常打断控制流
   （与 Step 1 修的 D4 同一个原则）。

### 3.4 后置校验的比较基准是**调用方的原始参数**

`write_file` 的校验逻辑是：用 args 复算出"本该写入的内容"，回读文件比对。
注意比较基准是**调用方想要什么**，而不是工具声称写了什么 ——
否则工具自说自话就永远校验通过。

### 3.5 预算检查放在两个位置

| 位置 | 覆盖什么 |
|---|---|
| 每次**工具调用**前 | 工具类预算（调用次数、循环） |
| 每次**LLM 调用**后 | token / 成本 —— 它们是在 LLM 调用时涨的 |

只查前者会漏掉"不停思考、不调工具"的失控路径（那类任务会完全绕过预算）。

## 四、🔴 真实运行的实测结果（本次最有价值的部分）

### 4.1 Baseline（observe，无故障注入）

```
[OK] steps=1/1 tools=10 llm=11 tokens=68,191 cost=$0.0424 elapsed=23.75s
预算[observe]: ✓ 越界维度 无（检查 24 次；本会中止=False）
循环检测     : 最长连续重复 1 次，熔断候选 0 次，动作多样性 1.00
```

无越界，多样性 1.00 —— 说明用户的 n=5 阈值对**正常任务**是合适的。

### 4.2 注入 `partial_write`（只作用于 write_file）

```
[OK] steps=2/2 tools=23 llm=29 tokens=203,326 cost=$0.1247 elapsed=56.8s
预算[observe]: ⚠️ 越界维度 ['tool_calls','tokens','cost_usd']（检查 52 次；本会中止=False）
循环检测     : 最长连续重复 1 次，熔断候选 0 次，动作多样性 0.52
故障注入     : {'partial_write': 6}
后置校验     : ⚠️ 6 条告警
  - write_file: 预期 26 字符，实际 13 字符（疑似部分写入/截断）: /home/ubuntu/f.txt
```

对比 baseline：

| 指标 | baseline | 故障注入 | 变化 |
|---|---|---|---|
| token | 68,191 | **203,326** | **+198%** |
| 成本 | $0.0424 | **$0.1247** | +194% |
| 耗时 | 23.75s | **56.8s** | +139% |
| 工具调用 | 10 | **23** | +130% |
| 动作多样性 | 1.00 | **0.52** | -48% |
| 错误数 | 0 | **0** | 不变 ⚠️ |

### 4.3 三条结论

**结论一：observe 模式第一次真实运行就证明了自己的价值。**
故障运行突破了 3 个软阈值（tool_calls / tokens / cost_usd），
**而且是在完全不干预的前提下**。这意味着：
- 用户给的阈值方向是对的（正常任务不越界、故障任务越界）；
- 但也说明**软阈值会被单次故障任务突破**，如果直接上 enforce，
  这类"本来能挣扎出结果"的任务会被砍掉 —— 所以先 observe 再定阈值是对的。

**结论二：`max_consecutive_repeat` 漏了，`action_diversity` 抓住了。**

这是本次最重要的技术发现。循环检测的两个指标给出了**相反**的结论：

| 指标 | 值 | 判断 |
|---|---|---|
| 最长**连续**重复 | 1 次 | ❌ 没发现问题 |
| 动作**多样性** | 0.52 | ✅ 明显异常（baseline 是 1.00） |

为什么漏了：Agent 反复写**同一个文件**，但每次内容长度不同（它在按校验结果调整），
于是 `(function_name, args)` 指纹每次都不同 —— 按"完全相同签名"定义的循环检测
**结构上就抓不到这种"近似重复"**。

**改进方向（Step 3.1 候选）**：把指纹从"全参数"改成**语义键**
（例如 `write_file + filepath`，忽略 content），检测"同一目标被反复操作"。
本次数据是提出这个改进的直接依据。

**结论三：所有 23 次工具调用都报 `✓ ok`，但一半是错的。**

轨迹里 6 次 `write_file` 全是绿灯，实际都只写了一半：

```
[tool] ✓ write_file @3172ms  ⚡fault=partial_write ⚠post=预期 26 字符，实际 13 字符
[tool] ✓ write_file @9110ms  ⚡fault=partial_write ⚠post=预期 93 字符，实际 46 字符
...
```

**如果只看 `success` 字段，这次运行是"完美成功"的。**
后置校验是唯一发现它的手段 —— 这就是为什么故障注入与后置校验**必须同时做**：
只做注入，你只会看到"成功率下降"，却分不清是模型变笨还是校验缺失。

### 4.4 阈值校准建议（基于本次数据）

| 维度 | 软阈值 | 硬上限(×2.5) | baseline | 故障运行 | 建议 |
|---|---|---|---|---|---|
| tokens | 150k | 375k | 68k ✅ | 203k ⚠️越界但未过硬线 | 保持 |
| 成本 | $0.10 | $0.25 | $0.042 ✅ | $0.125 ⚠️越界但未过硬线 | 保持 |
| 耗时 | 60s | 150s | 24s ✅ | 56.8s ✅未越界 | 保持 |
| 工具调用 | 15 | 37.5 | 10 ✅ | 23 ⚠️越界但未过硬线 | 保持 |
| 步数 | 15 | 37.5 | 1 ✅ | 2 ✅ | 保持（SUT 计划粒度很粗，15 步几乎不可能触发） |

**硬上限 2.5× 的设定在这次数据里被验证是合理的**：故障运行三次越界但都没过硬线，
说明 enforce 模式下它**不会**被误杀 —— 这正是我们想要的"只砍真正失控的"。

## 五、已知限制

| 限制 | 影响 | 何时处理 |
|---|---|---|
| 循环检测抓不到"近似重复" | 同一文件被反复操作看不出来（须看 diversity） | Step 3.1（本次数据已证明需要） |

| 无 `degrade` 实现 | 只有 observe 在用，degrade 是空壳 | 切模式时再实现 |
| MCP / A2A 工具未纳入幂等表 | 它们走"未知→非幂等"的默认分支 | 需要真 MCP 服务时再补 |
| `latency_spike` 只加固定延迟 | 无法模拟"长尾分布" | 需要时加分布参数 |
| 权限控制（handoff 提到的"权限"）未实现 | fast mode 只有文件/命令，无越权面 | 接入真沙箱时再做 |

## 六、下一步（Step 4：harness + 基线）

Step 4 的目标是 handoff 第 8 节那份指标模板。**第一件事是补数据落库**：

1. `tasks` 表加列（`budget_violated_metrics` / `budget_would_stop` / `faults_injected` /
   `postcondition_warnings` / `action_diversity`）+ 一个 `ALTER TABLE` 迁移函数
   （现在只有 `CREATE TABLE IF NOT EXISTS`，加不了列）；
2. `lab/bench/tasks/*.yaml`：10~20 个**确定性可验证**任务（含对抗/边界样本）；
3. `lab/bench/runner.py`：同一任务重复 n 次，输出 mean ± 95% CI；
4. `lab/bench/verifier.py`：确定性判定（文件内容/退出码/数值），**不靠 LLM judge 起步**；
5. `lab/report/`：markdown 报告 + Pareto 曲线（降 token 是否伤成功率）。

**Step 4 需要你确认一件事**：任务集的**领域边界**。

| 方案 | 内容 | 优点 | 缺点 |
|---|---|---|---|
| **A. 纯合成任务** | 自造 20 个"算数/文本处理/文件操作"任务 | 完全可控、确定性强 | 太玩具化，面试官会问"这能代表真实场景吗" |
| **B. 合成 + 半真实** | 合成 12 个 + 8 个真实小场景（CSV 清洗、日志统计、JSON 转换、代码修复） | 兼顾可控与说服力 | 真实任务需要仔细设计断言 |
| **C. 从真实需求倒推** | 用你自己工作里真遇到的任务（如"从两份 CSV 里对账"） | 最贴近生产 | 耗时长，且部分任务无法确定性验证 |

我推荐 **B**：12 个合成任务保证统计功效（能测出显著性差异），
8 个半真实任务保证"这不是玩具"的说服力。回 **A / B / C** 我就开始写 Step 4。
